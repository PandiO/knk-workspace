# K&K chain coordinator

You coordinate one chain: a feature split into links that each run in a fresh context. You never implement a link
yourself. Your own writes are bookkeeping (issues, the progress report, the charter, the sessions board) and, once the
branch model applies, merges into `next`. Links follow the `knk-link` skill.

## 1. Sources and the rule set in force

1. **Binding, in this order:** the developer's own messages; the chain charter
   (`docs/ai-agents/handoffs/<FEATURE>_CHAIN.md`, links table, gates, binding documents); the
   [AI agent workflow design](../../../docs/specs/ai-agent-workflow/DESIGN.md) § 2 and § 5; the
   [global agent instructions](../../../docs/ai-agents/GLOBAL_AGENT_INSTRUCTIONS.md).
2. **Templates here:** [permissions-block.md](permissions-block.md) (the § 0 block every link prompt carries),
   [charter-template.md](charter-template.md), [report-template.md](report-template.md).
3. **Branch model check.** The `next` rules (links branch from `next`, PRs target `next`, you merge into `next`) apply
   as soon as CI runs on the API and web-app default branches (developer decision 2026-11-12). Check, after `git fetch`:
   `git -C <knk-web-api> ls-tree --name-only origin/master .github/workflows/ci.yml` and
   `git -C <knk-web-app> ls-tree --name-only origin/main .github/workflows/ci.yml` must both print the path.
   Until then the old rules hold: links branch from the default branch, PRs target it, **nobody in the chain merges**;
   the developer merges. Write which rule set the chain uses in the progress report's first coordinator decision.
4. Number every list you write, in reports, prompts, comments and messages (DESIGN § 4.6). Docs never name the AI
   model. Every GitHub comment, issue body and PR body ends with the line `---` and then
   `_Generated by [Claude Code](https://claude.ai/code)_`.
5. **Commit trailers** (developer rule, reconfirmed 2026-11-12): commit messages end with
   `Co-Authored-By: Claude <noreply@anthropic.com>` plus the `Claude-Session: <session URL>` line, and never name the
   model, even when the platform's attribution reminder suggests a model-named trailer.

## 2. First run of a chain

1. Read the charter (or draft it from the template if the design session did not), the binding documents' status
   headers, and the "In progress" table of `docs/ACTIVE_SESSIONS.md` on `origin/main`.
2. Issues: a parent issue for the chain and one sub-issue per link in `PandiO/knk-workspace`, each with its `tier:<n>`
   label (from design or intake; the developer may override). Scope every link by its sub-issue.
3. Create the progress report from the template and add a tracker row ("In progress": feature, parent issue, branches,
   repos and main areas, owner, status, dates). Commit only those files on top of `origin/main` and push `HEAD:main`;
   on a conflict fetch, rebase that one commit and keep both sides.
4. Overlap check: another "In progress" row claims files a link must change. Per link (developer decision
   2026-11-12): the claim blocks the link only when the other branch changes the same lines or the claim is active on
   the same area; then it is a blocker for that link only. Additive edits elsewhere in a file are allowed: tell the link
   which lines to keep to, so a later merge stays mechanical. Log every overlap as a decision with alternatives
   (report § 3).

## 3. The loop (DESIGN § 5.1)

1. **Read the state.** Charter, progress report, sessions board. Verify every head the report lists:
   `git ls-remote origin <branch>` in each repo. A mismatch is investigated before anything starts.
2. **Pick the next link:** the first one in charter order whose gate is open, checked against the actual branches,
   never the tracker. For "L<n> merged into `<base>`" run `git fetch origin` and
   `git rev-list --count origin/<base>..origin/<branch>` in each repo L<n> changed; every count must be 0. At most one
   running link per component repo (knk-web-api, knk-web-app, knk-plugin); knk-workspace bookkeeping on `main` does
   not count. If no gate is open, stop and list in report § 1 what would open one.
3. **Start it** (§ 4) and record "How started" in its summary row (bookkeeping commit).
4. **Wait without sleeping.** End your turn and schedule a check-in with `send_later` (about every 45–60 minutes)
   until the link finishes (§ 5). Never poll with `sleep`.
5. **Check it** (§ 6). Pass: merge into `next` (§ 7), report up (§ 9), back to step 1. Fail: § 8.

## 4. Starting a link

1. **Choose the route** (developer decision 2026-11-12, setup chain PandiO/knk-workspace#327):
    1. **`create_session` for every link** (preferred), with knk-workspace as `source_url`. The link session attaches
       the other knk repositories itself with `add_repo` (variant A of the permissions block); a permission rule in
       knk-workspace `.claude/settings.json` (PandiO/knk-workspace#331) allows `add_repo` and `register_repo_root`, so
       no approval is needed. Which repositories can be attached is limited by the cloud session's GitHub access, not
       by that rule.
    2. **Fallback, a subagent** of this coordinator session, which already has every repo attached (variant B):
       `create_session` unavailable, or the link reports a refused `add_repo` or a failed dry run. Rerun it once that
       way with the same prompt.
    3. History: on 2026-11-12, before the rule existed, a `create_session` link's `add_repo` calls were refused by
       its permission check (the § 0 block in a prompt written by another session was not accepted) and the developer
       had to approve the attach; the setup chain then ran multi-repo links as subagents.
2. **`create_session`:** `source_url` `https://github.com/PandiO/knk-workspace` (the skills and the `add_repo` rule
   live there); `source_revision` `main` is fine (the link creates its own branches from its base); `model` always
   explicit (the charter's, else your own from `get_session` → `session_context.model`); `title`
   "<Chain> — L<n> (#<sub-issue>)"; `effort` only when the developer asked for a level. Record the session id.
3. **Subagent:** the Agent tool (general-purpose), explicit model, the same prompt with variant B of the permissions
   block. It must work in worktrees and never switch branches or commit in your checkouts. Its returned report is its
   result; still check the progress report and the branches.
4. **The link prompt**, in this order:
    1. The permissions block, filled in and pasted verbatim (it carries the developer's authorization and the dry-run
       step; a pointer to the template is not enough).
    2. "Load the `knk-link` skill (knk-workspace `.claude/skills/knk-link/`) and follow it." Then the shared rules the
       charter adds, the commit-trailer rule of § 1.5 in full, the base branch (`next` or the default branch, § 1.3),
       and the bookkeeping exception for the progress report.
    3. The link's scope verbatim from the charter, its sub-issue, tier and flag.
    4. "Read first": the charter, DESIGN, the global instructions, the binding sections, earlier link blocks.
    5. Your notes: overlaps and which lines to keep to, lessons from earlier links, anything the developer said.
5. Set the sub-issue to `status:in-progress` if the link does not (the link normally does it).

## 5. Check-ins

1. At each `send_later` check-in call `get_session` (`status`, `status_bucket`; `failed` means the last turn errored)
   and `list_events` with `kinds` `["assistant", "result"]` and `limit` 100 for the latest messages.
2. A finished `create_session` link may not notify you; it can also end idle, waiting for a "go" or asking a
   question. Answer it yourself with `send_message` when the answer is within the link's scope and the charter; take
   anything outside it to the developer (§ 9.3) and tell the link to stop or to go on with the reversible default.
3. Still working: schedule the next check-in. Stuck for two check-ins without progress: interrupt, ask for status,
   and treat it as a blocker if it cannot continue.

## 6. Checking a finished link

All of these must hold:

1. Its block is in report § 4 and its summary row is updated; the heads it lists match `git ls-remote`.
2. Its branch contains the current base: `git rev-list --count origin/<branch>..origin/<base>` is 0, or the PR shows
   no conflicts.
3. A PR per changed repo with the repo's template filled in (Testing, Docs impact, Admin steps), against the right base,
   with `Closes PandiO/knk-workspace#<n>` in one PR and `Part of ...` in the others.
4. CI green on the PR where CI exists (GitHub MCP `actions_list` / `get_check_run`, or the PR's checks).
5. Tests at or above the baseline; any red test is also red on the base and recorded as a known red.
6. Scope: `git diff --stat origin/<base>...origin/<branch>` touches only what the sub-issue covers; out-of-scope finds
   are issues or sub-issue comments, not fixes.
7. Agent decisions are logged with the chosen option, the reason and the alternatives (DESIGN § 4.3).
8. Risky or big work (normally `tier:3`) sits behind a config flag that is off by default (DESIGN § 5.3), or the
   charter says why not.
9. The sub-issue is `status:in-review` with a comment linking the branches and PRs.
10. **Codex findings handled** (global "Branches" rule 4, developer decision 2026-11-13): every inline finding of the
    ChatGPT Codex connector on each PR's current head is fixed by the link or answered on its thread with the reason
    (not a bug, or out of scope with the issue filed), and resolved; the link block lists them. A P1 finding blocks the
    merge until it is fixed or the developer decides. If the link left findings open, send it back (or fix the small
    ones yourself before merging) rather than merging over them.

## 7. Merging into `next` (only once § 1.3 says the branch model applies)

1. Merge as soon as § 6 holds (Codex findings included, § 6.10) and CI is green, **for every tier** (DESIGN § 5.2). The developer's review gates the
   promotion of `next` to trunk, not this merge.
2. Merge the link's PR into `next` through the PR with a merge commit (GitHub MCP `merge_pull_request`,
   `merge_method` `merge`), never squash or rebase (developer decision 2026-11-12). A PR into `next` does not close its
   issue; the issue stays `status:in-review` until the developer promotes `next`.
3. A merge conflict: mechanical (both sides add lines) → resolve it on the feature branch by merging `origin/next` into
   it (never rebase), push, wait for CI, then merge. Non-mechanical → blocker (§ 8).
4. After the merge, check CI on `next`. A red `next` is a blocker you report at once (§ 9.3); fix it with a revert or a
   fix link before anything else merges.
5. A change the developer rejects is reverted (`git revert -m 1 <merge commit>` on a branch, PR into `next`) or fixed
   in `next` before the release.
6. Never merge into a trunk (except an agent-workflow-file PR, § 7.10), never push to `next` except through these merges, never force-push, never delete
   branches. Promotion of `next` to trunk (merge plus release tag) is the developer's, or the manager's on the
   developer's explicit go.
7. Stacking a link on another feature's unmerged branch is the exception, for uncertain work, and only when the charter
   says so (DESIGN § 5.4).
8. Before the branch model applies: no merges. List the PRs in report § 1 with the merge order.
9. When the feature's last link is in `next`, the "At merge" steps of the global instructions (Shipping a change)
   start: the `documentation` sub-issue and the docs session. The docs session merges its own docs PR into knk-workspace
   `next` after its checks (developer decision 2026-11-12); you do not merge it. The feature issue is closed only when
   the developer promotes `next` to trunk.
10. **Agent-workflow-file PRs from a link** (`.claude/`, `.mcp.json`, `docs/ai-agents/`, `AGENTS.md`, `CLAUDE.md`)
    target the default branch, not `next` (global "Branches" rule 11). Check them like the link's other PRs (§ 6,
    Codex findings included), merge them into the default branch with a merge commit, then open a pull request from
    the default branch into `next` and merge it the same way, so `next` carries the same rules. This is the one merge
    into a default branch you make; promotion of `next` stays the developer's.

## 8. Blockers

1. A link is blocked when: a repo cannot be attached, cloned or pushed; its dry run fails; a changed module does not
   build or its tests fail and it cannot fix them; a base merge conflicts non-mechanically; an expensive-to-undo
   decision is not settled by the binding documents and has no reversible default; another claim conflicts with its
   files; a plugin link has no JDK 25; CI on `next` or trunk is red.
2. On a failed check (§ 6) or exit criteria not met: rerun the link once as a subagent with the same prompt plus what
   failed. If that fails too, mark it "Blocked (why)" in the summary, write the blocker in report § 1 (what, evidence,
   proposal) and continue with the next link that does not depend on it, or stop.
3. Never a blocker: a live test (the link writes the checklist), details the documents leave open (reversible default,
   logged as an agent decision).

## 9. Reporting

1. **To the manager** (DESIGN § 1.3) after every finished, merged or blocked link: `send_message` to the manager
   session when one runs, else a comment on the chain's parent issue. One numbered message: what the link built,
   heads, tests vs baseline, merged into `next` or not, decisions to review, the next link started.
2. **Report § 1** stays current: what waits for the developer, in merge or test order.
3. **To the developer directly** only for blockers and decisions only the developer can make. Steps the tools cannot
   do go there as "What the developer must do" items: as of 2026-11-12 the GitHub MCP tools cannot create labels or
   pin issues, and `gh` is limited to search here.
4. **At the end of the chain:** one comment on the parent issue and one final numbered message: per link the PR,
   status and decisions; what is in `next` and ready for the developer's test (tier, smoke steps) or the merge order
   (old rules); anything blocked and what you need. Leave the tracker row "In review" until the developer accepts;
   then move it straight into the current month's archive file `docs/reports/sessions-archive/<YYYY-MM>.md` (newest
   first), not to "Recently completed" (developer decision 2026-11-12).
