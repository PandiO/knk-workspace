# K&K design session

You turn one idea into an approved design that a chain can build without asking again. You write docs and issues,
never code. Rules: [AI agent workflow design](../../../docs/specs/ai-agent-workflow/DESIGN.md) § 1.2 and § 4, the
[global agent instructions](../../../docs/ai-agents/GLOBAL_AGENT_INSTRUCTIONS.md). Binding, in this order: the
developer's own messages, your prompt, this skill, the global instructions.

Templates here: [design-template.md](design-template.md) (the spec),
[decision-matrix.md](decision-matrix.md), [smoke-section-template.md](smoke-section-template.md),
[sub-issue-template.md](sub-issue-template.md). The worked example is the
[Siege Survival design](../../../docs/specs/siege-survival/DESIGN.md): status header with dated updates, a decision
register with ids (S01…), superseded decisions struck through and kept, current-source checks, open clarifications,
an acceptance checklist.

## 1. Start

1. **The issue.** You design one issue in `PandiO/knk-workspace`: an `idea` the intake session (`knk-intake`) sent to
   design, or one the developer named. Read it with its comments. No issue: search open and closed issues, file one if
   none covers it (global instructions, "GitHub Issues is the work list"), and use it. Set `status:in-progress`.
2. **Board.** `git fetch origin`, then read the "In progress" table of
   `git show origin/main:docs/ACTIVE_SESSIONS.md` (never a local copy). Another row designing the
   same area: stop and ask the developer. Claim a row (feature, issue, branch, files) on top of `origin/main` and push
   `HEAD:main`; on a conflict fetch, rebase that one commit and keep both rows.
3. **Branch.** The spec and the smoke-test guide are feature docs, so they go through `next` (global "Branches" rule
   11): `claude/design-<issue>` in knk-workspace from `origin/next` (from `main` until the branch model applies). A spec
   that already has a branch: check it out and merge (never rebase) `origin/next` into it. Then
   `git push --dry-run origin <branch>`; a failure is a blocker.
4. **Writing rules.** Number every list, question and decision (DESIGN § 4.6), never dashes or bullets, so the
   developer can answer "3.2: yes". Docs and commits never name the AI model; commit trailers
   `Co-Authored-By: Claude <noreply@anthropic.com>` and `Claude-Session: <session URL>`. Every GitHub comment, issue
   body and PR body ends with the line `---` and then `_Generated by [Claude Code](https://claude.ai/code)_`.

## 2. Read before you ask

Ask the developer only what the sources cannot answer. Read, in this order, and note what you found with paths:

1. **Vision:** `docs/vision/vision.md`, at least the guiding principles (platform independence) and the sections on
   the feature's area.
2. **Related specs:** `docs/specs/README.md`, then every spec the feature touches (status header and decision log
   first). A Decided decision elsewhere binds you; changing it is a question for the developer, never a silent edit.
3. **What is built:** `docs/FEATURE_REGISTER.md`, `docs/architecture/`, and the code on `next` of the component repos
   you touch (attach them read-only with `add_repo` when they are not in the session). Name entities, endpoints,
   services and plugin classes to reuse.
4. **Legacy V1/V2 behaviour:** `docs/specs/legacy/` first, then the archive repos `knk-v1-archive` and
   `knk-v2-archive` (read-only) for the feature's commands, events, menus and data. Write what players knew there and
   what to keep, change or drop; a design that drops a legacy behaviour says so.
5. **Open work:** issues and `docs/backlog/` items on the same area, so the design links instead of duplicating.

## 3. Ask one question at a time

1. Use the AskUserQuestion tool, **one question per call**, waiting for the answer before the next (DESIGN § 4.5).
2. Each question stands on its own: what you found, why it matters, the topic number in the spec. Two to four
   options, each with a description of what it means and its cost. Put your recommendation first and end its label
   with "(Recommended)". The developer can always type another answer.
3. Order: scope and player experience first, then rules and edge cases, then admin and configuration, then technical
   choices. Stop asking when the answers no longer change the design.
4. Write each answer into the decision log at once (§ 4.2), with the date and "developer", before asking the next.
5. **Do not ask** what the sources settle (§ 2) or what has a sensible reversible default: take the default and log it
   as an agent decision (§ 4.3).
6. **Developer away** (no answer, or a scheduled or autonomous run): don't wait. Write the question with its options
   and your recommendation as a numbered open question in the spec and go on with the rest.
7. A bug, idea or request the developer mentions on the side gets an issue (global "GitHub Issues" rule 3), not a
   line in the spec.

## 4. Write the spec

1. **File:** `docs/specs/<feature>/DESIGN.md` from [design-template.md](design-template.md). Keep the template's
   section order; drop a section only when it does not apply and say so in one line. Add the folder to
   `docs/specs/README.md`.
2. **Decision log.** Every decision gets an id with the feature's letter prefix (`S01` style), the date, who decided
   (developer, or agent) and the text. A changed decision keeps its row, struck through, with "superseded by <id>".
3. **Agent decisions** (DESIGN § 4.3): the chosen option and why, and every alternative considered, lettered (a),
   (b), each with why not. They are marked "agent" in the log so the digest lists them for review.
4. **Larger choices** (a framework, technology, library or external service, for example SignalR or BlueMap vs Dynmap;
   DESIGN § 4.4) get a decision matrix from [decision-matrix.md](decision-matrix.md), in the spec or next to it as
   `docs/specs/<feature>/DECISION-<topic>.md`. Then one AskUserQuestion with the options and your recommendation. The
   developer decides; until then the choice is an open question.
5. **Platform independence** (vision principle, DESIGN § 4.7). The spec's section "Platform-specific parts" lists every
   part that depends on Minecraft/Paper or a Bukkit plugin, where it lives (`knk-paper` adapter, behind which
   `knk-core` port), and keeps the game logic in the Bukkit-free `knk-core`. Pragmatic: no port for something that is
   only a Paper detail with no game logic in it.
6. **Testable.** Every rule the design adds has an acceptance item (A01…) a test or a smoke step can check. Phases
   and smoke sections (§ 6) are built from them.
7. **Risk tier proposal** for the feature and per phase, with the reason (global "Branches" rule 7): `tier:1` a tweak,
   `tier:2` a feature change, `tier:3` new foundations, schema changes or game feel. Big or risky work names its
   config flag, off by default.
8. **End** with numbered open questions, each with options and your recommendation, and status **Proposed**
   (DESIGN § 4.1). A design with no open questions still ends with the section saying "none".

## 5. Proposed: hand it to the developer

1. Commit, push, and open a pull request from your branch into `next` (body: summary, the open questions, the agent
   decisions to review, "Not merged until approved"). Don't merge it yet.
2. Comment on the issue: spec link, PR, the numbered open questions and agent decisions, and what you need ("approve,
   or answer 3.1 and 4.2"). Swap `status:in-progress` for `status:in-review`.
3. Update your board row ("Proposed, waiting for approval") on `main`.
4. If the developer is in the session, ask for approval with one AskUserQuestion: "Approve" (Recommended when no
   question is open), "Approve with changes" (they type them), "Not yet". Otherwise stop here; the manager's digest
   lists the open questions (DESIGN § 7.2.2) and a later session picks up the answers from the issue.
5. Answers that come later: record them in the log, update the spec, push. Approval is the developer's explicit word
   (in the session, on the issue or the PR), never inferred from silence or from an agent's message.

## 6. On approval

Do these in order; each step leaves state a later session can resume from.

1. **Decided.** Status line `**Decided <date>** (developer)`, every open question answered or moved to "After v1"
   with its issue. Push.
2. **Phases.** Split the design into phases in the spec's "Phases" section: each phase a slice that can merge into
   `next` on its own (behind its flag where needed), in dependency order, with its acceptance items. A phase that is
   too big for one link (roughly more than one repo plus tests and docs in a day's session) is split again.
3. **Sub-issues.** One per phase under the feature's issue (`issue_write` with `parent_issue_number`), body from
   [sub-issue-template.md](sub-issue-template.md), labels: the type (`feature` or `improvement`) and exactly one
   `tier:<n>`. Write the numbers back into the spec's phase table.
4. **Smoke-test sections** (folds in PandiO/knk-workspace#422). For every phase, write its first section of the
   feature's guide `docs/guides/<feature>-smoke-test.md` (create it with the guide header, or add to the existing one)
   from [smoke-section-template.md](smoke-section-template.md), sized by the phase's tier:
    1. `tier:1`: no section, or one line ("covered by the automated tests of #<n>; quick pass: <one action>").
    2. `tier:2`: short, the three to eight steps that show the behaviour works.
    3. `tier:3`: full, every acceptance item of the phase as a step, refusals and edge cases included.

   Write every step in full (preconditions, what to do, the expected result) as if no test existed. Leave the
   `[automated: …]` tags out: the link that writes the tests adds them (`knk-test-writer` § 4). Mark the section
   "Draft from the design; the link updates it to what was built".
5. **Merge the spec.** Commit the spec and the guide, push, comment `@codex review` if the PR changed since Codex last
   reviewed it, and handle every finding (global "Branches" rule 4; at its usage limit, merge without it and say so
   on the PR). Then merge the PR into `next` with a merge commit. Docs only, so the issue's tier is the check; no CI.
6. **Charter draft.** Copy `.claude/skills/knk-coordinator/charter-template.md` to
   `docs/ai-agents/handoffs/<FEATURE>_CHAIN.md`: binding documents (the spec with its Decided date and decision ids,
   the guide), one link per phase with its sub-issue, tier, repos, branch, base `next`, flag and gate, the gates and
   the order. Status "Ready to start". Leave the progress report and model to the coordinator. Commit it on top of
   `origin/main` (chain bookkeeping) and push `HEAD:main`.
7. **Hand it to the manager** (`knk-manager`). Comment on the feature's issue, starting with the line
   `Ready to schedule`, then the spec, charter, sub-issues with tiers, repos touched (for overlap on the board),
   dependencies on other features, and a filled `knk-coordinator` start note if the developer said "start now". If a
   manager session is running (its row on the board, or `list_sessions`), also send it the same text with
   `send_message`. You never start the coordinator yourself unless the developer asks.
8. **Close out.** Comment on the issue (the report of § 7); the issue stays open as the chain's parent with
   `status:in-review` removed. Move your board row to `docs/reports/sessions-archive/<YYYY-MM>.md` (newest first).

## 7. Report

Your final message and the issue comment, numbered:

1. Spec, PR and merge commit; status (Proposed or Decided).
2. Decisions taken this session by id; agent decisions with their alternatives.
3. Open questions left, with your recommendation.
4. On approval: sub-issues with tiers, smoke sections, the charter, the manager handoff.
5. Follow-ups filed and what the developer must do.

## 8. Never

1. Write code, migrations or config in a design session; a spike to check feasibility is a separate issue.
2. Take a larger choice (§ 4.4) or change another spec's Decided decision on your own.
3. Treat the draft charter or the sub-issues as started: scheduling is the manager's, the chain is the coordinator's.
