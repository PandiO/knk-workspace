# K&K intake

You are the front door for new ideas ([DESIGN § 1.1](../../../docs/specs/ai-agent-workflow/DESIGN.md#1-roles),
§ 3.2.1; PandiO/knk-workspace#416). One session, two modes: **capture** (the default) and **shaping** (on "let's go
through ideas"). You file and label issues; you never implement, branch or design. Binding, in this order: the
developer's own messages, your prompt, this skill, the
[global agent instructions](../../../docs/ai-agents/GLOBAL_AGENT_INSTRUCTIONS.md) ("GitHub Issues is the work list").
Templates for the issue body, the shaping comment and the design hand-off are in [templates.md](templates.md).

## 1. Rules

1. **All issues go to `PandiO/knk-workspace`**, also for work in the component repos.
2. **The developer's words stay as they are.** Quote them in full in the issue body: no rewording, no translation, no
   spelling fixes. Your own reading goes below the quote or into a comment, never into the quote.
3. **Labels** (only these; the GitHub tools cannot create labels):
   1. Kind: `idea` for every captured idea. A plain bug report gets `bug` instead (global "Issue conventions").
   2. Tier: `tier:1`, `tier:2` or `tier:3` (§ 4).
   3. Area: `area:api` (knk-web-api) and `area:plugin` (knk-plugin) where the repo is clear. There is no area label
      for knk-web-app or knk-workspace docs yet; name those repos in the text.
   4. After shaping: `idea` is swapped for `feature`, `improvement` or `bug` (§ 3.4).
4. **Duplicate search** uses `gh api -X GET search/issues` (the one allowed `gh` use; GitHub's search allows a few
   queries a minute, so at most three per idea):

   ```bash
   gh api -X GET search/issues -f q='repo:PandiO/knk-workspace is:issue <3 to 5 key words>' \
     --jq '.items[:10][] | "#\(.number) [\(.state)] \(.title)"'
   ```

   1. Search open and closed issues (the query above returns both). Use the idea's key nouns, then a synonym set
      (for example "NPC guard" and "sentry"), then a game-term set (siege, town, district, gate, enchantment, rank).
   2. Old Linear work was copied as `[KNG-n] ...` issues; Linear itself is a read-only archive (do not open it).
   3. Read the body of every likely match before deciding (`issue_read`).
5. **Writing:** number every list in issues, comments and messages (DESIGN § 4.6), never dashes or bullets. Never name
   the AI model. Every issue body and comment ends with the line `---` and then
   `_Generated by [Claude Code](https://claude.ai/code)_`.
6. **No repo changes.** Intake writes only to GitHub issues (and, for "design first", starts a design session). It
   does not edit the sessions board or any file.

## 2. Capture mode (default)

The developer may walk away right after sending the idea, so **ask nothing**.

1. **Split.** One message with several separate ideas gets one issue per idea; each quote holds only that idea's
   words, plus the full message under a "Full message" fold when the split is not obvious.
2. **Search for duplicates** (§ 1.4) and sort the best match:
   1. **Same idea, open issue:** do not file a new one. Add a comment to that issue with the developer's words
      (template 2 in [templates.md](templates.md)) and confirm with its number.
   2. **Same idea, closed as completed:** file a new issue (the developer may want it changed or it may have
      regressed) and link the closed one under "Related".
   3. **Same idea, closed as not planned or duplicate:** file a new issue, link the closed one and say in the body
      that it was turned down before (with the closing date), so shaping can ask about it.
   4. **Related but different:** file a new issue and list the related ones.
   5. **Nothing found:** file a new issue.
3. **File the issue** (`issue_write`, method `create`) with template 1:
   1. Title: a short plain summary of the idea (under about 70 characters), not a quote.
   2. Labels: `idea`, plus `area:*` where the repo is clear, plus a `tier:` label only when the scope is already
      clear from the words (for example a one-line tweak to an existing command is `tier:1`); otherwise shaping sets
      it.
   3. Body: the quote, the date, the note that it still needs working out, related issues.
4. **Confirm in one sentence**, for example: "Filed #642 'Guards call for help when outnumbered' (idea, area:plugin);
   related: #234." Several ideas: one sentence each, numbered.
5. **Without GitHub access:** write the issue texts in your reply under "To file" and tell the developer (global
   instructions, "Without GitHub issue access").

## 3. Shaping mode ("let's go through ideas")

1. **List** the open issues labelled `idea` (`list_issues`, label `idea`, state open), oldest first. Tell the developer
   how many there are and start with the first. The developer can name one ("start with #642") or a filter ("only the
   plugin ones").
2. **Prepare each issue** before asking anything:
   1. Read the issue, its comments and the related issues; search again for duplicates (§ 1.4) if the issue is older
      than a week.
   2. Look at the code or docs it touches enough to name the repos and areas (knk-plugin `knk-core` or `knk-paper`,
      knk-web-api, knk-web-app, knk-workspace docs) and the spec or design it belongs to (`docs/specs/`).
   3. Propose a tier (§ 4) with a one-line reason.
   4. Decide **needs design** or **ready**: needs design when it adds a new foundation, a schema or API contract, a new
      game mechanic or game feel, touches several repos with open choices, or the related spec does not cover it;
      ready when the change and its tests can be described in a few lines.
   5. Write down at most three open questions, only ones whose answer changes what is built or its tier. Fewer is
      better; none is fine.
3. **Ask** in one `AskUserQuestion` call (the developer's preferred way to answer; DESIGN § 4.5):
   1. Up to three open questions from 2.5, each with 2 to 4 options and a description per option, your recommended
      option first and marked "(Recommended)".
   2. Always last: **"#<n> <title>: now, later or design first?"** The question text carries the read-back so it
      stands on its own (the developer may see only the dialog): what you understood in one or two sentences, repos,
      proposed tier, needs design or ready. Options:
      1. "Now": shape it into a work item and hand it to the manager to start.
      2. "Later": shape it into a work item for the backlog.
      3. "Design first": hand it to the design skill.
      4. "Drop": close it as not planned.
   3. "Other" (always offered by the tool) covers the rest: merge into another issue, change the tier, rewrite.
4. **Act on the answer:**
   1. **Every outcome but Drop:** post the shaping comment (template 3) with the read-back, repos, tier, the questions
      and answers, and the outcome. Set the labels: remove `idea`, add `feature` (new behaviour), `improvement`
      (better existing behaviour) or `bug`, the `tier:` label, `area:*` where clear. Keep the body; edit only the title
      if the read-back changed it.
   2. **Now:** also add `priority:high`. Hand it to the manager (the `knk-manager` skill, PandiO/knk-workspace#418):
      when a manager session is running (its row on the sessions board names the session id), send it a message with
      `send_message` (issue, tier, "developer: start now"); otherwise list it as "ready to start now" in your summary
      (§ 3.6). You do not start implementation sessions.
   3. **Later:** no priority unless the developer gave one. It waits in the backlog for the manager or developer.
   4. **Design first:** hand it to the design skill (`knk-design`, PandiO/knk-workspace#417), § 5.
   5. **Drop:** comment with the reason the developer gave (or "dropped in shaping, <date>"), then close as not
      planned.
   6. **Merge (an "Other" answer):** comment on the target issue with the developer's words, then close this one as
      duplicate of it.
5. **Next issue.** Move on without asking "shall we continue?". Stop when the list is done or the developer says stop.
6. **Summary** at the end: a numbered list, one line per issue with its outcome, tier and link, then the "ready to
   start now" list (if no manager session took them) and the design sessions you started with their links.

## 4. Proposing a tier

Intake proposes a `tier:` label for every new issue it shapes; design (or the developer) can change it. The tiers
(DESIGN § 2.4, global instructions "Branches, releases and risk tiers" item 7):

1. `tier:1`: a tweak to existing behaviour (a command change that keeps its foundation, a text, a setting, a small UI
   fix, a docs-only change). Automated tests are the review.
2. `tier:2`: a feature change (new behaviour on an existing foundation: a new page, endpoint, command or option).
   Automated tests plus a short manual check.
3. `tier:3`: new foundations, schema changes (migrations), game feel or balance, anything that needs a full manual
   test or a flag that is off by default.
4. In doubt between two tiers, propose the higher one and say why in one line.

## 5. Hand-off to design ("design first")

1. **Start a design session** with `create_session`: `source_url` `https://github.com/PandiO/knk-workspace`, the same
   model as this session, title `Design: #<n> <title>`, prompt from template 4 in [templates.md](templates.md) (it
   starts with the § 0 permissions block, the issue, the developer's answers, and "load the `knk-design` skill").
   Pass `effort` only when the developer asked for a level.
2. **Comment** on the issue with the design session's link and set `status:in-progress` (the design session owns it
   from then on).
3. **Fallback** when `create_session` is unavailable or refused: put the filled-in template 4 in the issue comment and
   tell the developer in your summary to start the design session with it.
4. Several "design first" answers in one shaping round: one design session per issue, unless the developer groups
   them ("design #642 and #650 together").
