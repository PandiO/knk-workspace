- **Recommended model (A):**
  - `knk.admin.delete` (one record) and `knk.admin.delete.bulk` sit on top of the existing area nodes;
  - delete = area AND `knk.admin.delete`;
  - bulk = area AND delete AND bulk, through a new `POST api/Dashboard/bulk-delete` (max 100 ids, per-row results, one
    audit entry);
  - only the owner (`*`) may grant bulk or a wildcard covering it;
  - an additive migration grants both nodes to Admin (a no-op where `knk.admin.*` covers them) and backfills
    `knk.admin.delete` to every explicit area-node holder, so nobody loses a delete on day one;
  - the dashboard opens for any area node, with per-type checks from metadata;
  - realtime follows the area node per type.
- **Findings for the developer:**
  - no migration seeds `knk.admin.content` or `knk.admin.world` to any group (only Admin's `knk.admin.*` on the alpha
    covers them);
  - world-only staff can write world data through the API but can't open the dashboard (its route needs
    `knk.admin.content`);
  - Staff (`knk.admin.user.manage`) can delete user accounts through the API today;
  - a bare grant `knk.admin.delete` does not match `knk.admin.delete.bulk`, but `knk.admin.delete.*` matches both.
- **Flagged decisions:** none taken; 11 open questions in DESIGN § 7, each with a recommendation.

## Link P1 — #261: kit "Grant" from the web app reaches the player in game
Started: subagent of the coordinator, 2026-11-08; finished 2026-11-08.

- **Root cause:** `POST api/Kits/{id}/give` → `KitService.GiveKitAsync` writes the `KitClaim`, the `KitGranted`
  audit entry and the lootbox tokens and returns the loadout to its caller. Items are only ever placed by the plugin,
  and only in its own flows (`KitGrantFlow` → `KitGrantPlacer` for `/kit get|give|purchase` and the kits menu), which
  place straight from that response. From the web app the response goes to the browser, nothing tells the game server,
  and nothing records that a hand-over is owed — so the items never arrived (not late: never). Self-claims and
  purchases work because the plugin is the caller; purchases don't place at all (they unlock a later `/kit get`).
- **Fix (existing mechanisms):** the claim row is the delivery record (new nullable `DeliveryRequestedAt`,
  `DeliveredAt`); the player notification queue nudges (`KitDeliveryPending`, no payload — pushed by the hub-backed
  queue when realtime is on, polled every 2 s when off); the join reads the rows directly, so a lost or expired nudge
  delays nothing past the next join. Pattern of the lootbox tokens' `undelivered` + `LootboxTokensIssued`.
  - API: give from anyone but the game server (plugin key **without** a web login) sets `DeliveryRequestedAt` and
    queues the nudge; response gains `claimId`, `deliveryPending`; audit details gain `deliveryPending`.
    `GET api/Kits/deliveries/pending?userId=` and `POST api/Kits/deliveries/{claimId}/delivered?userId=` (both
    `[RequirePluginService]`, in `ProtectedRoutes`): the take is one conditional `ExecuteUpdate … WHERE DeliveredAt IS
    NULL` → 200 for the one winner, 409 `AlreadyDelivered`, 404 `NoPendingDelivery`.
  - Plugin: `kit/KitGrantDelivery` (resolve → take → place with `KitGrantPlacer` → "A staff member gave you the "X"
    kit."), `listeners/KitDeliveryJoinListener` (100 ticks after join, up to 4 tries while the account isn't cached),
    `PlayerNotificationPoller.setKitDeliveryHandler`, after-siege hook next to `deliverLootboxItemsAfterSiege`;
    api-client `pendingDeliveriesAsync`/`markDeliveredAsync`. `/kit give` unchanged.

- **Flagged decisions:**
  - **LP1-1** "Placed by the game server" = plugin key and no web login; everything else queues a delivery (also a
    web user under the development key bypass). A plugin configured with `api.auth.type: bearer` would count as a web
    user and get the items twice for `/kit give` — reversible (an explicit flag in the give body) if that mode is used.
  - **LP1-2** Take before place (at most once). A server crash, or the player logging out, in the instant between the
    API's 200 and the placement loses that one hand-over; the log names the claim (grant again). Place-then-confirm
    would risk a duplicate instead, which #261 rules out.
  - **LP1-3** Held back during a siege (hub or match), handed over by the after-siege restore hook, as lootbox
    tokens are (also matches #125's "pending deliveries are respected").
  - **LP1-4** One nudge type without payload; the plugin always re-reads the pending list (no claim id in the
    notification), so a stale or duplicate nudge is harmless.
  - **LP1-5** Items that can't be resolved (blueprint missing, API down) are not taken and stay pending for the next
    join or nudge; nothing retries on a timer.
  - **LP1-6** Unchanged on purpose: a staff grant still starts the kit's cooldown and issues its lootbox tokens; old
    claim rows are never pending (`DeliveryRequestedAt` NULL), so earlier web grants are not delivered retroactively
