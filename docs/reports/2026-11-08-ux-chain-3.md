## Link P1 — #261: kit "Grant" from the web app reaches the player in game
Started: subagent of the coordinator, 2026-11-08; finished 2026-11-08.

- **Root cause:** `POST api/Kits/{id}/give` → `KitService.GiveKitAsync` writes the `KitClaim`, the `KitGranted`
  audit entry and the lootbox tokens and returns the loadout to its caller. Items are only ever placed by the plugin,
  and only in its own flows (`KitGrantFlow` → `KitGrantPlacer` for `/kit get|give|purchase` and the kits menu), which
  place straight from that response. From the web app the response goes to the browser, nothing tells the game server,
  and nothing records that a hand-over is owed — so the items never arrived (not late: never). Self-claims and
  purchases work because the plugin is the caller; purchases don't place at all (they unlock a later `/kit get`).
- **Fix (existing mechanisms):** the claim row is the delivery record (new nullable `DeliveryRequestedAt`,
  `DeliveredAt`); the player notification queue nudges (`KitDeliveryPending`, no payload — pushed by the hub-backed
  queue when realtime is on, polled every 2 s when off); the join reads the rows directly, so a lost or expired nudge
  delays nothing past the next join. Pattern of the lootbox tokens' `undelivered` + `LootboxTokensIssued`.
  - API: give from anyone but the game server (plugin key **without** a web login) sets `DeliveryRequestedAt` and
    queues the nudge; response gains `claimId`, `deliveryPending`; audit details gain `deliveryPending`.
    `GET api/Kits/deliveries/pending?userId=` and `POST api/Kits/deliveries/{claimId}/delivered?userId=` (both
    `[RequirePluginService]`, in `ProtectedRoutes`): the take is one conditional `ExecuteUpdate … WHERE DeliveredAt IS
    NULL` → 200 for the one winner, 409 `AlreadyDelivered`, 404 `NoPendingDelivery`.
  - Plugin: `kit/KitGrantDelivery` (resolve → take → place with `KitGrantPlacer` → "A staff member gave you the "X"
    kit."), `listeners/KitDeliveryJoinListener` (100 ticks after join, up to 4 tries while the account isn't cached),
    `PlayerNotificationPoller.setKitDeliveryHandler`, after-siege hook next to `deliverLootboxItemsAfterSiege`;
    api-client `pendingDeliveriesAsync`/`markDeliveredAsync`. `/kit give` unchanged.

- **Root cause:** `RealtimeClient.stop()` ran `setState(STOPPED)` (a volatile write) and only then
  `transport.stop()` on its executor thread. The test waits for `state() == STOPPED` and then reads the fake
  transport's `stopCalled` at once, so a poll that landed between the two steps saw STOPPED with `stopCalled` still
  false. The window is a few instructions wide: 2000 repeats on `main` passed, which is why it showed up only in full
  builds under load.
- **Fix (client, not the test):** `stop()` requests the transport close first and publishes STOPPED after it (in a
  `finally`, so a throwing transport still ends STOPPED). STOPPED now means "the close was requested" (issue's
  second option); the test's existing wait for STOPPED is then the right signal and needs no sleep or retry.
  Production is unaffected: `RealtimeService.stop()` already waits for the executor to terminate, and nothing else
  reads STOPPED as a signal.

    saw a new state could still read the old connects/disconnects. Stats now go first. No current test depended on

    written after the state, or on transports created after it).

## Link P3 — #269: temp regions of abandoned drafts removed within minutes, not after 14 days
Started: subagent of the coordinator, 2026-11-09; finished 2026-11-09. Own worktrees under `/home/user/wt-P3/`.

- **Design (no binding document; issue text):** the API **releases** a region, the game server **removes** it. New
  table `temp_region_releases` (one row per world task; no foreign key, so a row outlives a task the sweep deletes with
  its session). The plugin polls `GET api/WorldTasks/temp-region-releases?serverId=` every 5 minutes and settles each
  release (`POST …/{id}/settle`: Removed / Missing / Kept, which deletes it). Both sides check before anything goes; when
  unsure the region stays and the 14-day cleanup decides.
- **When a region is released (API):**
  - draft deleted (`FormSubmissionProgressService.DeleteAsync`, the web app's Delete in Saved Progress; queued before the
    delete clears `world_tasks.FormSubmissionProgressId`): its region tasks — Completed unless the result picked an
    existing region ("select"), open ones (listed once closed), other closed ones a server held;
  - a region task closes without a result after a game server held it (`ClaimedAt` or `ReleaseCount` > 0): Cancelled
    (web cancel, "Capture again", `POST …/status`), Failed (also a refused completion), Expired (sweep; claim after
    expiry). Covers what #180 couldn't: a crash after drawing, lease lapsed, task expired;
  - the sweep removes the task's session (same save as the removal; the sweep's rules are unchanged).
  "Region task" = field `WgRegionId` (how the plugin routes to `WgRegionIdTaskHandler`) or a result naming its temp region.
- **When it is listed (API):** 5 min after the release and after the task's last change; task closed or gone; not a
  Completed task of a draft that still exists; server matches or unknown; and **nothing names the region**, any world,
  case-insensitive: domain or domain sub-region `WgRegionId`, lootbox area region or `ExcludedRegionIds`, road edge
  `RegionIdsJson`, any draft's step data (text match: a longer id containing it also keeps it). Rows older than 30 days

  `tempregion_worldtask_<taskId>` only; in exactly one loaded world (the task's world when loaded); not while a player here
