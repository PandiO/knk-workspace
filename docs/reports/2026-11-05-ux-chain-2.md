**Flagged decisions (reversible)**
- **LR1-1** A new feed table, one row per erased account, rather than the deletion-request rows (request order ≠
  execution order, one request erases several accounts, the UUID is cleared by the erasure).
- **LR1-2** The feed keeps the former UUID **35 days** (`Privacy:ErasureFeedUuidRetentionDays`, at least 31: past the
  plugin's 30-day max age), then clears it and keeps the row. A server catching up later deletes by user id only.
- **LR1-3** The push doesn't move the stored position; it applies at once and starts a catch-up (one extra GET per
  erasure), which moves it. Two erasures committing out of id order around a catch-up could be skipped (very rare: one
  hourly job); the hourly verifier is the backstop.
- **LR1-4** No `erasure-feed.json` (first start, or lost) = catch up from 0: the whole retained feed is applied again
  (idempotent). A position past the API's `latestId` (another database) restarts from 0.
- **LR1-5** Returning player (fresh account, same Minecraft UUID): the API serves such a row with `formerUuid: null`,
  and the plugin treats a UUID it knows under another user id (user cache, offline store) the same way: no kick, user-id
  steps only.
- **LR1-6** Kick message "Your account data has been deleted." (configurable); 2 s settle between kick and wipe. A
  player who rejoins inside those 2 s as a new account could lose that join's fresh local entries (offline store).

**Flagged decisions**
- **LX1-1:** no `staff` group. Each event is sent to holders of the node that gates the same data over REST, checked per
  message with the REST permission check: `knk.admin.content` (the dashboard's and detail page's route node) for every
  dashboard type; `knk.admin.user.manage` for `User`, `UserPermissionGroup`, `PermissionGrant`, `PermissionHolder`,
  `AuditLogEntry` and for `PresenceChanged` (same node as `GET api/Users`, the moderation list and the profile
  summary). `api/Presence/online-staff` (`knk.admin.world`) is unchanged and not used for the badges.
- **LX1-2:** never sent to the web: `UserIgnore` (plugin-only reads), `CurrencyTransaction`, `KitPurchase`, `KitClaim`
  (a player's ledger/purchases), `ItemInstance` (lootbox managers). Reversible: one set in `RealtimeWebChangeMap`.
- **LX1-3:** the "holds node" answer is cached 30 s per user and node (`Realtime:WebPermissionCacheSeconds`, 0 = check
  every message): a node taken away stops the events within 30 s (REST is denied at once). A failed check is "no" and
  not cached.
- **LX1-4:** a Town (District, Structure, …) also sends `EntityChanged` for its `[FormConfigurableEntity]` base type
  `Domain`, so a Domain list refreshes too.
- **LX1-5:** your own saves are skipped (by `actorUserId` = the connection's user), also in your other tabs; the game
  server's and background jobs' saves (no actor) count, shown as "Updated at …" — e.g. gate health or siege match rows
  written by the game server refresh a dashboard showing those types (one re-read per 750 ms burst).
- **LX1-6:** burst window 750 ms, then one quiet re-read; the "Updated by … at …" line stays until the next update or
  another type; a hub reconnect (also the first connect after the page loaded) re-reads once without a line (P2).
- **LX1-7:** detail page: only changes to that entity (or a `null`-id burst of its type); changes to related entities
  (a town's districts) don't refresh it. On delete the page stays with the old values and a warning with Back; Edit and
  Delete stay (they answer 404).
- **LX1-8:** moderation list: one player's change updates their rows in place; rows are never added or removed (an
  "online only" result keeps a player who went offline, shown Offline; Search re-runs the filter); a `userId: null`
  change or a reconnect re-reads the shown list quietly with the search/filter it was last run with.
- **LX1-9:** profile badge from the profile summary's new `presence` (`User.IsOnline`, the column the moderation list
  shows), "Offline · last seen <date>"; no badge for an account without a Minecraft UUID; the server id is not shown
  (one server).
- **LX1-10 (→ changed 2026-11-06 by the developer: `Realtime:WebLiveUpdatesEnabled`, default `true`; Coordinator notes):** not behind a switch: the web hub is on for every logged-in tab since WT2, so staff get the live updates
  whenever the API runs this branch (a UI change, charter §3). Presence follows the game also with the plugin's

- **LX1-11:** `actorName` is the `username` claim of the saver's access token (a rename shows the old name until their
  token renews).
- **LX1-12:** the web events are only built while at least one web hub connection (any user) is open; the per-node filter
