  `knk-paper` `realtime/ErasureRealtimeSync`, `privacy/{BukkitErasureKicker,ErasureSettings}`, `KnKPlugin`

  `DiscoverySpool.deleteAccount`, `StatisticsSpool.removeUser`, `PrivateMessageLogShipper.purge`,
  `LocalFilePrivateMessageLog.purge`, `SiegePlayerVault.discard`. Flow: kick → settle → main-thread steps → worker

**Flagged decisions (reversible)**
- **LR1-1** A new feed table, one row per erased account, rather than the deletion-request rows (request order ≠
  execution order, one request erases several accounts, the UUID is cleared by the erasure).
- **LR1-2** The feed keeps the former UUID **35 days** (`Privacy:ErasureFeedUuidRetentionDays`, at least 31: past the
  plugin's 30-day max age), then clears it and keeps the row. A server catching up later deletes by user id only.
- **LR1-3** The push doesn't move the stored position; it applies at once and starts a catch-up (one extra GET per
  erasure), which moves it. Two erasures committing out of id order around a catch-up could be skipped (very rare: one
  hourly job); the hourly verifier is the backstop.
- **LR1-4** No `erasure-feed.json` (first start, or lost) = catch up from 0: the whole retained feed is applied again
  (idempotent). A position past the API's `latestId` (another database) restarts from 0.
- **LR1-5** Returning player (fresh account, same Minecraft UUID): the API serves such a row with `formerUuid: null`,
  and the plugin treats a UUID it knows under another user id (user cache, offline store) the same way: no kick, user-id
  steps only.
- **LR1-6** Kick message "Your account data has been deleted." (configurable); 2 s settle between kick and wipe. A
  player who rejoins inside those 2 s as a new account could lose that join's fresh local entries (offline store).
- **LR1-7** Minecraft's own files (`players/data|stats|advancements`, plus the pre-26.1 folders) are listed in
  `plugins/KnightsAndKings/erasure-minecraft-files.txt` (paths contain the UUID), never deleted; the server log only
  says how many. The owner deletes them and clears the list.
- **LR1-8** The siege vault entry is discarded without a restore (the account is gone); the player's Minecraft
  inventory stays in their `.dat` (LR1-7).
- **LR1-9** Not deleted locally: statistics/telemetry still in memory and an in-flight PM batch (delivered, then dropped
  by the API for an erased account, D16), Paper's own server logs.
- **LR1-10** Accounts without a UUID (web-only, merged) get a row and a push too; the plugin deletes by user id.
- **LR1-11** With `realtime.enabled: false` nothing new runs, not even a catch-up at startup (behaviour = today's).
- **LR1-12** `realtime.erasure` lives under `realtime:` in `config.yml`; no `/knk health` line for the position.
