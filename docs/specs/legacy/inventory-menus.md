# Legacy inventory-menu (GUI) framework

> **Note:** A v3 rebuild of the inventory-menu system appears to have just landed (`Merge branch 'InventoryMenus' into main` in knk-workspace's recent git history). This document was written as forward-looking rebuild research but may now be more useful as **retrospective/comparison material** against whatever v3 already decided. See `docs/specs/legacy/README.md` for the index/principles of this folder. `docs/specs/inventory-menu/*` (the v3 spec) was intentionally not read while writing this file.

> **See also (2026-09-25):** [inventory-menu-screens.md](inventory-menu-screens.md) catalogues every legacy screen and item and allocates each to a v3 feature (this doc's open question 4). Its §5 corrects two statements below: the Kit overview's pagination never worked (it runs on the base `Menu` stubs, not `ContentGroup`), and the `menu/` rewrite *was* used in normal play by the Creation wizard's multi-select stage.

This covers the clickable chest/inventory GUI *framework* itself (how menus are opened, how clicks are routed, how pagination/back-navigation work, how items are built) — not the business logic of any one specific menu, which is used here only for illustration.

## Data model

### v1 — no dedicated menu domain model
Everything is a raw `org.bukkit.inventory.Inventory` built ad hoc inside one god-class, `v1:src/Menu/Menu.java` (6228 lines, ~60 `open*` methods, one per menu screen — `openHouselist`, `openPropertylist`, `openSkillMenu`, `openGateManager`, `openHSManager`, `openSiegeInformation`, etc.).

- Item construction helpers are static and free-floating: `MenuClick.addmenulist(...)`, `MenuCommand.addpmenu(...)`, `MenuCommand.addemptypmenu(...)` (`v1:src/Menu/MenuClick.java:479-508`, `v1:src/Menu/MenuCommand.java:82-115`) — all build an `ItemStack` from displayName/Material/lore varargs. No click behavior is attached to the item itself; a second, "richer" path builds items via `Product.createItem(...)`/`addItemDescription(...)` for purchasable content.
- Per-user menu state is a scatter of independent static `Map<UUID, ...>` fields spread across unrelated classes, with no unifying "session" concept: `MenuCommand.pmenu` and `MenuCommand.simenu` (`v1:src/Menu/MenuCommand.java:35-36`), `MenuClick.houselistmap/houselistpage/propertylistmap/propertylistpage/roomlistmap/roomlistpage/ownedhousesmap/ownedpropertiesmap` (`v1:src/Menu/MenuClick.java:48-55`), `SkillMenuClick.skillmenus` (`v1:src/Menu/SkillMenuClick.java:38`). `MenuCommand.simenu` is declared and never read or written anywhere else in the codebase (grep confirms zero other references) — dead state.
- "Which menu is currently open" is identified entirely by the `Inventory`'s **display-name string** (`e.getInventory().getName()`), compared against string constants in `Handlers.Menus` (e.g. `Menus.HouseListMenu`, `Menus.PersonalMenu`).
- The `User` domain object (`v1:src/Users/User.java`) does track menu state properly, though: `menu`/`menuPrevious` fields with `openMenu()/closeMenu()/getOpenMenu()` (lines 3476-3507), plus `menuViewers`/`menuViewing` supporting an admin "spectate another player's open menu" feature (mirrored inventory + the spectator's own clicks cancelled, see `v1:src/Listeners/InventoryListener.java`).

### v2 — three co-existing generations across two package trees
`src/main/java/net/knightsandkings/model/menu/**` and `src/main/java/net/knightsandkings/menu/**` are **not** a simple old-vs-new pair; they represent three layers of the same idea, evolved in place, with the newest layer never wired to the live game:

1. **`model/menu/` base (`Menu`, `MenuItem`, `IMenu`, `IMenuItem`)** — the original, and still-live, domain model. `Menu` implements `IPersistent<Integer>`, `IDisplayable<Integer>`, `IMenu` (`v2:src/main/java/net/knightsandkings/model/menu/Menu.java:32-34`): fields for `owner`, `target` (the user whose data is shown — may differ from the viewer, e.g. an admin viewing another player's info), `menuItems` list, `previousMenu`, `pageCapacity`/`currentPage`. `MenuItem` (`v2:.../model/menu/MenuItem.java`) implements `IMenuItem` + `IClickable` + Bukkit `Listener`; unlike v1 it carries a real `List<MenuItemAction>` keyed by `ClickType` triggers (`MenuItemAction`, `RunnableAction` — a proper functional click-callback pattern, `v2:.../model/menu/MenuItemAction.java`, `RunnableAction.java`).
2. **`model/menu/Menu2` extends `Menu`** — the actually-used mid-generation evolution. Adds composition via `ButtonGroup`/`MenuSection`/`SubSection` (`model/menu/group/*`) with automatic slot-overlap detection/resolution (`getOverlappingSlots`, `formatHeaders`) and dynamic runtime inventory expansion (`expandInventory`). `ContentGroup extends ButtonGroup` (`v2:.../model/menu/group/ContentGroup.java`) implements real generic pagination (see Business rules below). `group/cachable/CachableOverview<T,Key>` (`v2:.../model/menu/group/cachable/CachableOverview.java`) is a generic "list of persisted/cached objects" `MenuSection` built on top of `ContentGroup` and is what backs the Kit/Siege/Cache/Dominion overview screens.
3. **`menu/` (separate top-level package) + `command/menu/`** — an independent, more ambitious rewrite. Flexbox-like layout primitives: `IMenuObject`/`MenuObject` (start X/Y, absolute/relative flags, align/position/priority, `v2:.../menu/IMenuObject.java`), `MenuShape` (explicit start/stop X/Y + width/height + horizontal/vertical alignment math with validated bounds, `v2:.../menu/MenuShape.java`), and enums under `menu/enumerations/` (`AlignContent`, `AlignHorizontal`, `AlignVertical`, `Display`, `Growth`, `ListMode`, `Overflow`, `Position`, `Priority`). It introduces a **definition-vs-rendered-instance split**: `menu/Menu`, `MenuSection`, `MenuItem` are templates; `menu/displayed/MenuDisplayed`, `DisplayedMenuItem`, `DisplayedMenuSection` are the actual per-player rendered/cacheable state. `menu/MenuSession` (`v2:.../menu/MenuSession.java:22-33`) is an explicit browser-history analogy — "functions as a session of a user in an internet browser" — tracking `menuHistory` (a list of `MenuDisplayed` ids) and `previousMenu`. A generic pagination contract exists here too: `menu/pages/IPagable<T,O>` + `PageControl` enum (`TOPBOTTOM`, `LEFTRIGHT`, `TOP`, `BOTTOM`, `LEFT`, `RIGHT`) (`v2:.../menu/pages/IPagable.java`, `PageControl.java`). A separate text-templating system, `menu/variable/Variable`/`VariableString`/`VariableList`/`VariableUtil`, uses a `$self.getX.getY$` chained-getter reflection syntax. `command/menu/*` (`MenuOpenCommand`, `MenuConstructionCommand`, `MenuPreperationCommand`, `InventoryPreperationCommand`, `MenuSectionDisplayCommand`, `MenuVariableUpdateCommand`, etc.) implements an async, multi-stage, thread-pooled "open a menu" pipeline with an optional loading screen.

**Relationship, concretely evidenced**: the live `/menu` command (`v2:src/main/java/net/knightsandkings/spigot/command/menu/MenuCommand.java`, `@Default onDefault`) opens `net.knightsandkings.model.menu.main.MainMenu` — i.e. tree #2 (`Menu`/`Menu2`). The `menu/`+`command/menu/` rewrite (tree #3) is reachable only via the same class's `@Subcommand("test")` (`onTest`, permission `k&k.menu.menu.test`), which constructs `net.knightsandkings.menu.preset.menu.MainMenu` via `MenuOpenCommand` — and even there, the code that would persist the resulting `MenuSession` and (on one path) actually open the inventory for the player is commented out (lines 92-99). Both `menu/` and `model/menu/` last received commits on the same two consecutive days (2022-12-21/22 — see Finished vs WIP), so they were developed in parallel and abandoned together, not sequentially.

## Business rules and behavior

### v1 — illustrated via `Menu.java`, `MenuClick.java`, `HouselistClick.java`, `SkillMenuClick.java`, `GemShopClick.java`

- **Click routing is one global listener for every menu in the plugin.** `v1:src/Menu/MenuClick.java` `Onclick(InventoryClickEvent)` (lines 58-443) resolves which menu was clicked by string-matching `e.getInventory().getName()` against ~50 `Menus.XxxMenu` constants (an `if/else if` chain, lines 297-435), then either handles Personal-Menu clicks inline via a second string match on the clicked item's stripped display name (lines 99-296, `dc.contains("houselist")`, `dc.contains("gem-shop")`, etc.) or delegates to one of ~25 per-menu `*Click` classes (e.g. `new HouselistClick(main).onClick(e, user)`).
- **The entire routing block is gated behind `MenuCommand.pmenu.containsKey(uuid)`** (line 84) — a static map `put` exactly once, inside `OpenPersonalMenu` (`v1:src/Menu/Menu.java:237`), and never removed. In practice this is harmless because every menu is reached by first opening the Personal Menu (which populates the map before the click can occur), but it means "has this player touched the menu system this session" is being tracked via a map whose literal purpose (holding the currently-open Personal-Menu `Inventory`) is unrelated, and the map grows forever.
- **`OpenPersonalMenu(user)`** (`v1:src/Menu/Menu.java:151-254`) hand-places ~20 items at hardcoded slot constants (financial, skills, teleport, titles, social, gem-shop, assignments, events, support, plus admin-only items gated by `user.inOwnerModus()`), then calls `fillEmptyMenu` to pad remaining slots with glass panes, then `user.openMenu(pmenu)`.
- **Pagination is fully hardcoded.** `openHouselist(user, Integer pagenumber, Integer townID)` (`v1:src/Menu/Menu.java:587-745`) uses a `switch(pagenumber)` mapping page numbers 2-10 to fixed starting indices exactly 45 apart (`case 2: startingindex = 46; … case 10: startingindex = 406;`), with `default` silently falling back to index 0 (page 1) for any unmapped page. The "current page" a Next/Previous button remembers is **not stored anywhere** — it is re-parsed out of the clicked item's own lore text at click time: `HouselistClick.onClick` (`v1:src/Menu/HouselistClick.java:54`) does `Integer current = Integer.valueOf(e.getCurrentItem().getItemMeta().getLore().get(2).split(": ")[1]);`.
- **Item building** mixes two idioms throughout: hand-rolled `MenuClick.addmenulist`/`MenuCommand.addpmenu` (display name + varargs lore, no click semantics) and `Product.createItem(...)` + `addItemDescription(...)` for purchasable items, which bakes owned/affordable coloring directly into lore text (e.g. green "Available! Click here to buy!" vs red "Unavailable!").
- **Back-navigation is ad hoc per menu.** Each `*Click` class hardcodes which parent menu to reopen (`GemShopClick.onClick` → `menu.OpenPersonalMenu(user)`; `SkillMenuClick.onClick` → same) rather than using `User.menuPrevious`, which exists but is not consulted by these handlers.
- **Admin "spectate a player's menu"**: `User.menuViewers`/`menuViewing`, mirrored via `openMenu()/closeMenu()` broadcasting to viewers, with the spectator's own clicks cancelled (`v1:src/Listeners/InventoryListener.java:91-94`).
- **Item "blink" (flashing highlight)**: `v1:src/Menu/MenuItemBlink.java` runs an async `BukkitRunnable` (`runTaskTimerAsynchronously`, lines 106-133) that toggles a slot between the real item and a stained-glass pane every 10 ticks — mutating a live Bukkit `Inventory` off the main thread.

### v2 — illustrated via `model/menu/Menu.java`, `Menu2.java`, `MenuItem.java`, `ButtonGroup.java`, `ContentGroup.java`, `BackMenuItem.java`, `PageButton.java`, `main/MainMenu.java`, `group/cachable/CachableOverview.java`

- **Click routing is per-Inventory-instance, not global.** `Menu.onClick(InventoryClickEvent, User)` (`v2:.../model/menu/Menu.java:476-500`) looks up the clicked `MenuItem` by slot (`findMenuItem`), then calls `clickedItem.onClick(event.getClick(), clicker)`. `MenuItem.onClick` (`v2:.../model/menu/MenuItem.java:269-292`) iterates its `MenuItemAction` list and runs whichever actions' `triggers` (`List<ClickType>`) contain the click type — a real per-item, per-click-type dispatch table, replacing v1's inventory-title/display-name string matching for routing.
- **Back-navigation is generic.** `BackMenuItem` (`v2:.../model/menu/BackMenuItem.java`) reads `menu.getPreviousMenu()`; if null it exits (`owner.closeMenu(true)`), otherwise it reopens the previous menu (`previousMenu.open()`). Its label/lore is templated via `%getBackPhrase%` (see bug below).
- **Pagination is real and generic — but only inside `ContentGroup`.** `ContentGroup` (`v2:.../model/menu/group/ContentGroup.java:274-420`) slices its item list by `getPageCapacity()` (= number of content slots) via `getPageContent`/`getPageStartIndex`; `nextPage()/previousPage()` adjust `currentPage` and re-render (`this.getMenu().display(this)`); Prev/Next `PageButton`s auto-show/hide based on `contentSlots.size() < menuItems.size()`. `CachableOverview` (used for Kit/Siege/Cache/Dominion "overview" screens) delegates its listing to a `ContentGroup`, so those screens page correctly once content exceeds slot capacity — a genuine improvement over v1's hardcoded indices.
- **But the base `Menu.nextPage()/prevPage()` are unimplemented stubs** (`v2:.../model/menu/Menu.java:410-420`) that just play a fail-sound and return, and `ButtonGroup`'s own `changePage/getCurrentPage/getLastPage/nextPage/previousPage` default to throwing `UnsupportedOperationException` (`v2:.../model/menu/group/ButtonGroup.java:487-505`) unless a subclass overrides them — only `ContentGroup` and `creationstage/SelectMenu` do.
- **`Menu2`** (`v2:.../model/menu/Menu2.java`) composes a menu out of `MenuSection`s ("Headers"), auto-detects/resolves slot overlap (`getOverlappingSlots`, `formatHeaders`, reversed-priority ordering in `display(List<? extends ButtonGroup>)`), and can grow the backing `Inventory` at runtime (`expandInventory`; `createInventory` sizes off summed section slot counts via `MenuUtil.getMenuSize`).
- **Two unrelated dynamic-text mechanisms coexist.** `%getX%`-delimited reflection lookup for `model/menu` item names/lore, invoked from `MenuItem.updateVariables` via `MenuUtil.convertVariable`/`convertVariables` — versus a completely separate `$self.getX.getY$` chained-getter system (`menu/variable/VariableString` + `VariableUtil`) used only by the orphaned `menu/` framework.
- **The live root menu is sparse.** `model/menu/main/MainMenu` (`v2:.../model/menu/main/MainMenu.java:44-74`) places exactly: `BackMenuItem`@8, `KitOverviewItem`@12 (opens `KitOverview`, fully functional including pagination), `SiegeOverviewItem`@14 (functional), and a "Overview of Caches" item@22 whose own lore reads "For debug purposes only." That's the entire live `/menu` surface area found in this codebase.
- **The orphaned `menu/` framework's open flow** (`v2:.../command/menu/MenuOpenCommand.java`) is a genuinely more sophisticated async pipeline: submits `MenuConstructionCommand` (reflective constructor matching via Apache Commons `ConstructorUtils`) and `InventoryPreperationCommand` to a 1-thread `ExecutorService`, optionally opens a `LoadingMenu` first, updates a persisted `MenuSession`, then reopens the finished `Inventory` on the main thread via `BukkitRunnable`. None of this runs during normal play.

## Known edge cases / bugs

1. **v1 Houselist/Propertylist/Roomlist pagination `IndexOutOfBoundsException`** — clearly a bug. `openHouselist` (`v1:src/Menu/Menu.java:618-621`) loops `for (int i = startingindex; i < startingindex+45; i++) { houselist.add(list.get(i)); }` with no check that the list actually has `startingindex+45` elements; whenever the underlying list length isn't an exact multiple of 45 (the common case), opening the final page throws.
2. **v1 pagination hard-caps at page 10** — clearly a bug. The same `switch(pagenumber)` only defines cases 2-10; page 11+ (or any unmapped value) silently resets to page-1 content while the lore still claims the requested page number — wrong content shown silently instead of erroring or clamping.
3. **v1 Houselist "Back" button contradicts its own label** — clearly a bug. The item reads "Click here to go back to your personal menu" (`v1:src/Menu/Menu.java:648`) but `HouselistClick.onClick` (`v1:src/Menu/HouselistClick.java:47-51`) actually calls `menu.openOwnedHouses(user)`, not the personal menu.
4. **v1 static per-player maps are never cleared** (`MenuCommand.pmenu`/`simenu`, the several `MenuClick.*map`/`*page` fields, `SkillMenuClick.skillmenus`) — likely a bug: no quit-event cleanup was found anywhere in the codebase, so these grow for the life of the server process, one entry per player who has ever opened the relevant menu since last restart. Low severity, but genuine unbounded memory growth.
5. **v1 `openHouselist(user, Integer pagenumber, …)` unboxes `pagenumber` in a `switch`** — might be intentional, unclear: no current call site passes `null`, but if one ever did this throws `NullPointerException` before rendering anything.
6. **v1 `MenuItemBlink` mutates a Bukkit `Inventory` from an async scheduler task** (`runTaskTimerAsynchronously`, `v1:src/Menu/MenuItemBlink.java:106-133`) — likely a bug: Bukkit/Spigot's inventory API is not thread-safe; this is a known corruption/crash source even if it "worked" in practice on the Spigot build it targeted.
7. **v2 `%...%` template variables are never substituted** — clearly a bug. `MenuUtil.convertVariable`'s own doc-comment describes `%`-delimited codewords ("Example: %timeformat_time%…", `v2:src/main/java/net/knightsandkings/util/MenuUtil.java:228`), but the implementation compiles `Pattern.compile("$(.*?)$")` (line 242) — literal, unescaped `$` regex anchors, which in Java regex can only match a zero-width string at the very end of input. Every `%getBackPhrase%`, `%getPageDirection%`, `%getCurrentPage%/%getLastPage%`-style placeholder used throughout `model/menu` (`BackMenuItem`, `PageButton`, …) would render as literal, un-interpolated text in-game.
8. **v2 `Menu2.expandInventory` validates the wrong variable** — likely a bug. It computes `newMax = currentMax + slots` but the overflow guard checks `if (currentMax > Menu2.INV_MAX_SIZE)` (`v2:.../model/menu/Menu2.java:551-554`) instead of `newMax > INV_MAX_SIZE`; since `currentMax` is always ≤53 for any existing valid inventory, the guard can never actually fire — the very expansion that would push the inventory past 54 slots is never blocked before being handed to `Bukkit.createInventory`.
9. **v2 base `Menu.prevPage()/nextPage()` are no-op stubs** that just play a fail sound (`v2:.../model/menu/Menu.java:410-420`) — might be intentional, unclear: harmless today since every screen found pages through `ButtonGroup`/`ContentGroup` instead, but any future `PageButton` attached directly to a `Menu` (not a group) would silently do nothing.
10. **v2 `MainMenu`'s debug-only "Overview of Caches" button is not permission-gated** differently from the Kits/Sieges buttons next to it, despite its own lore saying "For debug purposes only" (`v2:.../model/menu/main/MainMenu.java:56-58`) — might be intentional, unclear whether this was meant to ship visible to regular players.
11. **Two unrelated, differently-delimited variable-templating systems coexist** in v2 (`%x%` reflection in `MenuUtil`, `$self.x.y$` chained-getter in `menu/variable/*`) — likely evidence of an in-progress migration between conventions that was never finished or reconciled; compounds bug #7.

## Finished vs work-in-progress

**v1**: the menu system is "finished" in the sense of being fully wired end-to-end — every button reachable from the Personal Menu reaches a working handler, and no orphaned/dead `*Click` classes were found among those reviewed (all are reached from `MenuClick.Onclick`'s dispatch chain). Code shape nonetheless shows heavy accumulated patching: large commented-out blocks left in place rather than deleted (e.g. `v1:src/Menu/Menu.java:701-738`, old item-building logic superseded by `Product.createItem`; `v1:src/Menu/MenuItemBlink.java:84-88,112-124`, commented-out safety checks), and a single 6228-line god-class as the only real architecture.

**v2** splits three ways:
- **`model/menu/` (live system)**: unevenly finished. `MainMenu` itself is very sparse (2 functional buttons + 1 debug button + Back); Kit and Siege overviews work end-to-end including real pagination via `ContentGroup`; but the root menu never grew to cover v1's feature set — houses, properties, rooms, financial, titles, friends/social, gem-shop, assignments, quests, events, support, teleport, admin tools all have no `model/menu` equivalent found anywhere in this codebase. The variable-substitution mechanism used for item lore/names is broken (bug #7), so even "finished" screens would show raw `%codeword%` text to players in practice.
- **`menu/` + `command/menu/` (the flexbox-style rewrite)**: substantial, deliberate engineering investment (layout enums, definition/rendered-instance split, session/history tracking, async open pipeline, generic `IPagable`) — but never wired to the live `/menu` command. It's reachable only via the permission-gated `/menu test` subcommand, whose own follow-through (persisting the `MenuSession`; on one path, actually opening the menu for the player) is commented out (`v2:src/main/java/net/knightsandkings/spigot/command/menu/MenuCommand.java:92-99`). Git history corroborates mid-work abandonment: the last commits ever made to the `menu/` package tree are `10cab12 Update for Page functionality of MenuSection` and `937dfe7 Begun working on a Page-functionality for MenuSections` (both 2022-12-21) — i.e. this framework's own pagination support was actively being built when work stopped. The repository's last two commits touching either menu tree are `Revert`s of an unrelated "CreationStageSelect" change, and the very last commit in the whole repo's history (`400e5c8`, 2022-12-22) touches unrelated Dominion/Town equality-check code, not menus at all.
- Per the task brief's general caution that feature branches like `ImprovedMenus`/`ImprovedPagable` might never have merged: **checked directly, they are in fact both fully merged into `main`** (`git merge-base --is-ancestor origin/ImprovedMenus main` and the `ImprovedPagable` equivalent both report zero unmerged commits). So the `menu/` package as seen on `main` already *is* that accumulated work — it simply was never cut over to be the live system, rather than being lost on an unmerged branch.
- **Net read**: this is direct, concrete evidence for the project owner's own account that v2 had *less finished functionality* than v1 despite better architecture — v2's late-2022 development window went into building a second, more ambitious menu framework instead of porting v1's feature set onto the first (already-working) one, and development stopped before either was feature-complete.

## v1 vs v2 differences

- **Click dispatch**: v1 routes every click through one global `Listener` string-matching the clicked `Inventory`'s display name (`v1:src/Menu/MenuClick.java`) → v2 dispatches per-`MenuItem` via a `ClickType`-keyed `MenuItemAction`/`RunnableAction` list (`v2:.../model/menu/MenuItem.java`). Real upgrade: no fragile display-name/lore parsing for *routing* (though lore-text templating for *display* is itself broken — see bug #7).
- **Pagination**: v1 is fully hardcoded (switch-case of magic starting indices assumed to be exactly 45 apart, "current page" round-tripped through item lore text, hard ceiling at page 10, unguarded `IndexOutOfBoundsException`) → v2's `ContentGroup` computes pages generically from slot-capacity vs. item-count with no hardcoded indices, and auto-hides Prev/Next when unnecessary. Genuine improvement where it's actually used; not universal (base `Menu`-level paging is an unimplemented stub, bug #9).
- **Back-navigation**: v1 hardcodes the parent menu per `*Click` class (with at least one demonstrated mismatch, bug #3) → v2 has a generic `BackMenuItem` driven by `Menu.getPreviousMenu()`.
- **Persistence/architecture**: v1 has no ORM involvement at all — menus are pure in-memory `Inventory` objects plus scattered static maps → v2's `model/menu` classes implement `IPersistent`/`IDisplayable` and save into a cache-backed `RepositoryManager` (`SaveMode.ONLY_CACHE`); the newer `menu/` tree adds a persisted `MenuSession`/`MenuDisplayed` split intended for real caching, though its repository-write call site is left commented out.
- **Composition**: v1 has no reusable "section" concept — every one of ~60 `open*` methods in the 6200-line `Menu.java` hand-places every item at a literal slot number → v2 introduces `ButtonGroup`/`MenuSection`/`SubSection` composition with automatic overlap resolution and dynamic inventory resizing (`Menu2`), and the orphaned `menu/` tree goes further with an explicit flexbox-style layout model (align/position/growth/overflow/priority enums).
- **Functional coverage regression**: v1's Personal Menu exposes roughly 20 features from one screen. v2's live `MainMenu` exposes 2 gameplay features (Kits, Sieges) plus one debug-only Cache viewer — the rest either don't exist in v2's menu layer in this codebase, or were never wired into a discoverable menu entry point.
- **Admin "spectate another player's menu"** exists in both and appears to be one of the few features carried forward largely unchanged (`v1:src/Users/User.java` `menuViewers`/`menuViewing` + `v1:src/Listeners/InventoryListener.java`; v2's `model/user/User.java` still carries equivalent `menuViewers`-related state per grep, not read in full depth here).
- **Item-blink/highlight utility** exists under the same class name in both trees (`v1:src/Menu/MenuItemBlink.java`, `v2:src/main/java/net/knightsandkings/menu/MenuItemBlink.java`) with a similar async-mutation shape; a byte-for-byte diff of the two was out of scope here (see Open questions).

## Open questions

1. **Most important**: which of the two v2 systems — if either — should inform judgment about "what v2 was trying to become" for comparison purposes: the sparse-but-live `model/menu` (`Menu2`/`ButtonGroup`/`ContentGroup` composition, battle-tested only for Kits/Sieges), or the more sophisticated but never-shipped `menu/`+`command/menu` rewrite (flexbox layout, `MenuDisplayed`/`MenuSession` split, async open pipeline)? These represent two different architectural bets made by the same developer in the same window, and only the project owner can say which direction they actually considered "right" versus which one merely happened to be live because it was older/simpler.
2. Given that a v3 `InventoryMenus` rebuild appears to have already merged, does this document need to answer any forward-looking questions at all, or should it be read purely as retrospective comparison against whatever v3 already decided?
3. Was the `%...%` variable-substitution bug (finding #7) known/worked around at the time (e.g. because the affected screens were rarely opened by players), or is this new information? It materially affects how "functionally complete" the `model/menu` screens should be considered.
4. v1's `Menu.java` covers far more subsystems (Sieges, Hide and Seek, Gates, Scenarios, Duels, Coupons, Tutorials, etc.) than were examined in depth here — this document intentionally focused on Houselist/Propertylist/Skill/GemShop/Personal-Menu as directed, illustrative examples rather than a full catalogue of all ~60 `open*` methods. If full parity with v1's menu surface area matters for comparison, a follow-up pass enumerating the rest would be needed.
5. Whether the "spectate another player's menu" admin feature (present, largely unchanged, in both versions) is something worth preserving as a concept given its complexity (mirrored inventories, click-cancellation) relative to its likely rare (staff-only) use.
