## Data model

### v1 (raw JDBC, no ORM)

- `` `v1:src/Sieges/SiegeObject.java` `` — base class for anything placed in the world for a siege: `scenarioID`, `spawnpointID`, `subID`, a `Spawnpoint` (from `SpawnPoints`/`DataManager`), and a derived `Location`. `remove()` branches on `instanceof SiegeSpawnpoint`/`instanceof SideObjective` to detach itself from its `Scenario`.

- `` `v1:src/Sieges/MainObjective.java` `` extends `Objective` — adds nothing but a constructor that hardcodes 500 points and `DyeColor.BLUE`.
- `` `v1:src/Sieges/SideObjective.java` `` extends `Objective` — `name`, `structureID`, an optional `Gate` (`Models.Structures.Gate`), `originalGateState`. Persisted via raw `PreparedStatement`s directly against a `SiegeObjectives` table (`saveGate`, `saveSideObjective`, `v1:src/Sieges/SideObjective.java:105-145`).
- `` `v1:src/Sieges/SiegeSpawnpoint.java` `` extends `SiegeObject` — `name`, `teamNumber`, `spawnCountID`, `active`, a particle-effect `circleTask`, `safeZoneRadius` (hardcoded 4).
- `` `v1:src/Sieges/Scenario.java` `` — the persisted "map": `ID`, `name`, `town`/`townName`, `entryTitle`, `playersMin`/`playersMax`, `expRewardWin`/`coinRewardWin`, `expRewardSideObjective`/`coinRewardSideObjective` (holding reward), `expRewardCapture`/`coinRewardCapture` (individual capture reward), `mainObjectiveID`/`mainObjective`, `sideObjectives` (`CopyOnWriteArrayList<SideObjective>`), `team1Color`/`team2Color`, `team1Spawnpoints`/`team2Spawnpoints`, `districts`, `editMode` (per-user in-place-edit state map), `testingList`, `nonPlayingGates` (gates inside the scenario area that aren't objectives, restored after a match), `active`, `siege` (back-reference to the live match), `votes`. Entirely persisted with raw `PreparedStatement`/`CallableStatement` (stored procedures `addSiegeScenario`, `addSpawnpointSiegeScenario`, `addSpawnpoint`) — no ORM.
- `` `v1:src/Sieges/Siege.java` `` extends `Minigames.MiniGame` — the live, in-memory match/session: `scenario`, `suggestedScenarioList` (2 candidates for the pre-match vote), `Team1`/`Team2` (`Minigames.SiegeTeam`), `WinningTeam`, `titleIDMin`/`titleIDMax`/`skilledMatch` (title-range gating for "skilled" matches), `isActive`, `randomVotes`. - `` `v1:src/Sieges/SiegeMember.java` `` extends `Minigames.Participant` — `spawnpoint` (helper), `currentSpawnpoint` (`SiegeSpawnpoint`), `teamNumber`, `capturedObjectives`.
- `` `v1:src/Sieges/TempSpawnpoint.java` ``/`` `v1:src/Sieges/TempSideObjective.java` `` — throwaway DTOs (name + `Location`, `TempSideObjective` adds a `structureID`) used only while a `ScenarioCreation` wizard is in progress, before anything is written to the DB.
- `` `v1:src/Minigames/MGTeam.java` `` — the generic, non-persisted team base: `Number`, `Name`, `Color`, `BannerColor`, `Scoreboard`, `Members` (`List<Participant>`), `winMessage`.
- `` `v1:src/Minigames/SiegeTeam.java` `` extends `MGTeam` — adds `siege` (back-reference), `spawnpoints`, `heldObjectives`, and scoreboard sidebar methods (`CreateSideBarBoard`/`UpdateSideBarBoard`/`ResetSideBarBoard`) that are hardcoded around exactly two teams. **This confirms the class the task description asked about**: `Minigames.SiegeTeam` is not a parallel/duplicate concept — it is genuinely `Sieges.Siege`'s real team class (imported directly, `v1:src/Sieges/Siege.java:20`), just organizationally placed in the shared `Minigames` package instead of inside `Sieges`.
- `` `v1:src/Minigames/Participant.java` `` — generic base for any minigame's player-in-a-match: `user`, `Team` (`MGTeam`), `beforeJoinLocation`, `storedInventory`. `SiegeMember` and `HideAndSeek`'s participant type both extend it, but each minigame otherwise reimplements its own logic; there's no generic `MGObjective`/`MGScenario` equivalent in v1.

## Business rules and behavior

### Match lifecycle (both versions follow the same shape; v2 is a fairly direct structural port of v1)

1. **Bootstrap.** v1: a singleton `Siege` is created automatically 2 seconds after `MiniGame`'s constructor runs, and the server's repeating task ensures exactly one `Siege` instance exists at all times (`Sieges.Sieges.Sieges.add(new Siege())` inside `Main.startvariousTasks()`, `` `v1:src/Main/Main.java:1007-1010` ``, itself invoked from a repeating `BukkitRunnable`). v2 has the same "create if none exists" pattern **written but commented out** in `KNK.java` (`` `v2:src/main/java/net/knightsandkings/KNK.java:292-306` ``) and referencing a stale `siegeFactory` API from before the Repository-pattern migration — so in v2 nothing auto-bootstraps a `Siege`; an admin must run `/siege new`, which hardcodes the name `"TestSiege"` and join command `"/siege join TestSiege"` (`` `v2:src/main/java/net/knightsandkings/spigot/command/minigame/siege/SiegeCommand.java:82` ``).
2. **Matchmaking.** `startMatchmaking(true)` picks up to 2 suggested scenarios (random draw from all persisted scenarios, `setRandomSuggestedScenarios`/`setRandomSuggestedSiegeScenarios`), opens joining (`canJoin`/`joinable = true`), and runs a per-second `BukkitRunnable` counting down `matchmakingSeconds` from `matchmakingExpire` (300s default in both versions). Fixed timestamp notifications fire at 290/60/30/15 seconds remaining (hardcoded map, `setMatchmakingNotifications`, identical between versions). At **30s** remaining, voting closes and a "teleporting to hub in 15s" warning is sent. At **25s**, `drawScenario()`/`drawSiegeScenario()` picks the winning scenario by vote count (ties broken by a 50/50 coin flip in v1, `v1:src/Sieges/Siege.java:333`; in v2 the suggested list is simply sorted by vote count and the top entry taken, `v2:.../Siege.java:369-373`) — in both versions, if `randomVotes.size()` exceeds the winning scenario's own vote count, a *fully random* scenario is drawn instead, discarding the vote. At **15s**, all joined players are teleported to the scenario's hub (`sendToHub`) and `inHub = true`. At **10s**, `setTeams()` shuffles participants and deals them alternately into exactly 2 buckets in v1 (`team1 = !team1` toggle, `v1:src/Sieges/Siege.java:452-485`) or into `N` buckets sized by `Math.ceil(members/teamAmount)` via a `Partition` utility in v2 (`v2:.../Siege.java:242-259`) — genuinely generalized to more than 2 teams, though `SiegeScenario` still only models a single `defenders`/`attackers` pair. At **0s**, matchmaking stops and `startProgress(true)` begins the match.
3. **Progress (the actual match).** Scenario/objectives/spawnpoints are activated (`scenario.setActive(true, siege)` — spawns banners, starts capture/particle tasks, opens town PvP flag in v2 via WorldGuard `Flags.PVP`). Players are spawned at their team's first spawnpoint. A per-second task ticks `progressSeconds` down from `progressExpire` (v1: fixed 900s; v2: `calculateProgressExpire()` scales with player count — `Math.ceil(members*1.25)` minutes, floored at 5 minutes, `v2:.../Siege.java:503-515` — a deliberate v2-only balancing change). At `progressExpire-2` an action-bar message is sent to each team (`startMSGDefense`/`startMSGAttack` in v1; per-team `getStartMessage()` in v2). At 0 seconds, v1 calls `stopSiege()` directly; v2 calls `setComplete()` (which itself eventually calls `stopSiege()`).
4. **Objective capture.** Every objective runs an independent 1-second `captureTask` (`Objective.startCaptureTask`/`MGObjective.startCaptureTask`) that calls `calculateCapturePoints()` and applies the delta to `currentCapturePoints` via `setCurrentCapturePoints`. `calculateCapturePoints()` scans every player within `captureRadius` (2.5 blocks default) who is alive, and buckets them by team: the **defending** side subtracts points (−6 for the first defender present, −3 for each additional one, doubled to −6 for the Main/instant-victory objective), the **attacking** side adds points (+5 for the first attacker, +2 for each additional, doubled to +5/+6 for the Main/instant-victory objective) — identical formula and identical author-acknowledged uncertainty ("Right now it is probably not working correctly", `v1:src/Sieges/Objective.java:139-140`, carried verbatim into `v2:.../MGObjective.java:713-714` and `v2:.../SiegeObjective.java:544-545`) in both versions. `setCurrentCapturePoints` clamps to `[0, original]`, advances the banner-pattern gradient (`Math.ceil((current/original)*8)`), and calls `setCaptured(true)` once points hit 0. Capturing an objective picks the **closest** eligible player as `capturer` (`calculateCapturer`), announces it to both teams, and (if a gate is attached) destroys the gate.
5. **Win condition.** v1: capturing the `MainObjective` is the *only* win condition — `Scenario.setObjectiveCaptured()` calls `setComplete()` specifically when `objective == mainObjective` (`v1:src/Sieges/Scenario.java:663-665`); capturing a `SideObjective` only nudges the Main Objective's `currentCapturePoints` down by a fraction (`v1:src/Sieges/Scenario.java:668-681`) — side objectives make the main objective easier, they never win the game by themselves. v2 generalizes this: any `SiegeObjective` can be flagged `instantVictory`, and capturing *any* instant-victory objective ends the match immediately (`SiegeScenario.setObjectiveCaptured`, `v2:.../SiegeScenario.java:406-408`); non-instant-victory captures instead nudge every instant-victory objective's points down by a shared fraction (`v2:.../SiegeScenario.java:409-419` — same "reduce main objective by a computed part" idea as v1, just pluralized). If the timer runs out with no instant-victory objective captured, the **defenders win by default** in both versions (v1: `WinningTeam = Team1` unless `mainObjective.getCaptured()`, `v1:src/Sieges/Siege.java:687-696`; v2: `winners = scenario.getTeam("cinixians")` unless an instant-victory objective was captured, `v2:.../Siege.java:844-858` — see Known edge cases for why the v2 default-winner lookup is broken).
6. **Rewards and cleanup.** Both versions send a per-player reward breakdown (win bonus, per-held-objective bonus, per-individually-captured-objective bonus) and grant coins/experience, then call `stopSiege()` → teleport everyone back, clear teams/scenario, and `startCooldown(true)` (900s default in both) which loops back into `startMatchmaking(true)` once it expires — a fully self-sustaining cycle in v1 (once the initial singleton exists) and, in principle, in v2 too (once a `Siege` has been manually created via `/siege new`).

### Joining

- v1: the advertised `/siege join` command is an explicit stub — `` `v1:src/Sieges/SiegeCommands.java:59` ``: `sender.sendMessage(ColorOptions.error + "Command not configured yet.");`. The **actual, working** join path is menu-driven: `Menu > Events > Siege overview > click a siege` → `EventsClick.onSiegeOverviewClick` → `siege.joinPlayer(user)` (`` `v1:src/Menu/EventsClick.java:87` ``). `/siege leave` and `/siege skip` (donator-gated) are implemented as real commands.
- v2: `/siege join <siege>` (`SiegeCommand.onJoin`) and `/siege leave <siege>` are real, implemented commands that also open the `InformationOverview` menu; joining is additionally available through the equivalent menu click (`SiegeSelectItem.onClick` → opens `InformationOverview`, joining itself happens via the `SiegeCommand`-backed menu action). This is one concrete respect in which v2 is *more* finished than v1.

### Scenario/map creation flow

- v1 (`` `v1:src/Sieges/ScenarioCreation.java` ``, extends the shared `Models.creations.Creation` base): a 13-stage interactive **chat wizard** reached via `/scenario create` (`` `v1:src/Sieges/ScenarioCommands.java:83-84` ``). Stages in order: name → min players → max players → Team 1 (Defenders) spawnpoints (stand + type a name or `save`, up to 9) → Team 2 (Attackers) spawnpoints (up to 9) → Main Objective location (stand + `save`, or right-click a banner) → Side Objectives (right-click a gate/property to auto-attach it, or stand + type a name for a plain location, up to 9) → win-reward exp → win-reward coins → holding-reward exp per side objective → holding-reward coins → capture-reward exp (individual) → capture-reward coins (individual) → a final `confirm` step that shows a summary and persists everything through stored procedures (`Scenarios.CreateScenario`, using `CALL addSpawnpoint`, `CALL addSiegeScenario`, `CALL addSpawnpointSiegeScenario` per spawnpoint/objective). The wizard is dispatched not by the Sieges-package's own `ScenarioCreationEvents` listener (which is 100% dead, see below) but by the **shared, generic** `Creation` framework: any player chat/command/interact event is routed through `Creations.FindCreation(user)` → `creation.processEvent(event)` from the global `Listeners.PlayerListener` (`` `v1:src/Listeners/PlayerListener.java:586-589,974-978,1352-1356` ``), which `ScenarioCreation` overrides to implement all of the above.
- v2 has no equivalent from-scratch creation wizard for `SiegeScenario`/`SiegeObjective`/`SiegeTeam`. Each has only `list`/`fetch`/`save`/`remove`/`edit` subcommands (`` `v2:src/main/java/net/knightsandkings/spigot/command/minigame/siege/SiegeScenarioCommand.java` ``, `SiegeObjectiveCommand.java`, and — checked for parity — `SiegeTeamCommand.java` has the same five, no `new`). `edit` starts the generic `Creation` stage framework (`getCreationStages()`/`createInstance()`, e.g. `` `v2:.../SiegeScenario.java:474-578` ``) against an **already-persisted** object — there is no command anywhere that instantiates a brand-new, empty `SiegeScenario`/`SiegeObjective`/`SiegeTeam` and hands it to the creation flow the way v1's `/scenario create` does. `Siege` itself does have `/siege new`, but it only ever creates a hardcoded `"TestSiege"` placeholder instance rather than walking an admin through building a real one.

## Known edge cases / bugs

- **v1: `/siege join` command is an unimplemented stub** (`` `v1:src/Sieges/SiegeCommands.java:59` ``, literally `"Command not configured yet."`). Clearly a bug/incomplete — the only working join path is the menu. Tag: **clearly a bug**.
- **v1: multi-player capture/defend scaling is author-flagged as probably wrong.** `Objective.calculateCapturePoints()` has an inline comment: "TODO: Find out if we want a linear or exponential growth... Right now it is probably not working correctly" (`` `v1:src/Sieges/Objective.java:139-140` ``). Tag: **likely a bug** (author-acknowledged).
- **v1: inconsistent persistence table names across the Sieges package.** `Scenario.fetchSideObjectives()` reads from a `SpawnpointSiegeScenario` table joined with `Spawnpoint` (`` `v1:src/Sieges/Scenario.java:304-322` ``); `SideObjective.saveSideObjective()`/`saveGate()` write to a `SiegeObjectives` table (`` `v1:src/Sieges/SideObjective.java:109,132` ``); `Scenarios.RemoveScenario()` deletes from `SiegeScenario` (`` `v1:src/Sieges/Scenarios.java:493` ``); but `Scenario.removePermanently()` deletes from a table named `Sieges` (`` `v1:src/Sieges/Scenario.java:938` ``). These can't all be the live schema's actual names for the same concepts. Tag: **likely a bug** (can't fully confirm without the DB schema itself, but the inconsistency is real and load-bearing).
- **v1: `SiegeEvents` and `ScenarioCreationEvents` are registered Bukkit listeners with zero active `@EventHandler` methods** — every handler in both files is commented out (`` `v1:src/Sieges/SiegeEvents.java` ``, `` `v1:src/Sieges/ScenarioCreationEvents.java` ``), yet both are still registered in `Main.java` (`` `v1:src/Main/Main.java:744-745` ``). Harmless (the real event dispatch happens through the shared `Creation`/`PlayerListener` framework instead), but dead weight that was never cleaned up. Tag: **might be intentional, unclear** (moved elsewhere but not removed).
- **v2: capture/defend scoring is hardcoded to a single literal team name.** Both `MGObjective.calculateCapturePoints()` (`` `v2:.../MGObjective.java:695` ``) and its near-duplicate override `SiegeObjective.calculateCapturePoints()` (`` `v2:.../SiegeObjective.java:526` ``) branch on `teamName.equalsIgnoreCase("cinixians")` to decide who is "defending" instead of comparing against `scenario.getDefenders()`, which exists on the very same `SiegeScenario` class. Any scenario whose defending team isn't literally named "Cinixians" will score captures backwards. Tag: **clearly a bug**.
- **v2: default (timeout) win resolution is hardcoded the same way.** `Siege.setComplete()` sets `winners = scenario.getTeam("cinixians")` as the default before checking for an instant-victory capture (`` `v2:.../Siege.java:844` ``), instead of `scenario.getDefenders()`. Same root cause as above. Tag: **clearly a bug**.
- **v2: `SiegeObjective.getGateName()` has inverted null-check logic.** `` `v2:.../SiegeObjective.java:208-214` ``: `if (this.gate != null) { return "No gate"; } else { return this.gate.getName(); }` — reports "No gate" when a gate *is* attached, and throws a `NullPointerException` calling `.getName()` on `null` when no gate is attached. Tag: **clearly a bug**.
- **v2: `SiegeObjective.gate` is a required (`optional = false`) foreign key**, yet the objective's own creation stages and constructor explicitly support a gate-less, location-only objective (`` `v2:.../SiegeObjective.java:85-88,130-142,574-609` ``). A location-only `SiegeObjective` would violate its own `@ManyToOne(optional = false)` constraint. Tag: **likely a bug** (schema/code contradiction).
- **v2: `/siege remove` unconditionally throws after doing its work.** `SiegeCommand.onRemove` stops and removes the siege in a try/catch, then unconditionally executes `throw new Exception("This method does not contain any functionality to properly stop and remove a Siege. Please notify a Developer");` (`` `v2:.../SiegeCommand.java:117` ``) regardless of whether the preceding steps succeeded. Tag: **clearly a bug** (or at minimum a loud, never-followed-up unfinished-marker).
- **v2: several commands are unconditional stubs.** `SiegeCommand.onEdit` (`` `v2:.../SiegeCommand.java:134` ``) and the generic `MiniGameCommand.onNew` (`` `v2:.../MiniGameCommand.java:85` ``, whose description string — "Adds a new Siege object to the Cache" — is a copy-paste leftover from `SiegeCommand`) both unconditionally `throw new UnsupportedOperationException("This command has not been configured yet.")`. Tag: **clearly incomplete, not a bug per se**.
- **v2: no in-game path exists to create a brand-new `SiegeScenario`/`SiegeObjective`/`SiegeTeam`.** Only `list`/`fetch`/`save`/`remove`/`edit` subcommands exist for each; `edit` requires the object to already exist in the repository. Tag: **clearly incomplete**.
- **v2: two non-interoperating `SiegeOverview` menu classes coexist.** `` `v2:src/main/java/net/knightsandkings/menu/preset/menu/siege/SiegeOverview.java` `` (newer `MenuItem`/`DisplayableListFormattedMenuSection`/`VariableString`-based framework) and `` `v2:src/main/java/net/knightsandkings/model/menu/siege/SiegeOverview.java` `` (older classic-`Inventory`-based framework). ## Finished vs work-in-progress

### v1

The core match loop — matchmaking → vote → team split → hub teleport → progress countdown → per-tick capture scoring → win resolution → reward payout → cooldown → repeat — is fully implemented, internally consistent, and reachable from server startup: `Main.startvariousTasks()` guarantees exactly one live `Siege` singleton exists at all times (`` `v1:src/Main/Main.java:1007-1010` ``), so the match cycle is genuinely self-sustaining without any admin action. The scenario/map creation wizard (`ScenarioCreation`, 13 stages) is a complete, working, DB-persisted flow reachable through `/scenario create`, and is dispatched through the shared `Creation` framework (confirmed live via `Listeners.PlayerListener`, not dead). The one clearly broken piece of *player-facing* surface area is the `/siege join` command stub — joining only works through the menu. `SiegeEvents`/`ScenarioCreationEvents` are dead classes, but harmlessly so, since their job is done elsewhere. Judged by code shape (no stub methods in the core loop, no unresolved TODOs beyond the one scoring-math caveat, every class reachable from a real command or listener except the two empty listener classes): **this is a finished, playable minigame.**

### v2

The data model and generic `MiniGame`/`MG*` base-plus-`Siege*`-specialization architecture is clearly the most heavily invested-in part of either codebase — real Hibernate entities, a repository/cache abstraction, N-team alliance support, per-objective instant-victory flags, richer gate-state snapshotting, and cross-cutting kill/death stat tracking. The match loop in `Siege.java` structurally mirrors v1's closely and is wired to real commands (`/siege join`, `/siege leave`, `/siege skip`). However, several load-bearing pieces are broken or missing in ways that go beyond cosmetic TODOs:

- The capture-scoring and default-win-resolution logic is hardcoded to a single literal team name ("cinixians") instead of using the `defenders`/`attackers` fields that exist on the very same `SiegeScenario` class — so, unless every scenario's defending team happens to be named exactly "Cinixians", the core game-resolution logic is wrong. This is present in the code reachable from `main`, not tucked away on an abandoned branch.
- There is no command-driven way to create a new `SiegeScenario`, `SiegeObjective`, or `SiegeTeam` from scratch — a load-bearing capability v1 had fully working.
- `/siege remove` and `/siege edit`, and the generic `/minigame new`, are explicit stubs/always-throw.
- Nothing auto-bootstraps a `Siege` instance at server startup — that logic exists but is commented out and references a stale pre-Repository-pattern API (`` `v2:src/main/java/net/knightsandkings/KNK.java:292-306` ``); `/siege new` must be run manually and only ever creates a hardcoded `"TestSiege"` placeholder.
- The `menu.preset.menu.siege.SiegeOverview` rewrite is unreachable dead code. Git history confirms this is a stalled effort, not merely an unused alternative: its only commit is `514367d "Begun adding Siege overview menu"` (2022-11-14), and it was never touched again. For context, the last commit touching any siege model file on `main` is `2022-12-21`, and the last commit on `main` at all is `2022-12-22` — so this abandoned menu rewrite was one of the very last things worked on before the project went dormant, left mid-migration.
- Per the task's git-history heuristic for "reachable only from an unmerged branch": this does **not** apply to the Siege system. `git log --oneline main -- src/main/java/net/knightsandkings/model/minigame/siege/` and `git log --all --oneline` for the same path return an identical commit list, and the same holds for `spigot/command/minigame/siege/` and `model/menu/siege/`. Every siege-related file that exists is already merged into `main` (checking `ImprovedMenus`, `CreationArchitecture2`, and the other long-lived feature branches specifically turned up nothing siege-related beyond what's already on `main`). The WIP-ness here isn't "stuck on a branch" — it's "merged to main in a half-finished, under-tested state."

Judged by code shape and reachability: **v2's Siege system is architecturally the more sophisticated of the two, but is not currently a correctly-functioning, fully playable minigame** — it is closer to "generalized skeleton with one hardcoded-team-name test case still wired in" than to a finished feature.

## v1 vs v2 differences

**Concrete architecture upgrades in v2:**
- A genuine generic `MiniGame`/`MGMember`/`MGObjective`/`MGScenario`/`MGSpawnpoint`/`MGTeam` base layer that `Siege`/`SiegeMember`/`SiegeObjective`/`SiegeScenario`/`SiegeSpawnpoint`/`SiegeTeam` actually extend (real inheritance). v1 had no equivalent generic *data* model — only a thin, non-persisted `Minigames.MiniGame`/`Participant`/`MGTeam` runtime layer that `HideAndSeek` (a separate, non-inheriting sibling) and `Sieges.Siege` each built on top of independently.
- Hibernate/JPA entities (`@Entity`, `@ManyToOne`, `@ManyToMany`, `@OneToOne`) plus a `RepositoryManager` cache abstraction, replacing v1's raw `PreparedStatement`/`CallableStatement` calls scattered through `Scenario.java`, `SideObjective.java`, and `Scenarios.java`.
- N-team/alliance support (`SiegeTeam.allies`/`enemies`) vs v1's hardcoded exactly-two-teams model (`Siege.Team1`/`Team2`, `GetOppositeTeam()`).
- Per-objective `instantVictory` flag generalizing v1's implicit "only the Main Objective ends the game" rule to "any number of designated objectives can end the game."
- Fuller gate-state snapshot/restore (`gateOpenedOriginal`/`gateActiveOriginal`/`gateHealthOriginal`) vs v1's single `originalGateState` boolean.
- Kill/death/killstreak stats wired into the shared `User.getStatistics()` system — absent in v1.
- A generic `Creation`-stage framework (`getCreationStages()`/`createInstance()`) reused by Scenario/Objective/Team "edit" — vs v1's one-off, hand-rolled 13-stage chat wizard that only `ScenarioCreation` uses.
- Match-length that scales with player count (`calculateProgressExpire`) instead of v1's fixed 900 seconds.
- A working `/siege join`/`/siege leave` command pair, vs v1's stubbed `/siege join`.

**Concrete functionality v1 has that v2 dropped or never finished:**
- A complete, working, DB-persisted scenario-creation wizard reachable via a real command (`/scenario create`) — v2 has no "new" subcommand for `SiegeScenario`/`SiegeObjective`/`SiegeTeam` at all, only "edit" of an object that must already exist.
- Automatic server-startup bootstrap of a live `Siege` instance — present and working in v1; present in v2's source but commented out and stale.
- Capture/defend scoring and default win resolution that work for **any** pair of teams — v2's equivalent logic is hardcoded to one literal team name and would misbehave for any other matchup.

**On the project owner's "v2 has better architecture but v1 has more finished functionality" claim:** this system is strong supporting evidence, and the evidence is fairly unambiguous rather than mixed. The architecture comparison is clear-cut in v2's favor (generic base classes, ORM, N-team model, richer win-condition modeling). But the *finished functionality* comparison also comes out clearly in v1's favor on the two things that matter most for actually running a siege: (1) v1 can create new siege content and run indefinitely without admin intervention; v2 can do neither out of the box, and (2) v1's core scoring/win logic is correct for whatever two teams are assigned; v2's is silently wrong unless the defending team happens to be named "Cinixians". The one place v2 is unambiguously *more* finished than v1 is the `/siege join`/`/siege leave` commands themselves (v1 stubs `/siege join`; v2 implements it) — a genuine but narrow exception to the overall pattern.
