# User system (users, roles, ranks, levels, permissions)

Mined from `v1` (single-commit Bukkit import, no ORM) and `v2` (Hibernate/JPA + cache, 196 commits on `main`, more across feature branches). See `docs/specs/legacy/README.md` for citation conventions. All fields/behavior below are read directly from source; nothing is inferred beyond what a cited method body shows.

Methodology note on v2: the clone's working tree was on `main` at HEAD `400e5c8` ("Patch for constructorParam bug for MenuConstructionCommand", 2022-12-22) at the time of this research, not `2025/01/Hibernate-update` as pre-recon expected — history for specific paths was cross-checked with `git log --all` / `git show <branch>:<path>` regardless of which branch was checked out, so this doesn't affect the findings below.

## Data model

### v1 — no ORM, raw JDBC against MySQL, one fat `User` object

- `v1:src/Users/User.java` — a plain Java object (no annotations) representing one player. Constructed as `User(UUID uuid)`, which calls `existUser(uuid)` (`SELECT * FROM Player WHERE UUID=?`) then `fetchUser(uuid)` then `setData(uuid, data)` to populate ~80 fields from a single `Player` table row via a `ResultSet`. Identity/rank/permission-relevant fields (types as declared):
  - `id:int`, `uuid:UUID`, `username:String`, `joinDate:Date`, `address:InetAddress` (duplicate-IP detection), `banned:boolean`.
  - `level:int` — loaded from column `Level` and saved back, but has **no setter anywhere** and **zero callers of `getLevel()`** in the whole v1 tree outside unrelated `Skills`/`Structures`/`Property` classes that happen to share the method name (`v1:src/Users/User.java:151,303,413,1217`). Effectively a dead/orphaned column (see Known edge cases).
  - `titleID:int`, `titleName:String` (progression rank, see below), `expierienceNext:int` [sic, misspelled in source], `experience:int`.
  - `donatorID:int`, `donatorName:String` (purchased rank), `previousDonatorID:int`, `previousDonatorName:String` (restore target after a temporary donator rank expires).
  - `salary:int` — cached copy of `Title.getSalary(titleID)`, set **only** inside `setData()` (`v1:src/Users/User.java:336`); not refreshed when `titleID` changes mid-session (see Known edge cases).
  - `coins:int`, `gems:int`, `income:int`/`incomeTime:Long`, `salaryTime:Long`, `rentTime:Long`.
  - `ownermode`/`staffmode` and their `...DisableonQuit`/`...EnableonQuit` booleans — declared on `User` but the actual enabled/disabled state is tracked separately in static maps on `Main`/`OwnerCommands`, not persisted to the DB (see Business rules).
  - Plus ~50 more economy/combat/skill fields (`blocksBroken*`, `kills`, `skillPoints`, `houseAmount`, etc.) not detailed here as out of scope for the user/rank/permission system.
  - Persistence: `getSaveQuery()` builds a single `UPDATE Player SET ... WHERE UUID=... AND Username=...` by **string concatenation**, not a `PreparedStatement` with bound parameters — a large block of the equivalent parameterized version is left commented out directly below it (`v1:src/Users/User.java:373-568`). `saveUser()` runs this async via `BukkitRunnable.runTaskAsynchronously`.
- `v1:src/Titles/Title.java` — stateless helper, no fields; every method issues its own `SELECT * FROM Titles WHERE ID=?` (or similar) against a `Titles` table with implied columns `ID, MaleName, FemaleName, Salary, CoinBonus, GemBonus, ExpBonus, MinExp, MaxExp`.
- `v1:src/Donator/Donator.java` — likewise stateless; backs a `Donator` table with implied columns `ID, Name, Multiplier, PrimaryColor, SecondColor, Price`. Rank name→ID mapping is hardcoded in `getDonatorIDbyString`: `"noble"→1, "royal"→2, "dragon blood"/"dragonblood"→3, "default"→0` (`v1:src/Donator/Donator.java:187-202`).
- `DonatorTemp` table (SQL only, no Java model class) — implied columns `UserID, DonatorID, TimeStart, TimeEnd, PreviousRankID`, backing temporary/expiring donator ranks (`v1:src/Users/User.java:2581-2652`).
- `v1:src/Users/offlineUser.java` (4,174 lines) — a large **parallel** implementation of nearly all of `User`'s read/write logic, but UUID-parameterized (`getTitleID(UUID)`, `setDonatorRank(UUID, Integer)`, `SalaryPayout(UUID)`, etc.) instead of instance-based, so staff commands can act on offline players without constructing a live `User`. This duplicates the title/donator/salary/experience business rules independently of `User.java` (see Finished vs WIP).
- `v1:src/Users/UserProfile.java` — a 14-line interface declaring `experience`, `titleID`, `coins`, `gems`, `salary`, `income`, `houseAmount`, `propertyAmount`, `roomeAmount` [sic] all as `Integer = null`. No implementers found anywhere in the tree — dead scaffold.
- Permissions: **not** a KnK-owned entity. Plain Bukkit permission-node strings of the form `k&k.<feature>[.<subaction>]`, checked via `sender.hasPermission(...)` / `player.hasPermission(...)`, presumably granted by an external permissions plugin — confirmed by direct `Bukkit.dispatchCommand(sender, "pex group ...")` / `"pex user ... group add ..."` calls (PermissionsEx) in `v1:src/UsefulCommands/RankCommands.java` and `v1:src/Users/UserCommands.java`. Full inventory of `k&k.*` nodes found by grep across `v1/src`: `arena, co-owner, coins, donator, enchant, enderchest(.others), experience, fly, gamemode(.others), gate(.info/.passthrough/.toggle), gems, ghosted, heal, hideandseek, home, house, initiate, join.nolocation, kills, lore, menu, owner, product, property, propertycategory, ranks(.co-owner/.modify/.owner/.staff), reload, rename, repair, resourceproperty, room, rooms, shopkeeper, soulbound, spawn(.others), spawnpoint, specialskill, staff, street, teleport.normal/.owner/.staff, test, town, treasure, tutorial.others, weather`.

### v2 — Hibernate/JPA entities behind a cache+DAO repository layer

- `v2:src/main/java/net/knightsandkings/model/user/User.java` (`@Entity @Table(name="user")`) — the live, actively-developed entity. `uuid:UUID` (`@Id`), `created:Date`, `name:String`, `hostAddress:String`, `inetAddress:InetAddress` (`@Transient`), `cash:int` (default 100), `stashedItems:List<Item>` (`@ManyToMany`, join table `user_items_stashed`), `statistics:UserStatistics` (`@OneToOne(cascade=ALL, mappedBy="user")`), plus `@Transient` runtime state: `player`, `loginEvent`, `newUser`, `menu`, `previousMenu`, `menuViewers`, `menuViewing`. Implements `IPersistent<UUID>`, `IDisplayable<UUID>`.
- `v2:src/main/java/net/knightsandkings/model/user/KnKUser.java` (`@Entity @Table(name="users")`) — an **earlier, abandoned draft** of the same concept: `uuid`, `created`, `username`, `inetAddress`, `cash`, `gems:int`, `experience:int`. Confirmed dead (see Finished vs WIP): last functionally touched in the "Initial setup of Hibernate" commit, its only live reference anywhere is a single `KnKUser.cache.clear()` call in `KNK.onDisable()`, immediately below a commented-out per-object save loop (`v2:src/main/java/net/knightsandkings/KNK.java:340-342,378`). It is **not** a wrapper or subclass of `User` — it's an independent, superseded entity.
- `v2:src/main/java/net/knightsandkings/model/user/UserLogin.java` (`@Entity`) — per-session record: `id:int` (`@Id @GeneratedValue(IDENTITY)`), `user:User` (`@OneToOne(cascade=ALL)`, join column `user_id`), `loginDate:Date`, `logoutDate:Date`, `totalPlayTime:long` (computed in `logout()` as `logoutDate - loginDate`), `hostAddress:String`.
- `v2:src/main/java/net/knightsandkings/model/user/UserLoginError.java` (`@Entity`) — login-failure tracker: `id:int`, `uuid:UUID` (`@Column`, oddly annotated `@Convert(converter = WGRegionConverter.class)` — a WorldGuard-region converter applied to a plain user UUID column, almost certainly copy-paste residue, `v2:...UserLoginError.java:39-41`), `errorDate:Date`, `loginAttempts:int` (default 0), `stackTraceString:String` (`MEDIUMTEXT`), `exceptionMessage:String`. `MAX_LOGIN_ATTEMPTS = 3` (static constant).
- `v2:src/main/java/net/knightsandkings/model/user/UserStatistics.java` (`@Entity @Table(name="user_statistics")`, `@Inheritance(TABLE_PER_CLASS)`) — lifetime stat totals: `id:UUID` (`@Id`, `@MapsId` to `user`), `user:User` (`@OneToOne`), `dailyStatistics:UserStatisticsDaily` (`@Transient` — its `@OneToOne`/`@JoinColumn` mapping is commented out directly above the field, `v2:...UserStatistics.java:67-70`, see Known edge cases), and 20 `int`/`double` counters defaulted to 0: `logins, cashEarned, cashSpent, kills, minigameKills, siegeKills, deaths, minigameDeaths, siegeDeaths, minigameWins, siegeWins, minigameLosses, siegeLosses, objectivesCaptured, gateDamage, arrowsFired, headshots, damageDealt, damageReceived, distanceTraveled, highestFall, highestKillstreak`.
- `v2:src/main/java/net/knightsandkings/model/user/UserStatisticsDaily.java` (`@Entity @Table(name="user_statistics_daily")`, extends `UserStatistics`) — adds `date:Date`; overrides every `add*/remove*` mutator to apply only to itself (no further propagation); `isValid()` compares its `date` to "today" via `LocalDate` — used on login to decide whether to keep or replace the cached daily record.
- Persistence pattern: `UserRepository extends Repository<User, UUID>` (`v2:...dal/repository/UserRepository.java`) reads from `UserCache` first and falls back to `UserDAO` (Hibernate `EntityManager`, one per call) on a cache miss, populating the cache with the result — no raw JDBC anywhere in v2.
- Permissions: same `k&k.<feature>` string convention as v1, but expressed two ways: (1) one top-level permission per Bukkit command in `v2:src/main/resources/plugin.yml` (e.g. `user: permission: k&k.user`, `enderchest: permission: k&k.enderchest`, `stashedcreation: permission: k&k.creation.stashed`, and 20+ more — no `k&k.donator`, `k&k.ranks`, `k&k.title`, or `k&k.experience` entries anywhere), and (2) fine-grained ACF `@CommandPermission("k&k.user.list")`-style annotations at the (sub)command-method level inside `spigot/command/**` classes (e.g. `k&k.user`, `k&k.user.list`, `k&k.user.fetch`, `k&k.user.save`, `k&k.user.statistics` in `UserCommand.java`; `k&k.enderchest`, `k&k.enderchest.open`, `k&k.enderchest.check` in `Enderchest.java`). No `permissions:` defaults block exists in `plugin.yml`, so grants are entirely external (a permissions plugin, unnamed in source). v1's in-plugin PermissionsEx group-management commands (`/user staff|owner|...`) have no v2 equivalent at all.

## Business rules and behavior

### v1

- **Two independent "rank" tracks.** (1) **Title** — an in-game progression rank driven purely by `experience`, looked up via `Titles.MinExp <= exp <= MaxExp` (`Title.getTitleIDbyExp`); clamped to the range 0–18 by `User.setTitle` (`if (titleID > 18) titleID = 18;`, `v1:src/Users/User.java:1696-1703`). (2) **Donator** — a purchased/granted rank (`default`/`noble`/`royal`/`dragon blood`), entirely independent of experience, changed only via admin/purchase flow (`Users.setDonator`), which can be permanent or temporary (`Donator`/`DonatorTemp`, `previousDonatorID` used to restore the prior rank when a temporary one expires, `v1:src/Users/User.java:2581-2652`).
- **Promotion/demotion pipeline.** `ExperienceChangeEvents` compares the title bracket implied by the new experience total against the current `titleID`; if different, fires `TitleChangeEvent(user, old, new, promoting?)` (`v1:src/Experience/ExperienceChangeEvents.java:26-49`). `TitleChangeEvents.onChange` applies a **single**-level change immediately via `userPromotion`/`userDemotion`; a **multi-level** jump (`change >= 2`) is *not* applied all at once — it's queued in `Main.titleChangeList<UUID,Integer>` and drained one level per tick-loop iteration (`runTaskTimer(main, 0, 2*20)` — every 2 seconds) via `setPromoteLoop`/`setDemoteLoop` (`v1:src/Titles/TitleChangeEvents.java:35-68,295-343`). A player who jumps several titles via `/exp add` will visibly promote one title every 2 seconds.
- **Promotion rewards / demotion penalties**, both hardcoded at the same thresholds: 1 skill point per title level gained/lost always; plus, at titleID crossing **5**: +1 house slot, +1 property slot; at **10**: +1 house, +1 property, +1 special-skill point; at **12**: +1 quest slot; at **15**: +1 house, +1 property, +1 keep slot, +1 assignment slot (`v1:src/Titles/TitleChangeEvents.java:121-293`, magic numbers 5/10/12/15 repeated in both directions). Demotion additionally removes a banked skill point if any exist, else randomly removes one level from a random skill the user has invested in (shuffling the skill list if the first random pick has nothing to remove) — a fairly elaborate fallback chain (`v1:src/Titles/TitleChangeEvents.java:248-273`).
- **Salary.** Paid hourly, per online user, via a scheduled comparison `current > user.getSalaryTime()` in `Main.java` that fires a `SalaryPayoutEvent`; the actual payout listener recomputes the amount fresh as `title.getSalary(titleID)` multiplied by the donator multiplier and a global event multiplier (`User.getMultipliedInt`, `v1:src/Currency/SalaryPayout.java:27-54`). `saveSalaryTime()` schedules the next payout exactly `3,600,000` ms (1 hour) later; the separate passive "Income" payout uses `43,200,000` ms (12 hours) (`v1:src/Users/User.java:1535-1547`).
- **Assignment cap bug-prone formula.** `refreshAssignmentMaximum()`: base is a field-initialized `3`; if `titleID >= 15`, increment by 1; then **unconditionally** `this.AssignmentDailyAmount = this.AssignmentDailyAmount + this.donatorID` — with no reset to a base value first (`v1:src/Users/User.java:628-635`). See Known edge cases.
- **Quest cap.** `refreshQuestMaximum()`: base `2`, becomes `3` once `titleID >= 12` (recomputed, not incremented, so it's idempotent across repeat calls) (`v1:src/Users/User.java:620-626`).
- **Owner/staff mode.** `/ownermode`, `/staffmode` toggle a vanish-like state gated by `k&k.owner`/`k&k.co-owner` and `k&k.staff` respectively (`v1:src/Users/OwnerCommands.java`); enabling hides the player from anyone lacking `k&k.staff` (`target.hidePlayer(player)`) and shows an action-bar message. State lives in static maps on `Main` (`ownermodus`/`staffmodus`) and `OwnerCommands` (`enableonquit`/`disableonquit`), **not** on the persisted `User` row.
- **In-game group/rank management.** `/user default|staff|builder|co-owner|owner|save|remove <player|all>` (gated by `k&k.ranks`, with `k&k.ranks.co-owner`/`k&k.ranks.owner` for the top two tiers) directly issues console-dispatched PermissionsEx `pex user <name> group remove/add <group>` commands to move a player between mutually exclusive server groups — a **third**, separate rank concept from Title and Donator (`v1:src/Users/UserCommands.java`). `/default` is a narrower duplicate of just the "reset to default group" part, gated by `k&k.ranks.modify` (`v1:src/UsefulCommands/RankCommands.java`).
- **The actual, wired-up join flow** lives in `v1:src/Listeners/PlayerListener.java` (`OnLogin`/`OnJoin`, registered at `v1:src/Main/Main.java:677`), which creates the DB row for first-time joiners, calls `user.join(player)` (which itself kicks off `Users.CheckScheduledRank`/`CheckScheduledItems` and duplicate-IP detection), and prints a stats block including `Title`, `Salary`, coins/gems. `Users.JoinEvents` (registered separately, `v1:src/Main/Main.java:766`) is **not** this flow — see Finished vs WIP.
- **`CheckScheduledRank`** (`v1:src/Users/Users.java:477-490`): 5 seconds after join, if the joining player's UUID is a key in `Main.scheduledDonator`, applies that donator rank. This map is populated by `Users.setDonator` when an admin sets a donator rank for a currently-offline player (`v1:src/Users/Users.java:150-203`) — see Known edge cases for its persistence gap.

### v2

- **Login/join flow.** `PlayerListener.onLogin` (`PlayerLoginEvent`, async) fetches-or-creates the `User` row (cache → DAO), then calls `user.login(player, address)`, which starts a `UserLogin` session, adds **1** flat cash (`this.addCash(1)`, a magic-number per-login reward, `v2:...User.java:503-522`), lazily creates `UserStatistics` if absent, and replaces the cached `UserStatisticsDaily` with a fresh one only if it's not from today (`isValid()`), otherwise reuses it and logs it. `PlayerListener.onJoin` (`PlayerJoinEvent`, sync) re-fetches the cached `User`; if unexpectedly `null` (the async login step hasn't finished or failed), it builds/reuses a `UserLoginError` capped at `MAX_LOGIN_ATTEMPTS = 3` and kicks the player, annotated with its own TODO about eventually redirecting repeat-failures to an "error lobby" (`v2:src/main/java/net/knightsandkings/listeners/PlayerListener.java:66-121`) — this whole branch is explicitly unfinished.
- On successful join: welcome message differs by `user.isNewUser()`, reports current cash; if the player lacks `k&k.join.owner`, they're forced to survival, un-flown, and teleported to `RepositoryManager...getRepository(Town.class,...).getList().get(0)` — i.e. **whatever town happens to be first** in an unordered list — or world spawn if no town exists at all (`v2:...PlayerListener.java:122-140`).
- **Statistics are wired into real gameplay**, not just self-referential: `UserStatistics`'s `add*` mutators are called from `EntityListener` (headshots, damage dealt/received, highest fall), `PlayerListener` (kills, deaths, distance traveled), `ProjectileListener` (arrows fired), `MGMember` (minigame/siege kills, deaths, killstreak), and `Siege` (cash earned from siege rewards). Every lifetime mutator also calls the matching daily mutator via `getDailyStatistics()`, which lazily creates one if missing.
- **No rank/title/level/experience progression system exists in v2.** The only traces anywhere in `src/main` are: a `TODO Make an interface for purchasable items with basePrice, requiredTitle, requiredRank etc.` that was never implemented (`v2:src/main/java/net/knightsandkings/model/item/Item.java:133`); an orphaned `MenuUtil.DonatorMenu = "...Donator-ranks' information"` string with no menu behind it and no other references anywhere (`v2:src/main/java/net/knightsandkings/util/MenuUtil.java:26`); and a block of dead, copy-pasted code in `ColorOptions.java` (structurally identical to v1's file, down to the same numbered section comments, including `//8 //Title Promotion` at line 54) whose commented-out `getPlayerStats(User user)` method calls `user.getTitleName()`, `user.getExperience()`, `user.getJoinDate()`, `user.getPlayTime(...)`, `user.getKills()`, `user.getGems()`, `user.getFriendAmount()` — **none of which exist on the v2 `User` class** (`v2:src/main/java/net/knightsandkings/util/ColorOptions.java:54,123-138`). It would not compile if uncommented.
- **Owner/staff-mode checks continue ad hoc** (`k&k.owner`, `k&k.staff` checked directly at each call site) but the v1 vanish-toggle behavior itself was never rebuilt — see Finished vs WIP.

## Known edge cases / bugs

1. **Clearly a bug** — v1 `User.refreshAssignmentMaximum()` unconditionally re-adds `donatorID` to `AssignmentDailyAmount` on every call without first resetting to a base value; since it's invoked on login, on every promotion, and on every demotion, repeated calls compound the donator bonus indefinitely instead of applying it once. `v1:src/Users/User.java:628-635`.
2. **Likely a bug / dead field** — v1 `User.level` (DB column `Level`) is loaded and saved on every load/save cycle but has no setter anywhere in the codebase, and `getLevel()` on a `User` has zero callers. `v1:src/Users/User.java:151,303,413,1217`.
3. **Likely a bug** — v1 `Main.scheduledDonator` (and the sibling `scheduledgive`) is an in-memory-only `HashMap<UUID,Integer>`, never persisted to the DB. A donator rank granted to an offline player is silently lost if the server restarts before that player's next login. `v1:src/Main/Main.java:289`, `v1:src/Users/Users.java:150-203,477-490`.
4. **Clearly a bug** — v1 `UserCommands.onCommand`'s `"save"` branch checks `!sender.hasPermission("k&k.ranks.staff")` and sends an error message, but does not `return` — the save logic executes regardless of whether the permission check failed. `v1:src/Users/UserCommands.java:217-222`.
5. **Likely a bug** — v1 `User.salary` is a cached field, set only inside `setData()` (i.e. on load/refresh); it is never refreshed when `titleID` changes via promotion/demotion mid-session. The welcome-message display (`Listeners/PlayerListener.java`) and the dead `User.SalaryPayout(uuid)` instance method both read this stale cache, while the actual scheduled payout listener (`Currency/SalaryPayout.java`) bypasses the cache and recomputes fresh from `Title.getSalary(titleID)`. A player promoted mid-session sees a stale salary figure in their status display until they relog. `v1:src/Users/User.java:336`, `v1:src/Listeners/PlayerListener.java:175`, `v1:src/Currency/SalaryPayout.java:35-36`.
6. **Likely a bug** — v1 `offlineUser.SalaryPayout(uuid)` calls `Bukkit.getServer().getPlayer(...)` and immediately calls `player.sendMessage(...)`/`player.playSound(...)` with no null-check, despite this class existing specifically to operate on **offline** users — will NPE if actually invoked for a player who is offline. `v1:src/Users/offlineUser.java:2853-2874`.
7. **Might be intentional, unclear** — v1 group-name casing is inconsistent between `RankCommands` (`"Owner"`, `"Builder"`, `"Staff"`, `"Default"`) and `UserCommands` (`"owner"`, `"co-owner"`, `"builder"`, `"staff"`, `"default"`) when dispatching `pex group/user ...` commands. PermissionsEx group matching may well be case-insensitive, but this reflects the same duplicated/never-reconciled logic pattern seen elsewhere in v1's user code. `v1:src/UsefulCommands/RankCommands.java:35-38` vs `v1:src/Users/UserCommands.java:86-208`.
8. **Clearly dead code, not a runtime bug** — v1 `Users.JoinEvents` is registered as a Bukkit listener (`v1:src/Main/Main.java:766`) but every `@EventHandler` method in it is commented out, making the registration a no-op. The real join flow lives in the separately-named `Listeners.PlayerListener`. Anyone reading `JoinEvents.java` in isolation could mistake it for the active flow. `v1:src/Users/JoinEvents.java`.
9. **Clearly a bug** — v2 `Enderchest.opCheck` dereferences `target.getName()` on a `Player target` that is provably `null` at that point, in two places: once inside the `if (offlinePlayer == null)` branch, and again inside a later `if (target == null)` branch. Guaranteed `NullPointerException` whenever those branches are reached. `v2:src/main/java/net/knightsandkings/spigot/command/user/Enderchest.java:78,88`.
10. **Clearly incomplete/WIP** — v2 `UserCommand.onFetch(Player player, String username)` declares (and its `@CommandCompletion` implies use of) a `username` parameter, but the method body never references it at all — it fetches only the caller's own `User` and does nothing further. `v2:src/main/java/net/knightsandkings/spigot/command/user/UserCommand.java:66-79`.
11. **Clearly a bug** — v2 `PlayerListener.onJoin` calls `errorRepo.getObjectByUser(user)` with `user` already confirmed `null` on that code path (that's why the branch is entered). `UserLoginErrorCache.getObjectByUser` dereferences `user.getUuid()` inside its loop, which throws NPE as soon as the error cache is non-empty. `v2:src/main/java/net/knightsandkings/listeners/PlayerListener.java:94-98`, `v2:src/main/java/net/knightsandkings/dal/cache/UserLoginErrorCache.java:23-26`.
12. **Likely a bug** — v2 `UserDAO.getObjectByUsername` builds its JPQL by raw string concatenation (`"from User AS u WHERE u.name = '" + username + "'"`) instead of a bound `:param`, unlike every other query method in the same class (`getIdListByAddress`, `getListByAddress` both use `setParameter`). Injection-shaped code smell even if only ever called with trusted input today. `v2:src/main/java/net/knightsandkings/dal/dao/UserDAO.java:30-54`.
13. **Clearly a bug** — v2 `UserDAO.getUsernameList` builds the query string as `"select d.name from" + ClassName` with no space between `from` and the class name, producing invalid JPQL (`"select d.name fromUser"`). This method would throw at runtime on every actual invocation. `v2:src/main/java/net/knightsandkings/dal/dao/UserDAO.java:107-125`.
14. **Likely a bug, severity unclear** — v2 `UserLoginError.uuid` is annotated `@Convert(converter = WGRegionConverter.class)` — a WorldGuard *region* converter applied to a plain user UUID column, almost certainly copy-paste residue from a dominion/region entity. Whether it actually breaks persistence depends on `WGRegionConverter`'s internal behavior on a non-region UUID, which wasn't traced further as out of scope for this system. `v2:src/main/java/net/knightsandkings/model/user/UserLoginError.java:39-41`.
15. **Self-flagged bug by the original author** — v2 `UserLoginError`'s constructor comment reads `//TODO: Not converting properly to readable string` directly on the line that converts an exception's stack trace to `stackTraceString`. `v2:src/main/java/net/knightsandkings/model/user/UserLoginError.java:72`.
16. **Might be intentional, unclear** — v2 `UserStatistics.dailyStatistics` is `@Transient`, with its `@OneToOne`/`@JoinColumn` mapping present but commented out directly above the field. Daily statistics are computed and used in memory each session (and presumably persist as their own standalone `UserStatisticsDaily` row via its own `@Entity @Table`), but the relation **back** from the parent `UserStatistics` row doesn't survive a reload — looks like an abandoned half-migration rather than a deliberate design choice, but wasn't confirmed either way. `v2:src/main/java/net/knightsandkings/model/user/UserStatistics.java:67-70`.

## Finished vs work-in-progress

### v1

- **Title / Experience / Donator system: finished and consistently wired up.** Save/load, event-driven promotion/demotion (`ExperienceChangeEvent` → `TitleChangeEvent`), commands (`/experience`, `/nexttitle`, `/donator`), and the active join listener all reference it coherently, and it has no orphaned classes.
- **`Users.JoinEvents`: dead code.** Registered but 100% of its `@EventHandler` methods are commented out; superseded by `Listeners.PlayerListener` (see Known edge cases #8).
- **`UserProfile.java`: dead/orphaned scaffold.** An interface of nullable fields with a misspelled field (`roomeAmount`) and no implementers found anywhere.
- **`offlineUser.java`: finished but duplicated.** A large (4,174-line), independently-maintained parallel implementation of nearly all of `User`'s business logic, wired into real staff commands (`/donator`, `/user`), but a standing maintenance liability since every rule change (e.g. the assignment-cap bug above) has to be made in two places to stay consistent — and evidently wasn't always.
- **`User.level`: abandoned/dead field.** Persisted every load/save but never mutated or read by any code path found (see Known edge cases #2).
- **Owner/staff mode: finished**, actively wired (commands, permission gates, visibility toggling via `hidePlayer`/`showPlayer`), with state deliberately kept off the `User` entity in static maps rather than persisted.
- **In-game PermissionsEx group commands (`/user`, `/default`): finished and wired**, though duplicated in style between the two command classes (Known edge cases #7).

### v2

- **`User` / `UserStatistics` / `UserStatisticsDaily` / `UserLogin` / `UserLoginError`: finished and actively wired.** `User.java` was touched across dozens of commits through 2022-09-17 (its most recent change on `main`), and `UserStatistics`'s stat mutators are called from real gameplay listeners across combat, movement, minigames, and sieges — not merely exercised from within the `model/user` package.
- **`KnKUser.java`: dead/abandoned.** Introduced in the very first Hibernate-setup commit (`1a83652`, "Initial setup of Hibernate") and never functionally touched again on `main` after `e6f9d34` ("Multiple improvements") — its only later appearance anywhere in the repo's full history is an IDE "Clean" auto-format commit and a Java-21-porting commit on the unrelated `2025/01/Hibernate-update` branch, neither of which added real logic. Its only live reference in `main` is `KnKUser.cache.clear()` in `KNK.onDisable()`, directly below a commented-out per-object save loop. It was superseded by `User` + `UserRepository`/`UserDAO`/`UserCache` before it was ever finished.
- **Title/Rank/Level/Experience progression: never (re)built in v2.** No entity, no command, no listener, no DB table implied anywhere. Only traces are a never-implemented `TODO` about future item-purchase gating and dead, non-compiling-if-uncommented copy-pasted code in `ColorOptions.java` (see Business rules and Known edge cases).
- **Owner-mode/staff-mode vanish toggle: not (re)built, but explicitly intended.** Three separate TODO comments across unrelated files say so directly: `v2:src/main/java/net/knightsandkings/listeners/EntityListener.java:140` ("TODO Should be changed to OwnerMode"), `v2:src/main/java/net/knightsandkings/model/dominion/Gate.java:785` ("TODO Should be changed to ownermode"), and `v2:src/main/java/net/knightsandkings/model/minigame/MiniGame.java:837-839` ("TODO Can be added when the User Class supports ownerMode and StaffMode" — directly above commented-out calls to `user.setOwnerMode(false)`/`user.setStaffMode(false)`). This is a known, deliberate gap, not an oversight — but the TODOs are themselves years-stale with no further movement.
- **`UserCommand.onFetch`: stub.** Ignores its own `username` argument (Known edge cases #10).
- **The join-failure/"error lobby" handling in `PlayerListener.onJoin`: explicitly unfinished** per its own TODO ("Handle sending player to error lobby to get help from staff...").

## v1 vs v2 differences

- **Persistence architecture.** v1: hand-written JDBC, several `PreparedStatement`s built via raw string concatenation rather than bound parameters, against a monolithic `Player` table plus small lookup tables (`Titles`, `Donator`, `DonatorTemp`); one giant `User` object mixes identity, economy, combat stats, and permissions-adjacent state. v2: Hibernate/JPA entities split by concern (`User`, `UserStatistics`, `UserStatisticsDaily`, `UserLogin`, `UserLoginError`) behind a repository → cache → DAO layer, so identity, session/login history, and gameplay statistics are separate persisted objects instead of one row.
- **Rank/Title/Level progression — dropped entirely.** v1's `Title` system (experience-gated, 0–18, salary/coin/gem/exp bonuses, multi-level catch-up promotion/demotion loop, unlock thresholds at 5/10/12/15) has **no v2 equivalent whatsoever.** This is a full feature removal, not a rename or simplification — see Business rules and Known edge cases for the dead traces that confirm it was once planned to carry over and then abandoned.
- **Donator rank — dropped entirely.** v1's purchasable donator tier (default/noble/royal/dragon blood, with a temporary-rank-plus-expiry-plus-restore mechanism) also has no v2 equivalent; v2's `User` has only a flat `cash` balance and no rank/tier field of any kind. The only leftover trace is the unused `"Donator-ranks' information"` menu title string in `MenuUtil`.
- **Currency model simplified, then re-simplified.** v1 tracks `coins` and `gems` as two separate currencies plus `experience` as a third numeric resource on `User`. v2's live `User` entity has only one: `cash`. The abandoned `KnKUser` draft entity still carried `cash` + `gems` + `experience`, suggesting gems/experience survived into the earliest v2 design and were dropped specifically when `KnKUser` was abandoned in favor of the current `User`.
- **Owner/staff "mode" — permission checks kept, behavior dropped (with intent to restore).** v1 has a fully working vanish/god-adjacent toggle. v2 keeps the `k&k.owner`/`k&k.staff` permission checks at relevant call sites but never rebuilt the actual mode/toggle — and says so explicitly via TODOs in three unrelated files.
- **In-game server-group/rank management — dropped.** v1 has commands (`/user staff|builder|co-owner|owner|default`, `/default`) that directly manipulate PermissionsEx group membership from inside the plugin. v2 has no equivalent command anywhere; group/rank assignment, if it happens in v2 at all, happens entirely through the external permissions plugin's own commands, outside KnK's control.
- **Session/login tracking — new and more structured, but unfinished at the edges.** v1 has no structured login-history entity; `lastLogin`/`playtime` are just overwritten fields on `User`, with no login-error tracking at all. v2 adds two entities with no v1 counterpart — `UserLogin` (a per-session record with login/logout timestamps and computed play time) and `UserLoginError` (a login-failure/retry-counter record capped at 3 attempts) — but the failure-handling flow built around `UserLoginError` is explicitly unfinished (Known edge cases #11, Finished vs WIP).
- **Gameplay statistics — restructured, not just carried over.** v1 keeps kill/death/blocks-broken/fish-caught counters as flat "today + lifetime" field pairs directly on `User` (e.g. `blocksBrokenWood`/`blocksBrokenWoodToday`). v2 consolidates all of this into a dedicated `UserStatistics`/`UserStatisticsDaily` pair with a broader and different set of tracked stats — it adds combat/minigame/siege specifics (headshots, gate damage, kill-streak, objectives captured, minigame/siege win-loss-kill-death splits) that v1 never had, while dropping v1's block-breaking and fishing counters entirely.
- **Permission node naming — same convention, more structure.** Both versions use `k&k.<feature>` strings checked via Bukkit's `hasPermission`. v1 declares essentially nothing in `plugin.yml` (permissions are ad hoc strings scattered through code, backed by PermissionsEx groups managed via in-plugin commands). v2 registers a top-level permission per command in `plugin.yml` **and** layers finer-grained ACF `@CommandPermission` annotations per subcommand — more structured declaration, though enforcement is still entirely external in both versions.

## Open questions

1. Was the v1 Title/Rank/Donator progression system (experience thresholds, salary/coin/gem/exp bonuses, promotion/demotion unlocks, donator tiers) intentionally dropped going into v2/v3, or is it something the project owner still wants rebuilt? Nothing in the v2 history explains the removal — it simply stopped being maintained, with dead copy-pasted references left behind and no design notes.
2. Should v3 rebuild the owner-mode/staff-mode vanish toggle? v2's own TODOs treat it as "still wanted, just not built yet," but those TODOs are years old with no follow-up — worth confirming it's still desired (and in what form) before rebuilding.
3. Is the in-game PermissionsEx/rank-group-management surface (`/user staff|owner|...`, `/default` from v1) meant to be rebuilt inside v3, or is coarse rank/group assignment intentionally meant to live entirely in the external permissions plugin, as it already effectively does in v2?
4. If a progression/rank system is wanted in v3, should it keep v1's two-track split (an earned "Title" tied to numeric experience, separate from a purchased/granted "Donator" rank), or should these be merged into a single rank concept? In v1 the two systems interact only through the shared `AssignmentDailyAmount` bonus formula and a "highest title" congratulatory message — nothing structurally requires them to stay separate other than history.
5. What was v1's `User.level` field actually for? It's persisted every load/save but never set anywhere and never read by any caller found. Candidates include: a vestigial predecessor to `titleID` from an earlier design, a planned-but-never-built separate "player level" concept distinct from Title, or simply dead scaffolding from a template. Not resolvable from code alone.
6. Given that v2's `UserStatistics`/`UserStatisticsDaily` system is the one clearly finished, actively-used piece of the v2 user model (unlike the abandoned `KnKUser`, the unbuilt rank system, and the unfinished login-error handling), should it be treated as the closest thing to a "reference" for how a v3 user/stats model should be shaped, even though this spec's scope is nominally about users/roles/ranks/levels/permissions rather than statistics?
