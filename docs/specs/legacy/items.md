# Items (custom item types)

Scope: the item/product entity itself — its data model, material/type mapping, grade/rarity, soulbound/ghosted/enchant/limited behavior, and crafting/drop restrictions. Kits and siege objects are covered by other spec files in this batch and are intentionally out of scope here. Shop/property selling mechanics are only described to the extent they touch the item entity itself (price fields, sellability rules); the property/shop system proper is out of scope.

## Data model

### Naming mismatch (read this first)

v1 has **no class literally named "Item."** Its closest equivalent is the `Products/*` package: `Product` is the de-facto item definition, `ItemType` + `ProductMaterial` supply the Bukkit-material mapping, and `ProductCategory` supplies the taxonomy. v2 introduces an explicit `Item` + `Itemtype` pair. The mapping is roughly `Product ~ Item`, `ItemType+ProductMaterial ~ Itemtype`, `ProductCategory ~ Category`, but **v2's `Item` is not a superset of v1's `Product`** — v2 dropped soulbound, ghosted, custom enchantments, price ranges, limited-time items, and crafting restrictions (see "v1 vs v2 differences").

### v1 (`Products/*`, `GemProducts/*`) — raw JDBC, no ORM

- `ItemType` (`v1:src/Products/ItemType.java`) — CRUD over an `ItemTypes` table. Columns inferred from SQL: `ID`, `MaterialID` (FK to `Materials`), `ItemType` (string), `BlockID` (string, format `"<numericMaterialId>"` or `"<numericMaterialId>:<data>"`). This is a mapping from a legacy Bukkit numeric material id (+ optional data byte) to a symbolic type name. Note `MaterialID` (FK to `Materials.ID`, a display material *name*) and `BlockID` (the raw numeric id used to reconstruct an actual `ItemStack`) are two parallel, independently-queried concepts.
- `ProductMaterial` (`v1:src/Products/ProductMaterial.java`) — CRUD over `Materials` (`ID`, `Material` name string).
- `ProductCategory` (`v1:src/Products/ProductCategory.java`) — CRUD over `ProductCategories` (`ID`, `Name` — auto-capitalized on save, `Description`). Flat, single-level list.
- `Product` (`v1:src/Products/Product.java`, 2361 lines) — the actual item definition. Backed by **two parallel tables** selected via a `gemproduct` boolean threaded through almost every method: `Products` (regular items) and `GemProducts` (premium-currency items). Columns inferred from the queries: `ID`, `Name` (unique, lowercased on save), `DisplayName`, `CategoryID` (FK `ProductCategories`), `ItemTypeID` (FK `ItemTypes`), `PriceMin`, `PriceMax`, `Description`, `Grade` (int 1–5), `Enchantments` (string-encoded `"<enchantId>:<level> <enchantId>:<level> ..."`), `Lore` (comma-joined string), `LimitedID` (FK to `LimitedItems`, see below — effectively unused), `Active` (bool, filters "active" products), `BaseDropAmount`. There is no persisted NBT/ItemStack representation — every `ItemStack` is rebuilt on demand from Material + data + enchantments + lore each time an item is materialized (e.g. `Product.createPropertyItem`).
- `LimitedItem` (`v1:src/Products/LimitedItem.java`) — standalone CRUD over `LimitedItems` (`ID`, `Name`, `ExpireTime`). See "Finished vs WIP" — never actually wired to anything.
- `GemProducts` (`v1:src/GemProducts/GemProducts.java`) — `extends Product`, adds only `GemPrice` get/save against the `GemProducts` table. This confirms gem-products are the **same item shape, different currency + different table**, not a distinct data model — treat as a sub-concept, not a parallel entity family.
- Soulbound / Ghosted / effective-enchantment-level state is **not modeled as columns at all**. It's entirely encoded in the live `ItemStack`'s lore text (magic strings `"Soulbound"` / `"Ghosted"`, colored via `ChatColor`) plus unsafe enchantments applied directly to the stack. There is no persisted record of which physical item instances are soulbound — it's derived at runtime by scanning lore strings (`Product.soulbound(ItemStack)`, `Product.ghosted(ItemStack)`, `v1:src/Products/Product.java:1521-1585`).

### v2 (`model/item/*`, `model/category/*`, `model/Grade.java`) — Hibernate entities

- `Item` (`v2:src/main/java/net/knightsandkings/model/item/Item.java`) — `@Entity`. Fields: `id` (int PK), `name` (`@Column(unique=true, nullable=false)`), `displayName`, `description` (`@ElementCollection` `List<String>` in table `Item_Description`), `category` (`@ManyToOne` → `Category`, not null), `grade` (`@ManyToOne` → `Grade`, not null), `origin` (`@ManyToMany` `Set<Dominion>` via join table `Item_Origin` — a `//TODO` at `Item.java:106` notes multi-dominion origin is provisional), `itemtype` (`@ManyToOne` → `Itemtype`, not null), `baseItem` (`@ManyToOne`, self-referential, nullable — the "template" `Item` a modified copy derives from; null means this instance *is* the base item), `basePrice` (`int`, default `1`, single flat price — no min/max split). Two `//TODO` comments (`Item.java:131-133`) flag that "resource" (base-drop-amount) and "purchasable" (basePrice/requiredTitle/requiredRank) behavior were meant to become separate interfaces but never were.
- `Itemtype` (`v2:src/main/java/net/knightsandkings/model/item/Itemtype.java`) — v2's analogue of v1's `ItemType`+`ProductMaterial` combined, now type-safe: `id`, `name` (a Bukkit `Material` enum name string, resolved via `Material.getMaterial(name)`), `data` (`byte`, `@Deprecated`, legacy 1.12-era data value — its `@Column` mapping is commented out, i.e. not actually persisted despite the field existing), `blockData` (`String`, the modern `BlockData#getAsString()` serialization, nullable). Unique constraint on `(name, block_data)`.
- `KNKBlock` (`v2:src/main/java/net/knightsandkings/model/item/KNKBlock.java`) — links an `Itemtype` to a world `Location` (`@OneToOne(cascade = CascadeType.ALL)`, `location_id`, `nullable = false`). See `docs/specs/project-overview/SOURCES_LOCATION.md` for the Location relationship mechanics — not re-derived here per that file's existing coverage.
- `RegisterSession` (`v2:src/main/java/net/knightsandkings/model/item/RegisterSession.java`) — **not persisted**: it implements `IPersistent<User>` but is only ever saved with `SaveMode.ONLY_CACHE` (`RegisterSession.java:40`), i.e. it never touches the DB. It's a short-lived in-memory workflow object keyed by `User`: while active, right-clicking a block either (a) registers each newly-seen Material+data+BlockData combination as a new `Itemtype` row ("registering" mode), or (b) stamps a previously-chosen `Itemtype`'s material/blockdata onto the clicked block ("placing" mode, for testing). It auto-expires via a delayed `BukkitTask` after 5 seconds (registering) or 8 seconds (placing) (`RegisterSession.java:46`).
- `Category` (`v2:src/main/java/net/knightsandkings/model/category/Category.java`) — v2's analogue of `ProductCategory`, now hierarchical: `id`, `name` (unique), `parent` (`@OneToOne` self-reference — one level of nesting, not a materialized tree), `tags` (`@ManyToMany` → `Tag`), `itemtype` (`@OneToOne` → `Itemtype`, used purely as the category's **menu icon material**, not as a restriction on which materials/itemtypes belong to the category).
- `Tag` (`v2:src/main/java/net/knightsandkings/model/category/Tag.java`) — `id`, `name`, `categories` (inverse `@ManyToMany`). Freeform labels attached to Categories; no evidence `Item` itself carries tags directly.
- `Grade` (`v2:src/main/java/net/knightsandkings/model/Grade.java`) — `id`, `name` (unique), `stars` (`int`, unique), `gradeIcon` (`@Transient`, defaults to `"★"` — its `@Column` mapping is commented out, so it is **never persisted**; any customization would revert to `"★"` on restart, though notably the Grade creation wizard never even asks the admin to set it, so this is more an unreachable stub than an active bug). Replaces v1's hardcoded `switch` on int 1–5 with a real, admin-creatable, data-driven entity.
- Caching note: every one of the above entities carries a commented-out `//@Cache(region = "...", usage = CacheConcurrencyStrategy.READ_WRITE)` annotation. Second-level Hibernate caching is present in the code as a leftover/aspirational annotation but is **disabled** in the code state examined — worth knowing since the general framing of "v2 = Hibernate + MySQL + cache" is only partly true for the item subsystem.

## Business rules and behavior

### Material resolution has two inconsistent paths in v1

- `Product.createPropertyItem` (`v1:src/Products/Product.java:1018-1101`) resolves the physical item via `ItemType.getBlockID()` → parse `"<id>[:<data>]"` → `Material.getMaterial(int)` (legacy numeric API).
- `Product.createEnchantItem` (`v1:src/Products/Product.java:1103-1145`), used by the enchant-book flow, instead builds a string `"<MATERIALNAME>_<ITEMTYPENAME>"` from `ProductMaterial`+`ItemType` and resolves it via `Material.valueOf(name.toUpperCase())`.

These are two different resolution strategies for the same underlying product depending on which creation method happens to be called, and they can diverge if the two source tables (`ItemTypes.BlockID` vs `Materials.Material`+`ItemTypes.ItemType`) ever get out of sync. v2 unifies this into a single path: `Itemtype.getMaterial()` → `Material.getMaterial(name)`, plus a real `BlockData` string for block-placement fidelity.

### Grade / rarity system drives loot generation (v1 only)

Grade is a hardcoded `int` 1–5 everywhere in v1 and feeds several independent, hand-tuned lookup tables:
- `getItemAmount(contribution, grade, category)` (`Product.java:849-940`) — a nested `switch`-on-grade, `switch`-on-contribution-tier (5/10/15/20/30) table of `Random(min,max)` ranges, further multiplied ×20 for `meat`/`fish`/`baked-goods`/`furniture` categories (bulk consumables get bigger stacks).
- `gradeChance(productID)` (`Product.java:1801-1830`) — flat % chance by grade: grade 1 → 70%, 2 → 60%, 3 → 40%, 4 → 5%, 5 → 1%. Used by the voting-reward flow (`v1:src/Votes/VoteEvent.java:148`) and an admin command (`v1:src/me/Pandi/Commands.java:655`) to gate whether a rolled reward is actually granted.
- `getdropChance(productID)` (`Product.java:1943-1964`) — reuses the fields `drop1..drop5 = 80, 70, 60, 10, 1` (declared as public mutable ints at the top of `Product`, `Product.java:41-45`, never actually changed anywhere at runtime) as %-chance-by-grade weights for `getRandomProduct`'s weighted random loot pick.
- `getGradeLore` (`Product.java:1397-1412`) appends `grade` copies of `"★ "` to the bottom of an item's lore as `"§l§bGrade: ★★★"`.

v2's `Grade` entity is data-driven (arbitrary name/star-count, admin-creatable via the Creation wizard) but **no code was found that reacts to a Grade value** — no drop-chance table, no item-amount table, nothing keyed off `Item.getGrade()` beyond rendering the star lore (`Item.getLore()`, `v2:src/main/java/net/knightsandkings/model/item/Item.java:303-334`, via `Grade.getGradeFullString()`). The loot-generation *behavior* built on top of grade in v1 was not reimplemented.

### Soulbound / Ghosted (v1 only)

Two mutually-exclusive lore tags, both driven by simple string presence checks:
- `SoulboundItem(item)` / `GhostItem(item)` (`Product.java:1587-1643`) append `"Soulbound"` (red) or `"Ghosted"` (dark gray) to lore, refusing to add either if the other is already present.
- `SoulboundEvents.onDrop` (`v1:src/Products/SoulboundEvents.java:81-96`) cancels a `PlayerDropItemEvent` if the dropped stack's lore contains `"Soulbound"`.
- Player-facing commands `/soulbound add|remove` and `/ghosted add|remove` (`v1:src/Products/SoulboundCommands.java`) let a permitted player toggle the tag on the item in their hand.
- **Important**: the actual "keep soulbound/ghosted items on death" logic (`onPlayerDeathe`, `onRespawn` in `SoulboundEvents.java:29-79`) is entirely commented out. So today, Soulbound only blocks a manual `/drop` (Q key) — it does **not** currently prevent death-drops, despite that clearly being the original intent (see "Known edge cases / bugs").

v2 has **no equivalent at all** — not in the data model, not as a listener. The only surviving trace is an unused `ChatColor soulbound = ChatColor.RED;` constant in `v2:src/main/java/net/knightsandkings/util/ColorOptions.java:120`.

### Custom enchantments (v1 only)

`Product.addCustomEnchantment` (`Product.java:1646-1731`) implements "custom" (non-vanilla) enchantments — poison, wither, freeze, blindness, confusion, strength, health boost, resistance, invisibility, chaos, flash chaos, armor repair (full list gated by `Enchantment.customEnhantment(id)`, `v1:src/Products/Enchantment.java:165-201`) — by writing a line like `"Poison II"` directly into the item's lore rather than using Bukkit's enchantment API. Leveling up re-applies the method: it scans existing lore for a line matching the enchant name, counts how many `"I"` characters follow, and re-derives the next Roman-numeral level via a hardcoded `switch` on concatenated `"I"` strings (`"I"`, `"II"`, `"III"`, `"IIII"`, `"IIIII"`, `"IIIIII"`) capped at `Enchantment.getEnchantmentMaxLevel(id)`. Players apply these via right-clicking with an enchanted book onto an inventory item (`v1:src/Products/EnchantbookClick.java`), with the per-attempt max determined by `canEnchant()` (`EnchantbookClick.java:148-177`), itself gated by item grade (higher grade = lower per-click cap: `maxEnchantLevel = enchantMaxLevel / (6 - grade)`).

No v2 equivalent exists (no custom-enchantment table, no enchant-book-click listener).

### Crafting is blocked for almost everything except food/furniture (v1 only)

`CraftEvents.onCraft` (`v1:src/Products/CraftEvents.java:28-70`) listens to `PrepareItemCraftEvent` and, for any player **not** in "owner modus" (an admin/build mode flag), nulls out the crafting result (`e.getInventory().setResult(null)`) **unless** the recipe result maps to a registered Product whose category is `meat`, `fish`, `baked-goods`, `vegetables`, or `furniture` — in which case it's swapped for the properly-lored/enchanted `createPropertyItem` version instead. In effect: regular players can only ever craft consumables/furniture through vanilla crafting; every other item category (swords, armor, bows, jewelery, tools, magic, resources) is entirely uncraftable by normal players and must come from the shop/loot system. This is a strong, unexplained design decision with no equivalent in v2 — v2 has no `PrepareItemCraftEvent`/`CraftItemEvent` listener anywhere in the codebase.

### Loot boxes (v1 only)

Two named consumable items — "Legendary Sword Box" and "Rare Sword Box" — are detected by exact (color-stripped) display-name match on right-click (`v1:src/Products/SpecialItemEvents.java`) and consumed to grant a randomly-enchanted, sometimes-soulbound/ghosted sword via `Product.getLegendarySwordBox()` / `getRareSwordBox()` (`Product.java:1966-2175`). These are long chains of independent `random.nextInt(100) <= X` rolls per enchantment/custom-enchantment/soulbound-or-ghosted-status, with the base sword itself also randomly upgraded (e.g. legendary box: 30% chance of the top-tier "golemheartsword" instead of a plain diamond sword). No v2 equivalent found.

### Sellability matrix and pricing (v1 only, shop-adjacent)

`Product.canProductbeSold(productID, propertyID, gemproduct)` (`Product.java:1184-1356`) is a large hardcoded `if`/`switch` matrix mapping property (shop) category → allowed product category/name combinations (e.g. a "weaponry" shop can sell `swords`-category products, plus `ironingot` by name specifically). `getSellPrice` computes a shop's buy-back price as `priceMin + 10%` unless the property category is `"warehouse"`, in which case it's just `priceMin`. v2's `Item.basePrice` is a single flat int with no min/max, no sellability matrix, and no warehouse-vs-shop distinction found anywhere in the item package (this may be intentionally out of item-spec scope and live in a shop/economy system instead — flagged as an open question).

### Give / delivery workflow

- v1: `Product.giveProduct` (`Product.java:2177-2224`) tries main inventory, then ender chest, then falls back to `addScheduledGive` (an in-memory `HashMap<UUID, HashMap<productID, amount>>` on `Main`) for offline players or full inventories. This queue is actually drained on join via `Users.CheckScheduledItems(user)`, called from `v1:src/Users/User.java:726` — i.e. despite a *separate*, commented-out attempt at the same thing in `Users/JoinEvents.java`, the live path is wired and functional.
- v2: `User.giveItem(item, amount)` (`v2:src/main/java/net/knightsandkings/model/user/User.java:580-589`) tries main inventory, else calls `addStashedItem(item)`. Unlike v1, this stash is **never drained anywhere** — see "Known edge cases / bugs."

### v2 admin registration and creation workflows

- New `Itemtype`s are registered either by holding an item and running `/itemtype add hand` (`v2:src/main/java/net/knightsandkings/spigot/command/item/ItemtypeCommand.java:39-66`, captures Material+data but **no** BlockData), or by `/itemtype add click` which starts a `RegisterSession` and lets the admin right-click multiple blocks in the world within a 5-second window, capturing full `BlockData` for each (`RegisterSession.java:97-134`).
- `Item` itself is created/edited through the generic multi-step `CreationStage` wizard shared across many v2 entities: name → display name → description → category (single-select) → itemtype (single-select) → grade (single-select) → origin (multi-select of `Dominion`s) (`Item.java:373-421`). `/item edit <item>` re-runs this wizard against an existing Item (`v2:src/main/java/net/knightsandkings/spigot/command/item/ItemCommand.java:141-167`).

## Known edge cases / bugs

- **Clearly a bug** — `Product.giveProduct`'s ender-chest fallback branch checks `target.getEnderChest().firstEmpty() != -1` but then calls `target.getInventory().addItem(item)` (the same call as the main-inventory branch, not `target.getEnderChest().addItem(item)`) while still telling both the player and the sender the item was placed "in your/his enderchest." Since the main inventory was already confirmed full in the preceding `if`, this `addItem` call returns undelivered leftovers that are never checked or handled — items given this way are silently lost. `v1:src/Products/Product.java:2206-2211`.
- **Clearly a bug** — `ProductCommands.onCommand`'s `/product set` handler checks `args.length >= 5` but then indexes `args[5]` (a 6th element) unconditionally on the same line, so `/product set <name> <category> <grade> <minprice> <maxprice>` with no description (exactly 5 args after `set`, i.e. `args.length == 6` total... concretely: the condition allows `args.length == 5`, which only has indices 0–4) throws `ArrayIndexOutOfBoundsException`. `v1:src/Products/ProductCommands.java:71,75`.
- **Clearly a bug** — `PropertyProduct.getProductAmount`'s SQL is malformed: `"SELECT * FROM PropertyProducts WHERE PropertyID=? AND ProductID;"` is missing `=?` after `ProductID`, yet the code still calls `stmt.setInt(2, productID)` against a statement with only one placeholder — throws `SQLException` on every call. `v1:src/Products/PropertyProduct.java:118-120`.
- **Likely a bug** — `Product.soulbound(item)` / `ghosted(item)`: the lore-size branching assumes `meta.hasLore()` with `lore.size() <= 1` implies exactly one line and safely does `lore.get(0)`, but `hasLore()` can be true for a non-null, **empty** lore list, in which case `lore.get(0)` throws `IndexOutOfBoundsException`. `v1:src/Products/Product.java:1521-1585`.
- **Likely a bug** — `EnchantbookClick.canEnchant`'s per-click level cap is computed as `Math.round(enchant.getEnchantmentMaxLevel(id) / (6 - grade))`, but both operands are boxed `Integer`s, so the division truncates to an `int` *before* `Math.round` ever runs — the `Math.round` call is a no-op leftover, most likely from an earlier float-based version of this formula. `v1:src/Products/EnchantbookClick.java:151`.
- **Likely a bug** — `ItemtypeCommand.onAdd`'s `hand` registration path constructs `new Itemtype(mat.toString(), data, null)` — a `null` `BlockData` — while the `click` path (`RegisterSession`) always supplies real `BlockData`. `Itemtype.getBlockData()` unconditionally calls `Bukkit.createBlockData(blockData)` with no null-check, so any Itemtype registered via `hand` will NPE the first time its `BlockData` is read. `v2:src/main/java/net/knightsandkings/spigot/command/item/ItemtypeCommand.java:55` vs `v2:src/main/java/net/knightsandkings/model/item/Itemtype.java:143-145`.
- **Clearly a bug / dead feature** — v2's `User.stashedItems` (the full-inventory fallback for `giveItem`) is a plain `List<Item>` deduplicated via `Item.equals()` before insertion (`User.java:439-448`), so a second full-inventory grant of the *same* `Item` while one is already stashed is silently dropped with no quantity tracking at all (the stash only ever remembers "you're owed this Item," never a count). Worse, `removeStashedItem` has **zero callers** anywhere in the codebase — nothing ever drains the stash back to a player, so any item that lands there is permanently unrecoverable through normal play. `v2:src/main/java/net/knightsandkings/model/user/User.java:439-448,580-589`.
- **Might be intentional, unclear** — `addCustomEnchantment`'s level-up mechanic caps out via a hardcoded `switch` on concatenated `"I"` strings up to 6 characters (`"IIIIII"`) before falling back to `getCustomEnchantLevel(maxLevel)`. It functionally works for any `maxLevel` because of that fallback, but it's a fragile, string-length-based mechanism rather than storing an integer level — a redesign risk if this were ever ported. `v1:src/Products/Product.java:1646-1731`.
- **Might be intentional, unclear** — `CraftEvents.onCraft` reads `Player player = (Player) e.getViewers().get(0)` to identify the crafter, assuming the crafting inventory's first viewer is always the crafting player. Holds in the common single-player-at-a-crafting-table case but is an unguarded assumption. `v1:src/Products/CraftEvents.java:31`.

## Finished vs work-in-progress

### v1 (single squashed commit — judged by code shape / wiring, not history)

**Finished and wired:** `Product` core CRUD + `ItemStack` generation, `ProductCategory`/`ProductMaterial`/`ItemType` CRUD, `CraftEvents` (active listener), `DropItem` (active, sets custom entity name on dropped/spawned items), `SoulboundEvents.onDrop` (active), `SpecialItemEvents` (loot-box right-click, active), `SoulboundCommands` (`/soulbound`, `/ghosted`, active), `EnchantbookClick` (full enchant-book-on-item flow, active), `ProductCommands` (`/product set|get|give|remove|list`, active), `GemProducts` (cleanly extends `Product`, wired via the `gemproduct` flag), scheduled/offline item delivery (`Users.CheckScheduledItems`, wired from `User.java:726`).

**WIP / dead code:**
- `LimitedItem` (`v1:src/Products/LimitedItem.java`) is a fully-formed CRUD class with **zero callers anywhere outside itself**. `Product.getLimitedID`/`saveLimitedID` persist a `LimitedID` FK column, but nothing ever creates a `LimitedItem` row, checks its `ExpireTime`, or removes an expired item from a player. The schema and plumbing exist; the feature does not.
- `SoulboundEvents.onPlayerDeathe` / `onRespawn` — the death-protection logic for Soulbound/Ghosted items is entirely commented out (`v1:src/Products/SoulboundEvents.java:29-79`). Only the manual-drop-blocking handler is live, so dying currently still drops Soulbound items — the reverse of what the surrounding (commented) code clearly intended.
- A commented-out NMS-based `addGlow` method (`Product.java:963-975`) sits beside the live, simpler `EnchantmentGlow`-based approach actually used in `createItem` — an abandoned alternate implementation left in place.
- A separate commented-out attempt at delivering `scheduledgive` on join lives in `v1:src/Users/JoinEvents.java` — dead, but superseded by the working `Users.CheckScheduledItems` path described above (not itself unfinished, just duplicated/messy).

### v2 (git history available — `main` HEAD for item files is 2022-12-21/22; later branches are migration-only, see below)

**Finished and wired:** `Item`/`Itemtype`/`Category`/`Tag`/`Grade` as Hibernate entities with complete multi-step Creation-wizard flows; `ItemCommand` (`list`, `fetch`, `save`, `remove`, `edit`, `get`, `rename` — all implemented); `ItemtypeCommand` `add hand`/`add click`/`place` (functional registration workflow via `RegisterSession`).

**WIP / dead code:**
- `KNKBlock` implements `ICreatable` but `getCreationStages()` and `createInstance()` are raw `// TODO Auto-generated method stub` returns of `null` (`v2:src/main/java/net/knightsandkings/model/item/KNKBlock.java:111-121`), and `getKeyClass()` also returns `null` despite a `KEY_CLASS` constant being defined. KNKBlock is a data-model shell with no admin-facing creation flow — it cannot be created through the same generic wizard system the rest of the catalog uses.
- `ItemtypeCommand.onPlace` is explicitly annotated `@Description("...for test purposes only")` (`ItemtypeCommand.java:88`) — a self-admitted test/dev-only command.
- `User.stashedItems` — modeled, partially wired (writes happen), but functionally a black hole (see "Known edge cases / bugs").
- `ItemOverview` menu (`v2:src/main/java/net/knightsandkings/model/menu/item/ItemOverview.java`) reads as scaffolding rather than a finished admin UI: the top-level section is literally named `"TestHeader/Main"`, one button's lore is the single word `"Test"`, and the menu mixes an unrelated `"Players"` section (with player-order toggle buttons wired to nothing beyond visibility toggling) into what's supposed to be an item-browsing overview.
- Commit message `e920087 "Added item rename command to ItemCommand (untested)"` is a direct, self-admitted "shipped without verification" signal for the `/item rename` subcommand.
- **Git-history signal**: `Item.java` and `Category.java`'s last commit on `main` is 2022-12-21/22. Every later commit touching these files lives only on `2023/09/CommandEvents`, `2023/09/ProductionStructures`, `2023/12/LazyLoadingRemoval`, `2025/01/Hibernate-update`, and `2025/01/Java21-HibernateRemoval` — and a diff of `Item.java` between `main` and `origin/2025/01/Hibernate-update` shows **zero functional changes**, only a `javax.persistence` → `jakarta.persistence` + Hibernate-native `@Cascade` annotation migration. The tip of that chain, `2025/01/Java21-HibernateRemoval`, has a commit literally titled *"Succesfully compiled project in Java 21. Has major errors and does not run!"*. Conclusion: the **last known-working state of the item system is the `main`-branch Dec-2022 snapshot** described throughout this document; nothing after that is feature work, and the most recent work of all is explicitly broken.

## v1 vs v2 differences

### Architectural upgrades (v2 over v1)
- Raw JDBC `PreparedStatement`-per-field CRUD (v1, every getter/setter opens its own query) → Hibernate entities with typed relationships, explicit fetch/cascade control (v2).
- Grade hardcoded as `int` 1–5 with `switch` statements duplicated across ~6 methods (v1) → `Grade` is a first-class, admin-creatable entity with configurable name/star-count (v2) — though nothing yet *reacts* to a Grade value in v2 (see above).
- `ProductCategory`, a flat single-level list (v1) → `Category`, with parent/child nesting plus many-to-many `Tag`s (v2) — a genuine taxonomy upgrade.
- Two inconsistent, ad-hoc Material-resolution code paths (v1: legacy numeric id parsing vs `Material.valueOf(name)` string concatenation) → one consistent path via `Itemtype.getMaterial()`/`getBlockData()` (v2).
- One-shot, all-args-on-one-line admin creation (`/product set <name> <category> <grade> <min> <max> <description>`, no edit flow) (v1) → a generic, reusable multi-step `CreationStage` wizard with a dedicated `/item edit` (v2).
- New concept with no v1 equivalent: `Item.origin` (`Set<Dominion>`) — items can be tagged as originating from one or more kingdoms.
- New concept with no v1 equivalent: `Item.baseItem` self-reference — a "derived-from-template" relationship for modified/enchanted copies. v1 has no notion of item identity beyond superficial display-name matching on the live `ItemStack`.

### Functionality v2 dropped or never got around to reimplementing
- **Soulbound / Ghosted status** — absent from v2 entirely; only a leftover, unused `ChatColor soulbound` constant survives in `ColorOptions.java`.
- **Custom enchantments** (poison/blindness/confusion/chaos/armor-repair/etc.) and the enchant-book-click UI — no v2 counterpart.
- **Limited-time items** — no v2 equivalent (and as noted, this was already barely functional in v1).
- **Price range** (`PriceMin`/`PriceMax`) and the whole category↔property-category sellability matrix (`canProductbeSold`, `getSellPrice`) — v2's `Item` has only a single flat `basePrice`; no sellability rules were found anywhere in the v2 item package. (This may be intentionally shop/economy territory rather than item territory — flagged as an open question below.)
- **Crafting restriction** — v1 blocks nearly all player crafting outside "owner modus" except food/furniture categories; v2 has no crafting-related listener at all.
- **Loot boxes and grade-weighted random loot generation** (`getRandomProduct`, `getdropChance`, `getItemAmount`, `BaseDropAmount`) — no v2 equivalent; `Item` carries no drop-amount or drop-chance concept.
- **Premium-currency items** (`GemProducts`) — no v2 class/table was found anywhere in the codebase searched. Not confirmed whether this was moved to a different v2 package outside `model/item`/`model/category` or genuinely dropped (see open questions).

## Open questions

1. **Premium-currency items**: is there a v2-era redesign of `GemProducts` living outside the `model/item`/`model/category` packages searched here (e.g. under a payments/shop package), or was the whole premium-item-shop concept deferred/dropped? Needs confirmation before deciding whether v3 needs a parallel-currency item concept.
2. **Soulbound / Ghosted / Limited items**: given that v1's death-protection for Soulbound was already dead code (commented out) and `LimitedItem` was never wired up even in v1, how much real player-facing value did these ever deliver? Worth an explicit decision on whether v3 resurrects them, and if so, whether as persisted flags on the item entity itself rather than lore-string scanning on a live `ItemStack`.
3. **Crafting restriction policy**: v1's blanket "no player crafting except food/furniture" is a strong, opinionated rule with zero explanation in code or comments. Was this intentional (to force all non-consumable gear through the shop/loot economy), or an artifact of an incomplete category allow-list? This is undocumented business intent that v3 needs to make an explicit call on.
4. **`Item.origin` (Dominion linkage)**: the v2 data model and creation wizard support tagging an Item with one or more origin Dominions, but no code was found that *reads* `Item.getOrigin()` for any gameplay effect (e.g. restricting who can buy/craft/receive it). Is this meant to gate something, or is it purely cosmetic lore text?
5. **Grade-driven loot behavior**: v1's drop-chance/drop-amount tables are hand-tuned game balance hardcoded per grade 1–5. v2 made `Grade` data-driven but never reimplemented anything that reacts to it. If v3 wants loot-generation behavior back, should it stay keyed by an admin-configurable `Grade` (as v2 set up), and should the default value tables be v1's numbers, treated as already-tuned balance data?
6. **`Category.itemtype` (menu icon)**: is a "representative icon material per category," stored as a DB relationship, still wanted, or should v3 categories use a simpler config-driven icon map instead?
7. **Purchase gating on `Item`**: `Item.basePrice` defaults to `1` and a `//TODO Make an interface for purchasable items with basePrice, requiredTitle, requiredRank etc.` (`Item.java:133`) signals pricing/rank-gating was deliberately deferred and never built. Should v3 give `Item` first-class purchase requirements (title/rank gates), and should that live directly on the item entity or on a separate shop-listing concept — given v1 already split pricing between `Product` (price range) and `PropertyProduct` (per-shop price/amount)?
