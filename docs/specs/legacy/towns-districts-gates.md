# Towns, Districts, Gates (legacy `v1`/`v2` mining)

Source-driven spec covering the Town / District / Street / Gate / Structure / Warehouse system across the two legacy `knk` codebases. See `docs/specs/legacy/README.md` for the conventions used here. **Location internals (fields, `WorldConverter`, `CreationStageLocation`) are already fully documented in `docs/specs/project-overview/SOURCES_LOCATION.md` — this document does not repeat them and only describes how Town/District/Street/Gate/Structure/Warehouse reference Location.**

## Data model

### v1 — two parallel, both-live implementations

v1 actually contains **two separate Town/District model layers that coexist**, not one:

1. **Legacy DAO layer** (original, load-bearing across the whole plugin): `` `v1:src/Towns/Town.java` `` and `` `v1:src/Streets/Street.java` ``. These are not JPA entities — they are instance classes with raw JDBC (`PreparedStatement`/`ResultSet`) methods reading/writing tables `Town` (`ID, Name, RequiredTitleID, Description`), `TownRegion` (`TownID, SubID` — sub-regions), `DiscoveredTowns` (`TownID, UserID`), and `Street` (`ID, Name, TownID`). Dozens of unrelated feature packages (`Houses`, `Properties`, `Arenas`, `Quests`, `Resources`, `Rooms`, `Friends`, `NPCs`, …) import `Towns.Town` / `Streets.Street` directly for permission and region lookups, so this layer is the de-facto backbone of the whole plugin.
2. **Newer POJO layer**, added later and layered on top of the same DB tables: `` `v1:src/Models/Town.java` ``, `` `v1:src/Models/Street.java` ``, `` `v1:src/Models/district/District.java` ``, backed by static-method "repository" interfaces `` `v1:src/DataManager/Towns.java` ``, `` `v1:src/DataManager/Streets.java` ``, `` `v1:src/DataManager/Districts.java` ``. This layer introduces **District as a first-class concept for the first time in v1** — `v1:src/Models/district/District.java:14-30` (`ID, Name, TownID, Town, List<Structure>`), backed by a real WorldGuard region `district_<id>` created in `` `v1:src/DataManager/Districts.java:93-138` ``.

**Which is "live"?** Both are wired to real registered commands (see `` `v1:src/Main/Main.java:576-582` `` — `getCommand("town")`, `getCommand("street")`, `getCommand("gate")` → old DAO layer; `getCommand("town2")`, `getCommand("district")`, `getCommand("structure")`, `getCommand("creation")` → new POJO/wizard layer). Neither is dead code. The new layer is best understood as an in-progress, partially-finished rewrite that added District and a chat-driven creation wizard (see Business rules) without ever replacing the old DAO layer that the rest of the plugin depends on. This is itself the kind of "started and not finished" signal called out in the task brief.

**v1 has no class literally named "District" in the original/legacy layer.** The closest analog in the legacy layer is `Street` (`` `v1:src/Streets/Street.java` ``: `ID, Name, TownID`, no own WorldGuard region, just a DB-table grouping under a Town — confirmed by reading the class fully). `Street` is *not* architecturally equivalent to the new `District`: Street never owns a WorldGuard region of its own, District does (`district_<id>`). District is a genuinely new concept, not a rename of Street.

Structure model (new layer only — the old layer has no generic Structure base class):
- `` `v1:src/Models/Structures/Structure.java:11-42` ``: `id, name, streetID/Street, streetNumber, townID/Town, districtID/District (mandatory — the constructor calls `DataManager.Districts.InstantiateDistrict(districtID, false).addStructureList(this)` and will NPE if the district can't be resolved), spawnpoint`.
- `` `v1:src/Models/Structures/Gate.java:35-53` `` extends `Structure`: `materialID, faceDirection, originalHealth/health (default 200), gateRegion ("gate_<id>_gate"), isClosed, guardSpawnpoints, respawnRate (10), isInvincible, isDestroyed, canRespawn, isActive, GateEntity (ArmorStand)`.

### v2 — Hibernate entity hierarchy rooted at `Dominion`

All region-owning types share one JPA inheritance hierarchy (`@Inheritance(strategy = InheritanceType.JOINED)`), each with its own `@OneToOne` Location (see SOURCES_LOCATION.md) and its own WorldGuard region:

- `` `v2:src/main/java/net/knightsandkings/model/dominion/Dominion.java:77-217` `` — base: `id, name, description, created, allowEntry, location (OneToOne, cascade ALL), regionName (@NaturalId, column `wg_region_id`) + transient `ProtectedRegion region` resolved on demand via `WorldguardUtil``. Base WG flags: `DENY_MESSAGE=""`, `PVP=DENY` (`v2:...Dominion.java:150-156`), priority 10.
- `` `v2:...Town.java:53-186` `` extends `Dominion`: `requiredTitle` (int, default 1, column `reguired_title` — note the typo baked into the DB column name), `districts` (transient, lazily populated via `DistrictRepository.getDistrictsByTown`), deprecated `structures` field kept only for a menu shortcut. Region prefix `town_<id>`, priority 11.
- `` `v2:...District.java:56-170` `` extends `Dominion`: `town` (`@ManyToOne(optional=false)`, column `town_id` — a District **must** belong to exactly one Town), `streets` (transient, lazily populated via `StreetRepository.getStreetsByDistrict`). Region prefix `district_<id>`, priority 11.
- `` `v2:...Street.java:58-148` `` — **does NOT extend `Dominion`**. It is a standalone entity: `id, name, districts (@ManyToMany via join table `Street_Districts`)`, plus a deprecated `towns` field derived transitively from `districts`. It has no `location`/`region` of its own. This is the answer to "what actually distinguishes Street from District": **District is an administrative subdivision with its own physical WorldGuard region and belongs to exactly one Town; Street is a named road/path with no region of its own that can run through zero, one, or many Districts** (and therefore implicitly through multiple Towns).
- `` `v2:...Structure.java:69-198` `` extends `Dominion`: `district` (`@ManyToOne(optional=true)`, `nullable=true` — a Structure may exist outside any District, i.e. "in the wilderness"), `street` (`@ManyToOne(optional=false)` but the `@JoinColumn` is annotated `nullable=true` — contradictory, see Known edge cases), `streetNumber`, `capacity`/`capacityUsed`, `storages` (`@OneToMany` to `Storage` — see structure-production note below). `getTown()` (`v2:...Structure.java:180-191`) throws `NullPointerException` if `district` is null, i.e. wilderness structures crash this accessor.
- `` `v2:...Gate.java:90-1200` `` extends `Structure implements IStructure`: `material` (Itemtype, OneToOne), `gateBlocksOpened`/`gateBlocksClosed` (`@ManyToMany` to `KNKBlock` — captured block *snapshots*, not just a material id), `faceDirection`, `originalHealth`/`currentHealth` (default 500), `gateRegionClosed`/`gateRegionOpen` (two separate WG region-id string columns), `opened` (boolean, default true), `guardLocations` (`@Transient` — confirmed not persisted, consistent with SOURCES_LOCATION.md), `respawnRate` (10), `invincible`, `destroyed`, `active`, `canRespawn`, `gateStatsEntity` (transient ArmorStand), `overridden` (transient, Siege-minigame integration — out of scope here). Region prefix `gate_<id>` (plus `gate_opened_<id>`/`gate_closed_<id>`), priority 12, extra WG flag `INTERACT=allow`.
- `` `v2:...Warehouse.java:58-227` `` extends `Structure`: no extra persistent fields beyond `Structure`; exists purely as a storage-capacity Structure subtype. Priority 12, `INTERACT=allow`.
- `` `v2:src/main/java/net/knightsandkings/model/dominion/structure/**` `` (`Generation`, `GenerationHandler`, `IProducable`, `IProducer`, `Production`, `Storage`) implement a resource-production/storage system hung off `Structure`/`Warehouse` via the `storages` field. This is genuinely a separate system (production/transport chains) and is only mentioned here because it's structurally attached to `Structure`.

## Business rules and behavior

### Creation flow — general shape (both versions)

Both versions implement a **staged, chat-driven wizard**: a player types a start command, the plugin intercepts subsequent chat lines / commands (`PlayerChatEvent`, `PlayerCommandPreprocessEvent`) and feeds them into a running "Creation" session object rather than letting them reach normal chat/commands, one field at a time, until all stages are filled and the player types `confirm`.

**v1** (`` `v1:src/Models/creations/Creation.java` ``, `TownCreation.java`, `DistrictCreation.java`, `StructureCreation.java`): each subclass hardcodes its own numbered stages (`if (this.getStage() == 1) {...} else if (this.getStage() == 2) {...}`) with magic stage numbers. `StructureCreation` reuses the *same* stage-number space for House/Property/Gate and jumps around it with expressions like `addStage = this.getStage() + 8` (`v1:src/Models/creations/StructureCreation.java:540-547,862`) depending on `structureType` — brittle and easy to desync if a message list changes. Events are routed to whatever `Creation` is active for the sending user via `Creations.FindCreation(user)` in `` `v1:src/Listeners/PlayerListener.java:586-589,974-977,1352-1355` ``. Abandoned sessions can be "stashed" for a hardcoded 5 minutes (`300*20` ticks, `v1:src/Models/creations/Creation.java:240-255`), purely in-memory (`Creations.StashedCreations`), lost on restart.

**v2** (`` `v2:src/main/java/net/knightsandkings/creation/Creation.java` ``, `CreationStage.java`, `CreationStage{String,Boolean,Select,Region,Location,Combined}.java`): generalized into a reusable, **data-driven** stage model — each `ICreatable` (Dominion subtype) implements `getCreationStages(Creation)` returning an ordered `List<CreationStage>`, and one generic `Creation` engine drives `start/stop/next/undo/reset/complete/confirm/pause/resume/save/select/open` uniformly (`v2:...Creation.java:129-142`) instead of one big per-type switch statement. `Creation` and `CreationStage` are now real Hibernate entities (`creation`, `creation_stage` tables) so sessions survive a restart and can be stashed for up to `STASHTIME_MAX = 24*3600` seconds (`v2:...Creation.java:54`) — a real upgrade over v1's in-memory 5-minute stash. The *same* `getCreationStages()`/`createInstance()` pair is used for both creating a brand-new object (`id < 1`) and editing an existing one — see the `if (dominion.getId() < 1) {...} else {...}` branches in every `createInstance()` (e.g. `v2:...Dominion.java:105-147`, `Town.java:77-120`, `District.java:79-121`, `Gate.java:1095-1181`).

### Regions

v1 regions are always axis-aligned cuboids (`ProtectedCuboidRegion`, built from a WorldEdit selection's min/max corners). v2 regions are arbitrary `Polygonal2DRegion`/`ProtectedPolygonalRegion` footprints (extruded between a min/max Y) — towns, districts, gates and warehouses can have non-rectangular outlines in v2, which was not possible in v1.

Town/District WorldGuard region creation (v1, old DAO path, `` `v1:src/DataManager/Towns.java:116-190` `` and `` `v1:src/DataManager/Districts.java:100-166` ``): region id `town_<id>` / `district_<id>`, priority 8 for towns, `Worldguard.districtPriority` for districts, plus optional child "sub-regions" (`town_<id>,<index>` / `district_<id>,<index>`) parented via `region.setParent(parent)` for irregularly-shaped extensions to the main cuboid.

v2 region creation (e.g. `` `v2:...Town.java:77-120` ``): region id `town_<id>` / `district_<id>` / `dominion_<id>` (base) with priority 10 (Dominion) / 11 (Town, District) / 12 (Structure, Gate, Warehouse) — subclasses intentionally outrank their container so structure-level flags win region-priority ties.

### Spatial containment — is a District required to sit inside a Town? Does a Gate belong to exactly one Town/District?

- **v1, old `/town create` path** (`` `v1:src/Towns/TownCommands.java:95-160` ``): before creating a Town, both corners of the WorldEdit selection are checked against `checkTownRegion(...)` — if either corner already overlaps an existing `town`-category region, creation is refused ("You are overlapping another town, canceled creation."). Real anti-overlap enforcement.
- **v1, new `/town2 create` wizard path** (`TownCreation` → `DataManager.Towns.CreateTown(TownCreation)`, `` `v1:src/DataManager/Towns.java:80-254` ``): **no overlap check at all.** It will happily create a second `town_<id>` region overlapping an existing one.
- **v1, `/district create` wizard** (`DistrictCreation`, `` `v1:src/Models/creations/DistrictCreation.java:160-217,219-280` ``): explicitly validates that *both* corners of the main region (stage 3) and of every sub-region (stage 4) resolve, via `Worldguard.getStructureIDbyRegion("town", loc, manager)`, to the *same* `townID` selected in stage 1 ("The Region must be inside of the Townregions") before the selection is accepted. So v1 **does** enforce District ⊆ Town spatially — but only for District, not for Town-vs-Town overlap in the new path.
- **v1 Structure/Gate**: the `Structure` constructor requires an existing District to attach to (`v1:src/Models/Structures/Structure.java:41`), but `StructureCreation`'s wizard never checks that the Gate's own selected WorldGuard region actually falls inside that District's or Town's region — inconsistent with the District wizard's own containment check.
- **v2**: `District.town`, `Structure.district`, and `Gate/Warehouse.street` are all pure administrative foreign keys chosen from a dropdown (`CreationStageSelect`, e.g. `v2:...District.java:275-280`). **No code path validates that the drawn WorldGuard polygon for a District/Structure/Gate is actually spatially inside its selected parent's region.** This is a concrete regression relative to v1's District-containment check (though v1's own Town-vs-Town overlap check also didn't carry over into its new wizard path — both versions have containment gaps, just different ones).
- A Gate belongs to exactly one Street in both versions (`streetID`/`street`, mandatory field), and transitively to that Street's Town in v1 (`Street.TownID`) or Districts in v2 (`Street.districts`, many-to-many, so a Gate's Street — and therefore the Gate itself — can nominally sit on a Street that crosses more than one District/Town in v2, unlike v1 where a Street belongs to exactly one Town).

### Gate open/close mechanics

**v1** (`` `v1:src/Models/Structures/Gate.java` ``, `` `v1:src/Gates/GateAnimation.java` ``): a single WorldGuard region `gate_<id>_gate` defines the door's footprint, and a single `materialID` defines "the gate's block". `GateToggle.setClosed(boolean)` → `changeGateBlocks()` (`v1:...Gate.java:345-377`) constructs a `GateAnimation` that iterates the cuboid **layer by layer along Y** (`v1:src/Gates/GateAnimation.java:68-107`), replacing blocks matching `fromMaterial` with `toMaterial` one Y-level per tick (`animationSpeed = 10`, or `1` tick — i.e. near-instant — if the gate `isDestroyed`), playing `CHEST_OPEN`/`CHEST_CLOSE` sound. **No WorldGuard flag is toggled at all** — opening/closing a v1 gate is pure block-material replacement between "gate material" and air. On animation completion, `trySetGateEntity()` respawns an invisible marker `ArmorStand` at a computed gate-center (`getGateCenter()`, `v1:...Gate.java:266-312` — hardcoded per-facing-direction offsets and an unexplained `±0.5` nudge) whose custom name shows current HP.

Damage (`damageGate`, `v1:...Gate.java:409-469`): triggered by `BlockDamageEvent` (left-click/attack, not block-break — gates can't be mined away), not `PlayerInteractEvent`. Base damage 1 + item-derived bonus (`tools` category product doubles item damage; `DIG_SPEED`/`FIRE_ASPECT` enchantments add bonus damage). An item with no recognized "product" grade is confiscated unless the user is in owner-mode.

Toggling (`/gate toggle`, `` `v1:src/Gates/GateCommands.java:197-245` `` + `` `v1:src/Gates/GateEvents.java:126-186` ``): creates a `GateToggle` "arm" session; the *next* right-click on a block resolving to a `gate`-category region toggles that gate. `GateToggle` sets `timeOut = now + 4000ms` (`v1:src/Gates/GateToggle.java:79`) but schedules the actual auto-cancel task `3*20 = 60 ticks (3000ms)` later (`v1:...GateToggle.java:80-88`) — the stated 4-second window and the actual 3-second cancellation don't match (see Known edge cases). `/gate passthrough` opens the gate and force-recloses it 2 seconds later (`v1:...GateToggle.java:90-101`).

**v2** (`` `v2:...Gate.java` ``, `GateAnimationUtil` in `net.knightsandkings.util`): two separate WorldGuard regions, `gate_opened_<id>` and `gate_closed_<id>`, each created together with a **captured snapshot of the real in-world blocks** at creation time (`setGateBlocksOpened1`/`setGateBlocksClosed1`, `v2:...Gate.java:588-648`, called from `createInstance`, `v2:...Gate.java:1125-1163`) — every block in the region is read and stored as a `KNKBlock` (material + block-data + Location, see SOURCES_LOCATION.md) in the `gate_blocks_opened`/`gate_blocks_closed` join tables. `toggleOpened()`/`setOpened(boolean)` (`v2:...Gate.java:390-414`) delegates the actual block restoration to `GateAnimationUtil` (extracted into its own utility class — an architectural improvement, no longer inlined in the entity). This generalizes v1's single-material swap into an **arbitrary saved block pattern** (e.g. a multi-material drawbridge), at the cost of requiring the builder to physically construct *both* the open and closed states once to be captured. The gate's own base region (`gate_<id>`) carries `Flags.INTERACT = allow` so interaction inside the gate structure isn't blocked by whatever the containing Dominion's own region flags say.

Damage (`damageGate`, `v2:...Gate.java:774-857`): same core idea as v1 (tools-category doubles damage, `DIG_SPEED` bonus) plus new mechanics absent from v1: `FIRE_ASPECT` **and** `ARROW_FIRE` enchantments trigger *continuous* damage-over-time via `ContinuousGateDamageUtil` (fire keeps ticking damage on the struck block for a duration), and gates can be `overridden` by an active `Siege` minigame — while overridden, damage from a player on the siege's defending team (or an ally team) is cancelled outright. `passThrough()` re-closes after `4*20` ticks (4s, up from v1's 2s) unless the gate is `overridden`.

`/gate create` — **v1's old command path is broken**: `` `v1:src/Gates/GateCommands.java:452-492` `` calls `createGate(...)`, whose body has the actual DB-insert commented out (`// Gates.createGate(sender, name, streetID, townID, -1, faceDirection);`), and the corresponding `DataManager.Structures.Gates.createGate(...)` method itself is entirely commented out too (`v1:src/DataManager/Structures/Gates.java:49-75`). So `/gate create` never persists anything and then calls `Gates.instantiateGate(name, streetID, townID, true)`, which queries for a gate row that was never inserted. The only **working** way to create a Gate in v1 is `/structure create gate` (the wizard, `StructureCreation` → `DataManager.Structures.Gates.CreateGate(StructureCreation)`, which uses stored procedure `addGate`).

**v2's command layer has no `create` subcommand for any Dominion type at all** — see Finished vs WIP below for the detailed evidence; this is the single most important behavioral finding of this document.

### Ownership / permission checks

Neither version implements an in-game "owner of this specific Town/District" ACL. Both versions gate creation/edit/remove/toggle purely by static Bukkit permission nodes (v1: `k&k.town`, `k&k.district`, `k&k.gate`, `k&k.gate.toggle`, …, declared in `` `v1:plugin.yml` ``; v2: `k&k.dominion.town.*`, `k&k.dominion.district.*`, `k&k.dominion.structure.gate.*`, aikar `@CommandPermission` annotations). There is no "mayor"/per-object owner concept found in either codebase for Town/District (contrast with `House`/`Property`, which do have an `ownerID` — see `` `v1:src/Models/Structures/Buyable.java` ``).

## Known edge cases / bugs

- **Clearly a bug** — v1 `/gate create` (old command) is non-functional: the DB insert is commented out both in `GateCommands.createGate` and in `DataManager.Structures.Gates.createGate` (`v1:src/Gates/GateCommands.java:452-464`, `v1:src/DataManager/Structures/Gates.java:49-75`), so the command silently does nothing useful and then operates on a null `Gate`.
- **Clearly a bug** — v1 `DistrictCreation`'s sub-region save loop (`v1:src/DataManager/Districts.java:140-166`) iterates `creation.getTempSubRegions()` but for every iteration re-derives the selection from `creation.getTempRegion()` (the *main* region, not the loop variable `r`) and reuses the exact same WorldGuard region id `"district_" + districtID` on every pass — sub-regions never get their own bounds or unique id and will simply overwrite each other in WorldGuard.
- **Clearly a bug** — v1's "non-members" entry-group flag setup is a no-op in both `Towns.CreateTown` and `Districts.CreateDistrict` and `Towns.PurgeTown` (`v1:src/DataManager/Towns.java:140-148`, `v1:src/DataManager/Districts.java:117-125`): `RegionGroupFlag entryFlag = DefaultFlag.ENTRY.getRegionGroupFlag(); entryFlag.parseInput(Worldguard.getWorldGuard(), null, "non_members");` parses a value but never assigns it to the region via `region.setFlag(...)` — the parsed result is discarded. The apparent intent ("non-members can't enter") is never actually applied.
- **Likely a bug** — v1 `GateToggle` timeout mismatch: the field `timeOut` is set to `now + 4000ms` (`v1:src/Gates/GateToggle.java:79`) but the scheduled auto-cancel `BukkitRunnable` actually fires `3*20 = 60` ticks (3000ms) later (`v1:...GateToggle.java:80-88`) — the displayed/stored deadline and the real one disagree by a second.
- **Likely a bug** — v2 `Structure.street` is annotated `@ManyToOne(optional = false, ...)` but its `@JoinColumn` is `nullable = true` (`v2:...Structure.java:120-123`) — contradictory JPA metadata; unclear whether a Street is actually mandatory for a Structure.
- **Likely a bug** — v2 `Structure.getTown()` (`v2:...Structure.java:180-191`) throws `NullPointerException` whenever `district` is null, i.e. for any Structure legitimately placed outside a District ("wilderness") — exactly the case the class's own Javadoc says should be supported via a future `rulingTown` field that was never added.
- **Likely a bug** — v2's District/Structure/Gate/Warehouse creation wizards never verify that the drawn WorldGuard polygon is actually inside the selected parent Town/District's region (see Business rules → Spatial containment) — silent data inconsistency is possible (a District administratively "in" Town A but physically anywhere on the map).
- **Might be intentional, unclear** — v1's old `/town create` path checks for Town/Town overlap but the newer `/town2 create` wizard path does not; it's unclear whether the overlap check was deliberately dropped (e.g. because staff are trusted) or simply never ported.
- **Might be intentional, unclear** — v1 `Street.TownID == 1` is used as a sentinel meaning "street in the wilderness, no town" (`v1:src/Streets/Street.java:31-58`) rather than `NULL` or a dedicated flag — fragile (relies on town id `1` never being a real town) but may have been a deliberate shortcut given the DB schema at the time.
- **Might be intentional, unclear** — v2 `Gate`'s two `gateRegion*` columns are plain `String` region-id columns with a commented-out attempt at a `WGRegionConverter`-based typed conversion (`v2:...Gate.java:149-159`) — same raw-string pattern SOURCES_LOCATION.md documents for other WG-region fields elsewhere in v2, so this may simply be the established (if informally typed) convention rather than an oversight.

## Finished vs work-in-progress

- **v1**: both Town/Street model layers are live and reachable from registered commands — not dead code — but the old DAO layer remains the one nearly the entire rest of the plugin depends on, while the newer POJO/wizard layer only adds District plus the chat-wizard creation flow on top of (mostly) the same database tables. The new layer's `/gate create` old-command sibling was left broken (see bugs above) even though the wizard-driven creation path for the same object type works. This is a textbook "started a rewrite, got the new feature (District, wizard flow) working, never finished migrating the old call sites" situation.
- **v2, code-shape signal**: the `Dominion`/`Town`/`District`/`Street`/`Structure`/`Gate`/`Warehouse` entity model and their `getCreationStages()`/`createInstance()` pairs are fully implemented and reasonably polished (typed stages, region+location wizard steps, edit-reuses-create-code). However, **grepping the entire `spigot/command/**` and `model/menu/**` trees for a `create` subcommand or for any fresh `new Town()`/`new District()`/`new Gate()`/`new Street()`/`new Warehouse()` construction outside of `net.knightsandkings.data.Test*` seed-data classes turns up nothing.** Every `TownCommand`/`DistrictCommand`/`GateCommand`/`StreetCommand`/`StructureCommand`/`DominionCommand` only exposes `list/fetch/save/remove/edit(/resetflags/seed)`; `edit` always resolves an *existing* object by id via an aikar-commands context resolver before starting a `Creation` session against it. The only code anywhere that instantiates a Town/District/Gate/Street/Warehouse with the no-arg constructor (the precondition for `createInstance()`'s "new object" branch, `id < 1`) is the hardcoded `TestTown`/`TestDistrict1-3`/`TestGate1-2`/`TestStreet1-2`/`TestWarehouse1` seed generators wired to debug `seed`/`townseed` subcommands. **The player-facing "create a brand-new Town/District/Gate/Street/Warehouse in-game" entry point does not appear to exist anywhere in the code that reached `main`**, despite all the underlying machinery for it being built. This is the strongest concrete explanation found for the project owner's statement that v2 had *less finished functionality* than v1 despite better architecture: the create-wizard's `getCreationStages()` definitions read like a finished spec of an intended flow that was never actually hooked up to a command a player could type.
- **git-history signal (v2, `2025/01/Hibernate-update` currently checked out on disk but files read here are identical to `main` — confirmed via `git diff main -- Gate.java` returning empty)**:
  - Branch `ImprovedCreationArchitecture` (last commit 2022-12-16, never merged into `main`, and **not** an ancestor of `2025/01/Hibernate-update` either) began a ground-up rewrite of the Creation engine into "CreationV2" classes, then was explicitly abandoned: `git show -s --format=%B fafb229` → *"Stashing this branch in favour of modifying the existing Creation architecture."* A dead-end fork.
  - Branch `CreationArchitecture2` diverges from `main` at commit `400e5c8` (the newest commit `main` has that touches `model/dominion`) and continued for 19 more commits (last touched 2023-10-26) fixing exactly the machinery this spec covers: `da4383f` — *"Fixed persistence errors for CreationStageSelect and its selection objects... One known bug is still present: When retrieving a stashed Creation with a CreationStageSelect instance that already has been completed... the stage message doesn't detect the already selected results and says the stage is not yet completed."* `CreationStageSelect` is exactly the stage type used for Gate's street/material pickers and District's town picker (`v2:...Gate.java:1017-1023,1052-1055`, `v2:...District.java:275-280`). **This means the version of `CreationStageSelect` that shipped on `main` has a known, developer-acknowledged, never-fixed persistence bug in resuming a stashed selection stage** — the fix only exists on the unmerged branch.
  - `CreationArchitecture2` **is** an ancestor of `2025/01/Hibernate-update` (confirmed via `git merge-base --is-ancestor`), so that fix did eventually get carried forward into later work — just never back into `main`. `Hibernate-update` itself ends in an explicitly broken state per its own commit messages: `4f99eb5`/`ce69ebc` — *"Has major errors and does not run!"*, and `b7592a0` — *"There still are many runtime errors but API and Web App are more important now."*
  - Net effect: the most-refined version of this exact Town/District/Gate creation-stage machinery lives only on a branch chain that was never merged back to `main`, and whose current tip does not run.
- **Conclusion**: the Data model and the creation-*stage definitions* are close to finished in v2 and represent a real architectural improvement over v1. The actual end-to-end player-facing creation workflow, and the fix for a known bug in the shared select-stage component, are not present in the `main` line of v2 that this document (and presumably any earlier player-facing deployment) is based on.

## v1 vs v2 differences

- **Persistence**: raw JDBC scattered across static-method "DAO-ish" interfaces, with an in-memory duplicate POJO layer for the newer District/wizard features (v1) → proper Hibernate `@Entity` classes in a single `Dominion`-rooted `InheritanceType.JOINED` hierarchy, cached via a `RepositoryManager` (v2).
- **District**: did not exist as a first-class, region-owning concept in v1's original system — only appeared via the later, parallel Models-layer rewrite (with an explicit District ⊆ Town spatial check). v2 promotes District to a full `Dominion` subclass with its own WorldGuard region and `ManyToOne` to Town, but drops the spatial containment check that v1's own wizard had.
- **Street**: v1 Street belongs to exactly one Town (`TownID`, with `1` used as a "no town / wilderness" sentinel) and never owns a region. v2 Street is a standalone entity with **no** Town reference at all, related to zero/one/many Districts via `@ManyToMany` — a genuine conceptual shift from "street inside one town" to "street crossing multiple districts/towns".
- **Region shape**: always axis-aligned cuboids in v1 vs arbitrary WorldEdit polygons in v2 — towns/districts/gates/warehouses can be non-rectangular in v2.
- **Gate mechanics**: v1 = one region + one block material, animated as a simple material swap layer-by-layer. v2 = two independently captured block-state snapshots (open/closed), supporting arbitrary multi-material patterns (e.g. a drawbridge), with the animation logic extracted into a reusable `GateAnimationUtil` rather than inlined in the entity.
- **Gate features only in v2**: Siege-minigame override with defender damage immunity, continuous fire damage-over-time from `FIRE_ASPECT`/`ARROW_FIRE`, and an explicit `INTERACT=allow` WorldGuard flag on the gate's own region.
- **Commands**: v1 uses hand-rolled `CommandExecutor implements onCommand(String[] args)` parsing with magic argument indices. v2 uses the `co.aikar.commands` framework with annotated, permission-checked, tab-completed subcommands — a real upgrade in robustness, but in the process v2 **lost the working end-to-end "create" entry point** that v1's `/town2 create`, `/district create`, and `/structure create <type>` provided (see Finished vs WIP).
- **Session durability**: v1 creation sessions stash in-memory for a hardcoded 5 minutes and are lost on restart; v2 creation sessions (`Creation`/`CreationStage`) are themselves persisted entities, stashable for up to 24 hours and resumable across a restart — though with the acknowledged, never-merged-to-`main` `CreationStageSelect` resume bug noted above.
- **Ownership/permission model**: functionally unchanged — neither version has a Town/District "owner" ACL; both rely purely on static Bukkit permission nodes.

## Open questions

- **Was v2's "create a new Town/District/Gate/Street/Warehouse" flow ever actually exposed to players** through some mechanism not present in this source tree (a since-removed command, an external/web admin tool, direct DB inserts in production), or was it genuinely never finished end-to-end? This is the single most important open question raised by this research: it determines whether v3 should treat v2's `getCreationStages()` definitions as a faithful, battle-tested spec of a real flow, or as an unfinished design that needs fresh UX judgment.
- Should v3 enforce real spatial containment (District physically inside its Town's region, Gate/Structure physically inside its Street's District/Town) — something neither version fully implements end-to-end (v1 had it only for District, v2 has it nowhere)?
- Should v3's Street model follow v1 (belongs to exactly one Town) or v2 (crosses many Districts, Town only derived transitively)? These are materially different concepts sharing one class name across versions — the project owner's intent for "what is a Street" needs to be decided explicitly rather than assumed.
- Is a real ownership/ACL model intended for Town/District (e.g. a "mayor" role that can manage entry, invite members, edit description) — not found in either codebase, only blanket staff permission nodes?
- For Gate open/close in v3: is the v2 approach (capture two full block-state snapshots, open and closed, and swap between them) the desired mechanic going forward, given it requires an admin/builder to physically construct both states once? Or would a simpler schematic/WorldEdit-clipboard-based approach, or a pure WorldGuard-flag-based approach (interact/entry toggling with no block changes) be preferable?
- Was the "non-members can't enter" entry-group flag in v1 Town/District creation ever meant to work (it's currently a no-op — see Known edge cases), and is that kind of member-list-gated entry a feature v3 should actually implement?
- The `CreationStageSelect` persistence bug documented and fixed only on the unmerged `CreationArchitecture2`/`2025/01/Hibernate-update` branches (stashed-and-resumed select stages don't detect already-selected values) — should v3's equivalent "pick one of N existing objects" creation step be designed to sidestep this class of bug (e.g. by not supporting long-lived stash/resume for selection steps, or by handling it differently)?
