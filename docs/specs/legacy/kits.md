# Kit system

Source-mined spec for the legacy "Kit" feature across `v1` (single-commit Bukkit plugin) and `v2` (Hibernate/MySQL, 196 commits on `main`). See `docs/specs/legacy/README.md` for the mining principles this doc follows (verbatim-only, annotated, gaps marked, no invention).

## Data model

**v1** — there is no persisted "Kit" entity. `v1:src/Kits/Kit.java` is the *only* file in its package: a stateless helper class with one method, `starterKit(Player target)`, that hardcodes two literal product names ("beginnersword", "steelaxe") and resolves them at call time through `Products.Product`. No fields, no table, no config file, no name/description — "the kit" is not a data object, it's a code path.

**v2** — `Kit` is a full Hibernate `@Entity` (`v2:src/main/java/net/knightsandkings/model/item/kit/Kit.java:50-51`), persisted via the generic Repository system (implements `IPersistent<Integer>`), listable/displayable in generic menus (`IDisplayable<Integer>`), and editable through the generic multi-stage "Creation" wizard (`ICreatable<Integer>`). Fields:
- `id` (`int`, `@Id`)
- `name` (`String`)
- `description` (`List<String>`, `@ElementCollection` into a separate `item_description` table)
- `helmet`, `chestplate`, `leggings`, `boots`, `hand` — each `@OneToOne` to `Item`, `nullable = false` (`v2:.../Kit.java:103-125`)
- `shield` — `@OneToOne` to `Item`, `nullable = true` (`v2:.../Kit.java:119-121`)
- `contents` — `@ManyToMany` to `Item` via join table `kit_contents` (columns `kit_id`/`item_id`), `cascade = { CascadeType.ALL }` (`v2:.../Kit.java:127-132`)

No cooldown field, no "claimed by" / usage-tracking field, no rank/donator-tier field exists on the entity in either version.

## Business rules and behavior

**v1 — automatic, hardcoded, single starter kit.** `starterKit(Player target)` puts a "beginnersword" in the player's hand and adds a "steelaxe" to their inventory (`v1:src/Kits/Kit.java:14-19`), each resolved via `Product.getProductID(name, false)` → `Product.createPropertyItem(id, 1, false, false)`, which is itself backed by a SQL `Products` table (item stats/material/enchants looked up by row, not embedded in the kit code). This is triggered automatically, not via any command or menu — traced the real caller chain: `PlayerListener.OnJoin` (`v1:src/Listeners/PlayerListener.java:222`) and `PlayerListener.OnMove` (`v1:src/Listeners/PlayerListener.java:437`) both call `Users.newPlayer(player)` (`v1:src/Users/Users.java:417-467`), which — after teleporting the player, showing welcome titles, and starting the intro tutorial — calls `kit.starterKit(player)` as its last real step (`v1:src/Users/Users.java:467`). There is no `/kit` command, no kit menu entry, and no permission node anywhere in v1 for kits — a case-insensitive, `bukkit`/`toolkit`-filtered grep of the entire v1 `src/` tree turns up only `Kits/Kit.java` itself and its three call sites (`Users.java`, `JoinEvents.java`, and the dead-code duplicate in `Users2.java` below).

**v2 — full multi-kit system, pull-based only.**
- *Definition*: a Kit's fields are set through the Creation wizard (`getCreationStages`, `v2:.../Kit.java:423-479`): name (mandatory string), description (optional string), helmet/chestplate/leggings/boots/hand (each a mandatory single-`Item` select), shield (optional single-`Item` select), contents (mandatory-flagged multi-select, up to 10 additional `Item`s per stage call).
- *Granting* (`assignKit(User user)`, `v2:.../Kit.java:391-416`): sets the player's helmet/chestplate/leggings/boots armor slots directly; puts `shield` in the off-hand if set; puts `hand` in the main hand (quantity 1 if `hand.getCategory().getName()` equals "weapons", else 32); then `addItem`s every entry in `contents` (quantity 32, or 64 specifically if the item's name equals "arrow" case-insensitively, or 1 if its category is "weapons"). Sends the player a "You received kit `<name>`" message. No cooldown, no re-claim guard — `assignKit` is idempotent-unsafe and can be called any number of times.
- *Two independent grant paths*:
  1. Commands `/kit get` (self) and `/kit give <user> <kit>` (staff-to-other) — `v2:.../spigot/command/item/KitCommand.java:161-205`.
  2. Menu: `/menu` → "Kits" (`KitOverviewItem`) → `KitOverview` list → click a `KitSelectItem`, whose `onClick` calls `kit.assignKit(this.getMenu().getTarget())` directly with no confirmation step (`v2:.../model/menu/kit/KitSelectItem.java:100-108`).
- *Permission logic, command path*: **per-action, not per-kit, and not rank/donator-tiered.** `KitCommand` has a class-level `@CommandPermission("k&k.item.kit")` (`basePerm`), but every subcommand overrides it with its own node: `.list`, `.fetch`, `.save`, `.remove`, `.edit`, `.give`, `.get`, `.test` (`v2:.../KitCommand.java:26-219`, e.g. `.get` at line 188, `.give` at line 163). So "which kit" is never permission-gated — only "which action" is. Nothing in code differentiates by player rank or donator status. `v2:src/main/resources/plugin.yml:50-51` registers only the command alias `kit` → base permission `k&k.item.kit`; the file has no top-level `permissions:` block at all, so no default values, descriptions, or donator-group wiring exist anywhere in this repo — any tiering would have to live entirely in an external permissions-plugin config not present here.
- *Permission logic, menu path*: opening `/menu` at all requires only the single blanket node `k&k.menu.menu` (`v2:.../spigot/command/menu/MenuCommand.java:36-37`). Once inside, `KitOverviewItem`, `KitOverview`, and `KitSelectItem.onClick` apply **no permission check whatsoever** before calling `assignKit` (`v2:.../KitSelectItem.java:101-104`) — the granular `k&k.item.kit.get` node that gates the command equivalent is not consulted at all on this path. See bug #3 below.

## Known edge cases / bugs

1. **Clearly a bug (v1).** `PlayerListener.OnMove` re-invokes `Users.newPlayer(player)` — and therefore `kit.starterKit(player)` — on *every* `PlayerMoveEvent` as long as the player's UUID is still in the `newPlayers` set (`v1:src/Listeners/PlayerListener.java:437-438`). That set entry is only cleared by a task scheduled `3*20` ticks (3 seconds) later, from *inside* `Users.newPlayer` itself (`v1:src/Users/Users.java:471-477`). Any new player who so much as looks around during that 3-second window fires `PlayerMoveEvent` repeatedly, so the starter kit (sword + axe) gets duplicated into their inventory many times over before the cleanup task runs.
2. **Clearly a bug (v2).** `KitCommand` registers the alias `"g"` for *two different* subcommands at once: `@Subcommand("give|g")` on `onGive` (`.give` permission, `v2:.../KitCommand.java:161`) and `@Subcommand("get|g")` on `onGet` (`.get` permission, `v2:.../KitCommand.java:186`). `/kit g` is an ACF registration collision — ambiguous at best, one subcommand silently shadowing the other at worst.
3. **Likely a bug (v2).** The menu-based grant path bypasses kit permissions entirely: `KitSelectItem.onClick` calls `kit.assignKit(...)` with zero permission check (`v2:.../KitSelectItem.java:101-104`), while the functionally equivalent `/kit get` command is gated by `k&k.item.kit.get`. Any player able to open `/menu` (gated only by the blanket `k&k.menu.menu`) can obtain any kit for free, repeatedly, regardless of the finer-grained `k&k.item.kit.*` permissions.
4. **Likely a bug (v2).** `Kit.contents` is `@ManyToMany(cascade = { CascadeType.ALL })` against the shared `Item` entity (`v2:.../Kit.java:127-132`). `CascadeType.ALL` includes `REMOVE`; since `Item` rows are shared across shops/storages/other kits/etc. (it's a general item-catalog entity, not kit-owned), deleting or certain persistence operations on a `Kit` risk cascading a delete into `Item` rows still referenced elsewhere. Notably inconsistent within the same class: the single-slot equipment relations (`helmet`/`chestplate`/`leggings`/`boots`/`shield`/`hand`) are plain `@OneToOne` with no `cascade` attribute at all (`v2:.../Kit.java:103-125`), so only the `contents` list carries this risk.
5. **Might be intentional, unclear (v2).** `assignKit()` dereferences `getHelmet()`, `getChestplate()`, `getLeggings()`, `getBoots()`, `getHand()` with no null checks (`v2:.../Kit.java:395-404`), relying entirely on the DB schema's `nullable = false` and the Creation wizard's `mandatory = true` stages to guarantee non-null values. There's no defensive check at the point of use, so any Kit row created or edited outside the wizard (direct DB edit, partial data migration) would NPE on grant. `shield` is the one slot handled defensively (`if (this.getShield() != null)`, line 399), consistent with it being the only `nullable = true` slot — so the *pattern* looks intentional, just not defensively coded.
6. **Likely a bug (v1).** `Kit.starterKit()` resolves item ids via `Product.getProductID("beginnersword", false)` / `getProductID("steelaxe", false)`, which returns `null` (not an exception) if the named row is missing from the `Products` table (`v1:src/Products/Product.java:132-158`). That `null` then flows into `createPropertyItem` → `getitemTypeID(productID, ...)`, which does `stmt.setInt(1, productID)` on a `PreparedStatement` (`v1:src/Products/Product.java:367`) — unboxing a null `Integer` throws an uncaught `NullPointerException` (only `SQLException` is caught in that method). If either hardcoded product name is ever absent from the `Products` table, the exception propagates up out of the join-flow's kit-granting step with no handling.
7. **Might be intentional, unclear (both versions).** Neither version has any cooldown, expiry, or "already claimed" tracking on kits. In v2 this makes `/kit get` and the Kits menu both freely repeatable — the same kit can be re-claimed at will, indefinitely. Could be intended as a "try on / reset loadout" tool, or could be a gap versus an intended one-time/cooldown-gated design.
8. **Might be intentional, unclear (v1).** Uses the legacy `player.getInventory().setItemInHand(...)` call (`v1:src/Kits/Kit.java:16`) rather than `setItemInMainHand`; harmless on whatever Bukkit/Spigot version this targeted, just a sign of the code's vintage — not something to port forward literally.

## Finished vs work-in-progress

**v1** is genuinely minimal — a single method in a single file, not a "system" by any reasonable reading. It *is* fully wired (confirmed real, non-dead caller chain: `PlayerListener` → `Users.newPlayer` → `Kit.starterKit`), so within its own tiny scope it "works," but that scope is: one non-configurable, two-item starter kit, no persistence, no command, no menu, no permission gate. Do not read more design intent into it than that — this really is one of the thinnest systems in the legacy code, per the task brief, and the code confirms it.

Side finding while tracing v1 callers: `DataManager/Users2.java` contains a near-duplicate static `NewPlayer(Player)` method (its own `Kit kit = new Kit(); ... kit.starterKit(player);`, `v1:src/DataManager/Users2.java:217-262`) that has **zero callers anywhere** in the codebase (only its own definition matches a case-sensitive grep for `NewPlayer(`) — dead/orphaned duplicate left over from what looks like an incomplete `Users` → `Users2` refactor. It is not part of the live kit flow, but it shows the kit-granting call was copy-pasted mid-refactor and then abandoned in one of the two copies.

**v2** is comparatively complete and clearly the more developed of the two for this specific feature:
- Full CRUD + operational command surface (`list/fetch/save/remove/edit/give/get`), a Creation-wizard-driven kit editor, a browsable equip-from-menu UI, and real Hibernate persistence — none of which exist in v1.
- `git log --oneline -- .../Kit.java` on v2 `main` (196 commits total, HEAD at 2022-12-22) shows commits touching `Kit.java` spanning nearly the whole project history, with the last one (`c570dae`, "Revert 'Improved Creation Stage Select class'", 2022-12-21) landing the day before the branch's final commit — i.e. `Kit.java` was still being actively touched at the very end of the repo's recorded history, not abandoned early.
- `git log --all --oneline -- .../Kit.java` (and the other kit-related files: `KitCommand.java`, `KitOverview.java`, `KitSelectItem.java`, `KitOverviewItem.java`) returns the *same* commit set as `main` plus only generic, cross-cutting refactor commits reachable from other branches (Java 21 upgrade, DAL package renaming, an Eclipse "clean" pass). There is no Kit-specific work stranded exclusively on an unmerged feature branch (e.g. `ImprovedMenus`, `CreationArchitecture2`) — unlike some other v2 subsystems, this feature's whole development history lives in mainline.
- `KitOverviewItem` (the `MainMenu` entry point) was last touched 2021-02-11 and never changed again — old and static, but still a real, wired entry point present in `MainMenu.createMenu()` (`v2:.../model/menu/main/MainMenu.java:51`), not dead code.
- One piece of clutter: `KitCommand.onTest` (`v2:.../KitCommand.java:207-219`) computes `Math.log()` of a number and has no connection to kits whatsoever — a harmless leftover ACF debug scratch command in an otherwise clean command class.
- Overall: v2's kit system is one of the more finished, actively-maintained pieces of that codebase. Its problems (menu permission bypass, duplicate subcommand alias, risky cascade) read as inherited bugs in otherwise-complete code, not as missing/unfinished pieces.

## v1 vs v2 differences

- **Architecture.** v1: hardcoded, stateless, single-purpose helper tied to two literal product-name strings. v2: persisted Hibernate entity, arbitrary number of named/describable kits, editable at runtime via the generic Creation wizard, resolved/listed through the generic Repository system.
- **Item composition.** v1 grants exactly two fixed items (sword to hand, axe to inventory), no armor. v2 models a full equipment loadout (helmet/chestplate/leggings/boots/shield/hand) plus an arbitrary bonus "contents" item list, with category-aware stack sizing (weapons=1, arrows=64, everything else=32) — a capability v1 has no equivalent of.
- **Trigger surface, and a real functionality drop.** v1's kit-granting is automatic-only (on first join), with no command, no menu, no permission. v2 replaced this with pull-based access only (`/kit get`/`/kit give` or the menu) — a targeted, case-insensitive `Kit` grep across the entirety of v2 `src/main` (filtered for `bukkit`/`toolkit` false positives) found no listener anywhere that grants a kit automatically on `PlayerJoinEvent` or first join. The v1 "starter kit on first join" behavior was **never reimplemented in v2**. This is a concrete instance of the project owner's stated observation that v2 had less functionality actually finished than v1 — for this specific system, it's not "less finished," it's "the automatic-grant feature was dropped and not replaced."
- **Permissions.** v1 has none at all for kits. v2 added a real (if imperfectly enforced — see bug #3) permission model, scoped per command-action under `k&k.item.kit.*`.
- **Persistence.** v1's kit is never itself persisted — it's just two live `Product` table lookups on every join. v2 kits are full DB rows with Hibernate-managed relationships (including a risky cascade) to the shared `Item` entity.

## Open questions

1. **(Most important)** v2 dropped the automatic starter-kit-on-join behavior entirely — nothing in v2 grants any kit on first join, unlike v1's `PlayerListener.OnJoin`/`OnMove` → `Users.newPlayer` → `Kit.starterKit()` chain. Was this an intentional design shift (fully opt-in `/kit get`/menu access only), or unfinished migration work that simply never got carried over? This determines whether the v3 rebuild needs a "default kit granted on first join" feature at all.
2. Was the menu path's total bypass of kit permissions (`KitSelectItem.onClick` → `assignKit` with no permission check at all, versus `/kit get`'s `k&k.item.kit.get` gate) intentional — e.g. "anyone who can reach `/menu` should be able to freely try any kit" — or a bug? This decides whether v3 needs permission checks inside menu/UI click-handlers, not just command handlers.
3. Was rank/donator-tiered kit access ever a real intended requirement? No code in either repo implements it — permission is flat and action-scoped, entirely dependent on an external permissions-plugin config that isn't present in either repo. Worth confirming with the project owner whether "donator-exclusive kits" was a real product goal that never got built, or was never intended in the first place.
4. Is the fully repeatable, uncapped nature of kit granting (no cooldown, no one-time-only flag, in either version) intentional — a loadout-preview/reset tool — or a gap? Relevant to whether v3 needs claim-tracking or cooldowns on kits.
5. Should the `kit_contents` cascade-delete risk (`CascadeType.ALL` on a `@ManyToMany` to the shared `Item` entity, edge case #4 above) be treated as a historical bug to explicitly avoid repeating in v3's data model for any entity that references shared/reusable items (kits, shops, storages, etc.)?
