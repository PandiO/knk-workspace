## Ordering: Item 4 → 5 → 6 → 7

This is the order proposed, and it holds up against the dependency graph:

- **Item 4 first** — fully independent of the other three, small, and already fully decided (a single frontend fix in `normalizeFormSubmission.ts`). Doing it first matters practically, not just because it's easy: items 5 and 6 both involve repeatedly editing/saving gate configs and running scans during development, which hits this exact save-after-scan bug constantly if left unfixed. Fixing it first keeps the rest of the work friction-free.
- **Item 5 second** — this was already decided at the 2026-09-11 planning meeting: item 6's region data must land on the new `GateDoor` entity directly, or it needs a second migration later. Beyond that explicit dependency, item 5 also reshapes the animation engine's iteration model (from "one block list per structure" to "one block list per door"), which item 7 touches too — see below.
- **Item 6 third** — builds directly on `GateDoor` from item 5 (region capture, per-door state). It's also the largest, least-defined item (the rotation-rasterizer generalization and the round-trip WorldEdit-editing design are both explicitly unsized/undesigned as of the feasibility assessment), so it needs the foundation under it to be stable first.
- **Item 7 last** — the snow-layer fix hooks into the block-movement/placement code path (`GateAnimationTask`/`GateBlockPlacer`) that both item 5 (per-door iteration) and item 6 (region-based scanning, generalized rotation rasterization) substantially rewrite. Implementing it last means writing the snow-removal check once, against the final code shape, instead of writing it now and re-verifying/adapting it twice as 5 and 6 land.

**B. Structure-level override mechanism: nullable override fields, resolved at read time — not a write-cascade**

This resolves the previously-open design question from the original backlog item (item 5, "still open" #4: concrete design for the force-state cascade). Rather than looping over every child door and writing N rows (fragile, non-atomic, awkward to undo), every overridable field above gets a matching **nullable** field on `GateStructure` (e.g. `IsActiveOverride: bool?`, `HealthDisplayModeOverride: GateInfoDisplayMode?`). The *effective* value used everywhere at runtime — animation engine, display, command responses — is `structureOverride ?? door.OwnValue`. Setting an override is a single-row write on `GateStructure`; clearing it (`null`) instantly reverts every door to its own value, no per-door cleanup needed. This also makes the future Siege "capture destroys all doors" case cheap and atomic: set `IsDestroyedOverride = true` once, and every door's effective state reads as destroyed without writing to each door row.

**C. `OpenedState`: replace the `IsOpened`+`IsJammed` booleans with one persisted enum**

Recommendation: **yes, an enum is the better model.** Two concrete findings support this:
- The plugin already has an in-memory `AnimationState` enum (`knk-core/.../domain/gates/AnimationState.java`) with `CLOSED, OPENING, OPEN, CLOSING` — the animation engine already thinks in these terms; the DB just doesn't persist that granularity today, only a flat `IsOpened` bool plus a separate, currently shallow `IsJammed` bool (verified: `IsJammed` is only touched in `CachedGate.java` today, not woven into the animation state machine anywhere else).
- Two independent booleans allow nonsensical combinations (`IsOpened=true` *and* `IsJammed=true` simultaneously) that a single enum makes structurally impossible.

Add a new persisted `GateDoorOpenState` enum: `CLOSED, OPENING, OPEN, CLOSING, JAMMED` (mirrors `AnimationState` plus `JAMMED` as its own distinct state — a jammed door isn't cleanly "open" or "closed," it's stuck mid-motion). This replaces both `IsOpened` and `IsJammed` on `GateDoor`. Whether the existing in-memory `AnimationState` gets retired in favor of this richer persisted enum, or kept as a plugin-internal "currently animating" detail synced from it, is an implementation decision for 5.4/5.5, not something to lock in here.

**D. New: `GateDoor.Name` + door-name display**

- New `Name` field on `GateDoor` (string), unique **within its parent `GateStructure`** (not globally) — enforce via a unique index/service-level check scoped to `GateStructureId`.
- Enables name-based command addressing: `/knk gate open <gateStructureName|gateStructureId> <gateDoorName|gateDoorId>` — the command resolver needs to accept either an id or a name at both levels.
- New `DoorNameDisplayMode` field on `GateDoor` (reuse the existing `GateInfoDisplayMode` enum type, same as `GateNameDisplayMode`/`StatusDisplayMode`), toggling whether the door's own name line shows in its hover.
- Each door's hover combines structure + door info, e.g.:
  ```
  <GateStructureName>
  <GateDoorName>
  <GateDoorHealthCurrent>
  <GateDoorOpenedState>
  ```
  each line gated independently by its own (possibly structure-overridden) display-mode setting.

Fixed by adding `ChildFormState.persistIndependently` (set only when `parseListFieldSettings(field.settingsJson).ownedChildCollection` is true, so the architecturally separate many-to-many "create related entity" flow - `ManyToManyRelationshipEditor`'s own `ChildFormModal` instance, which already persists correctly through its own path - can't be double-persisted by this change) and calling the entity's own `getCreateFunctionForEntity`/`getUpdateFunctionForEntity` before applying the result to local state, inside the existing try/catch so a persistence failure still blocks the success path. New/updated test: `FormWizard.listCreateNew.ui.test.tsx` (asserts the create function is called once per new door, update is never called, and the list ends up holding the *persisted* entity - not the pre-save draft data). Full suite re-confirmed at the same 16-failure/10-suite baseline. Committed as `knk-web-app` `70a9e7e`.
- **Follow-up bug found and fixed (2026-09-13, same day)**: `GateDoor`'s "Activate gate immediately" checkbox never actually set `IsActive` to `true` on the created entity, no matter what the admin did - and, confusingly, it *rendered* pre-checked from the start. Fixed with a shared `toBooleanFieldValue()` helper (`src/utils/forms/booleanFieldValue.ts`) used by both `BooleanField`'s `checked` prop (rendering) and `normalizeScalarValue`'s Boolean branch (submission), so the two can no longer disagree with each other. ### 6.8 — Fix: orphaned "stuck" blocks under multi-frame skips

✅ Done 2026-09-16, `knk-plugin` commit `dcd787e`. Implemented exactly per the plan below. **Not yet confirmed live** - the user was away from the server at implementation time and will retest once back.

**Root cause, precisely**: `updateGateBlocks` derives what to vacate from arithmetic (`previousFrame = frame ± tickRate`), not from what was actually placed last time. `currentFrame` itself comes from wall-clock elapsed time, not a per-call counter, so it can jump forward by many frames between two `run()` invocations if the main thread stalls. When that happens, only the one `tickRate`-step-back position gets vacated; every frame in between is never targeted for removal by anything - `transitionRestingFrame` (called at completion) only diffs the two *resting* frames (0 and `animationDurationTicks`), so it has no visibility into mid-swing positions either. Compounding this, `gate.setCurrentFrame(currentFrame)` (`GateAnimationTask` `run()`, before `updateGateBlocks` is called) overwrites the gate's remembered frame before the vacancy calculation can use it.

**Implementation plan** (`GateAnimationTask.java`, `net.knightsandkings.knk.paper.gates` package, no domain/DB/API changes):

1. Add `private final Map<Integer, List<GateRestingFramePlacer.RestingCell>> lastPlacedCellsByGate = new HashMap<>();` - per animating gate, the actual (position, blockdata) cells its `BlockSnapshot`s occupied after the last successful `updateGateBlocks` call. `RestingCell` is already package-visible from `GateRestingFramePlacer`; the existing private `BlockPlacement` record in `GateAnimationTask` is structurally identical and can be replaced by it, removing a near-duplicate type.
2. In `updateGateBlocks`, build `targetCells` as a `List<RestingCell>` (today's `placements` list, retyped).
3. Resolve what to vacate: `previousCells = lastPlacedCellsByGate.get(gate.getId())`; if present, use it as-is (the real set, however many frames were actually skipped to get here). If absent (first call since this animation - or server - (re)started), fall back to exactly today's `previousFrame`-based computation once, to seed it - correct precisely because a fresh animation's first "previous" position genuinely *is* the resting position, so there is nothing to have skipped yet.
4. `List<RestingCell> toVacate = GateRestingFramePlacer.cellsToClear(previousCells, targetCells);` - reuse the existing, already-tested pure diff helper (same package, package-private, already does exactly "positions in `from` absent from `to`") instead of hand-rolling a second copy of this logic.
5. Vacate/place loops keep their current mechanics (`GateBlockPlacer.removeBlockIfMatches`/`placeBlockIfVacant`), just iterating `toVacate`/`targetCells` instead of today's `vacancies`/`placements`.
6. `lastPlacedCellsByGate.put(gate.getId(), targetCells)` after a successful pass - becomes next tick's `previousCells`.
7. Clear the gate's entry in `run()`'s existing "gate stopped animating" branch (`state != OPENING && state != CLOSING`, alongside the existing `emptySnapshotWarnings.remove(gate.getId())`/`jamTickCounters.remove(gate.getId())`) - a completed animation's `transitionRestingFrame` already fully reconciles the world, so nothing needs to survive to the next animation; the next start correctly re-seeds via step 3's fallback.
8. Spatial index: replace the per-block `BlockMove`/`spatialIndex.move(...)` loop with `spatialIndex.removeAll(gate.getWorldName(), <positions from toVacate>)` followed by `spatialIndex.putAll(gate.getWorldName(), <positions from targetCells>, gate.getId())` - both already exist and are used identically, in bulk, by the existing `resyncSpatialIndex`. A full remove/add-by-position is correct regardless of how the previous and next sets relate, unlike the per-block move-pairing it replaces, which implicitly assumed exact 1:1 correspondence (the `moves`/`BlockMove` list and record can then be deleted).

**Deliberate exclusion - why `lastPlacedCellsByGate` must NOT be seeded from the full resting-frame reconstruction**: `GateRestingFramePlacer.restingFrameCells` at a resting frame can include Mechanism 1's rasterized filler cells (or, after 6.9 below, the full open-scan list) - both of which are designed to persist untouched for the *entire* swing and only get reconciled at the far end by `transitionRestingFrame`'s own separate diff (`ROTATION_GAP_FILL_DESIGN.md` Decision 3: "only apply at resting frames, never mid-swing"). If step 3's seed included those cells, the very first swing tick's diff would immediately vacate them (they're absent from `targetCells`, which is real-`BlockSnapshot`-only), silently changing that already-intended persistence as an unrelated side effect. Seeding only from the existing per-`BlockSnapshot` fallback computation (exactly what today's code already computes) avoids this entirely.

A new `GateAnimationTaskTest` (first for this class) can then verify directly: given a `remembered` set representing a multi-frame-skip scenario (cells far from both `fallback` and `targetCells`), the result vacates the *remembered* stale cells, not just the naive one-frame-back guess - the actual bug this fix closes.

### 6.10 — Fix: rigid mid-swing motion (uniform transform)

🔶 Implemented and unit-tested (2026-09-16), then live-tested 2026-09-17 - **found insufficient, superseded in part by item 6.11 below.** Kept in place, not rewritten, so the reasoning trail stays intact: this section explains what was built and why it looked sufficient at the time; 6.11 explains what live testing actually found and what changed as a result. Decision and full rationale: **Decision 7**, [ROTATION_GAP_FILL_DESIGN.md](./ROTATION_GAP_FILL_DESIGN.md) — this section is the implementation plan for that decision; see 6.7's "Fourth round" above for the diagnostic evidence that led to it. **What live testing found**: the uniform-transform-only formula jammed entity 14's animation outright at frame 89/90 (a paired block's transform-predicted destination landed 5.7 blocks from its real position, colliding with a genuinely open-only block's correct position) - not just the smaller "loses exactness for an outlier block" trade-off Decision 7 anticipated. Full evidence and the resulting decision to build the hybrid: **Decision 8**, [ROTATION_GAP_FILL_DESIGN.md](./ROTATION_GAP_FILL_DESIGN.md).

**Root cause (recap, full evidence in 6.7's Fourth round)**: `GateFrameCalculator.calculateBlockPositionBreakdown`'s `ROTATION` branch adds a per-block correction term (`(openTarget - arcPosFinal) * progress`) on top of the rigid rotation arc, sized independently per block via `GateBlockPairing`'s nearest-neighbor match. Optimal total-distance matching doesn't make neighboring blocks' corrections agree, so the door doesn't swing as one rigid piece. Confirmed unrelated to `GeometryDefinitionMode`.

**Chosen approach (Decision 7, option 1)**: replace the per-block correction with a single best-fit rigid rotation+translation, computed once per door load and applied uniformly to every block's mid-swing position.

1. **Fit the transform once, at load time** (`GateLoaderAdapter`, alongside the existing basis/pairing precompute): given the closed/open point correspondences `GateBlockPairing.pairNearestNeighbor` already produces, solve for the rotation matrix `R` and translation `t` that best map paired closed points onto their open counterparts in a least-squares sense (Kabsch/Procrustes: center both point sets on their centroids, compute the cross-covariance matrix, SVD it, recover `R` from `U·Vᵀ` with the standard reflection-correction check, then `t = openCentroid - R·closedCentroid`). Store on `CachedGateDoor` alongside the existing per-door geometry fields. Degenerate-input handling needed: fewer than 3 non-collinear pairs (fall back to today's pure procedural rotation - nothing to fit), and the reflection case (`det(R) < 0`, fixed by negating the SVD's last singular vector before recomposing `R`, the standard Kabsch correction).
2. **Mid-swing position for every block with a fitted transform available**: replace `calculateRotationPosition`'s destination-only role for Mechanism-2-paired blocks with a blend between the existing procedural rotation arc and `R·relativePos + t`'s equivalent open-side position - the *shape* of the blend (arc as the base motion, something converging to the true open position by `progress=1`) is unchanged from today's formula; only what it converges toward changes, from a per-block nearest-neighbor target to the one shared transform's prediction. Every block gets the *same* transform, so no two neighbors can disagree.
3. **Open-only blocks (no closed-side pairing) get animated for the first time**: synthesize a closed-side start point by applying `R⁻¹`/`Rᵀ` (rotation matrices are orthogonal, so the inverse is the transpose) and `-t` to the block's real open-scan position, then run it through the same blend as step 2. This directly fixes the "open-only blocks pop in at the last tick" behavior item 6.9 explicitly accepted as a trade-off rather than fixed.
4. **`GateRestingFramePlacer` is unchanged.** Both resting frames continue to place exact scanned positions/blockdata verbatim - this was already true before this fix and stays true after it; only the mid-swing interpolation changes. This is also how multi-material support and closed/open shape-or-dimension mismatches stay fully intact under this change (see Decision 7's rationale) - neither one is a property of the swing formula.
5. **`GateBlockPairing` stays, repurposed**: still used to produce the closed/open correspondences the fit in step 1 needs, but no longer used to decide any individual block's mid-swing *destination* - that's now the shared transform's job.

**Explicitly not built now (Decision 7's deferred hybrid)**: a residual correction on top of the shared transform, sized per-block relative to the transform's own prediction (so a genuinely rigid block gets ~zero residual, and only a true outlier - e.g. a hand-built open-state addition with no rotational relationship to the closed shape - gets a small individual nudge). This is the version that gives up nothing at all from Mechanism 2's original per-block-exactness intent, at the cost of open design questions (residual sizing/tapering, avoiding reintroducing today's disagreement in a smaller dose) not worth resolving before shipping a clean-looking fix. Revisit if a future door's live testing shows a global rigid fit visibly failing for some of its blocks - Decision 7 has the full writeup so that work doesn't start from scratch.

**Tests** (pattern-matching 6.8/6.9's precedent of extracting pure, Bukkit-free logic):
- Kabsch fit helper: exact recovery of a known synthetic rotation+translation from perfect correspondences; the reflection-correction path (a deliberately mirrored input); the degenerate-input fallback (0, 1, 2, and 3-collinear-point cases).
- `calculateBlockPositionBreakdown`-equivalent blend: `progress=0` still returns the closed position exactly; `progress=1` still returns the real scanned open position exactly for both a previously-paired block and a previously-unpaired one; intermediate frames are a deterministic function of the shared transform (not the old per-block target).
- Regression: a gate with no open scan at all, or too few pairs to fit, is byte-for-byte unchanged from today's pure procedural rotation.
- Live verification: re-run entity 14's REGION-mode open/close cycle, confirm the swing reads as visually rigid (no adjacent-block correction disagreement) and all 49/32 resting-frame blocks are still exactly correct (no regression on 6.8/6.9's fixes).

Implemented exactly as planned above, with one addition the original plan didn't call out precisely (see below):

- **New `RigidTransform` (`knk-core`, `net.knightsandkings.knk.core.gates`)**: pure, Bukkit-free (only uses `org.bukkit.util.Vector` as this codebase's plain 3D-vector type, same as `GateBlockPairing`/`GateFrameCalculator` already do) Kabsch fit - `fit(fromPoints, toPoints)` centers both point sets, builds the 3x3 cross-covariance matrix, recovers the rotation via a hand-rolled 3x3 SVD (cyclic Jacobi eigendecomposition of the covariance's `HᵀH`, since Java has no built-in small-matrix SVD), with the standard reflection fix (negate the SVD's last singular vector when `det(R) < 0`) and a degenerate-input guard (fewer than 3 points, or the top-2 singular values not both meaningfully nonzero - covers 0/1/2 points and 3+ collinear points alike) returning `null`. `apply`/`applyInverse` round-trip exactly (`applyInverse` uses `Rᵀ`, the correct inverse of an orthogonal matrix). Verified by `RigidTransformTest`: exact recovery of a known synthetic rotation+translation, the reflection-correction path (a deliberately mirrored/non-rotation input), `applyInverse` round-tripping, and every degenerate case (0/1/2/3-collinear points, mismatched list sizes, null inputs).
- **`CachedGateDoor`** gained `fittedOpenTransform` (`RigidTransform`, null when no fit exists) and `openOnlyBlockSynthesizedRelativePositions` (`Map<Integer, Vector>`, open `BlockSnapshot` id → its synthesized closed-frame relative position), alongside the existing `openBlockPairing` field.
- **`GateLoaderAdapter.loadOpenBlockSnapshots`**: for `ROTATION` gates only (Decision 7 is `ROTATION`-specific; `VERTICAL`/`LATERAL`'s plain lerp was never the source of the reported non-rigid motion, so no fit is computed for them), a new `fitRigidTransform` helper takes the exact same `indexPairing` map `GateBlockPairing.pairNearestNeighbor` already produced, builds the paired closed/open world-position correspondence lists from it, and calls `RigidTransform.fit`. When a fit succeeds, every open-scan block *not* in the pairing (open-only) gets its closed-frame start point synthesized via `transform.applyInverse(openWorldPos) - anchor` and stored in the new map. `GateBlockPairing` itself needed no changes at all - exactly the "stays, repurposed" plan from step 5.
- **`GateFrameCalculator`**: the `ROTATION` branch of `calculateBlockPositionBreakdown` now branches on `gate.getFittedOpenTransform()` instead of the per-block `openTarget`: with a fit, the correction converges toward `transform.apply(anchor + relativePos)` (the *same* `R`/`t` for every block) instead of each block's individually-paired nearest-neighbor target; without one, it falls back to `position = arcPos` - the pure procedural arc, byte-for-byte, **ignoring any individual pairing entirely** (a deliberate behavior change from the old code, which still blended toward a pairing even with only 1-2 correspondences - now "nothing to fit" truly means "no correction at all"). ### 6.11 — Fix: hybrid rigid-transform-plus-residual mid-swing correction

✅ Done. Implemented and unit-tested (2026-09-17), live-tested 2026-09-17 and found still insufficient (jammed at the same frame, for a different reason - a floating-point rounding hazard, not a fit-quality one), then patched 2026-09-18 (item 6.11.1), live-tested again same day and found STILL insufficient (jammed at a different, earlier frame - proving 6.11.1's fixed-progress-threshold approach was itself the wrong tool), then patched again 2026-09-18 with a distance-based fix instead (item 6.11.2, confirmed live 2026-09-19), and finally a stray-cell-vacate + rigidity-tuning follow-up (item 6.11.3, **confirmed live 2026-09-20** - 4 full open/close cycles against entity 14 in `GeometryDefinitionMode=REGION`, clean, no orphaned blocks, swing reads as rigid). Decision and full rationale, including the algebraic pitfall that makes this harder than "just add a residual term": **Decision 8**, [ROTATION_GAP_FILL_DESIGN.md](./ROTATION_GAP_FILL_DESIGN.md). This section is the implementation plan for that decision.

**Root cause (recap, full evidence in Decision 8)**: item 6.10's uniform transform, applied to a *closed* block, can only ever predict a rotated copy of the sparse 32-block closed lattice. Entity 14's real open scan is genuinely denser than that in exactly the region Decision 7 already flagged as the fit's weak spot (the extra row farthest from the hinge). As `progress → 1`, paired closed blocks (converging on "the closed shape, rotated") and open-only blocks (converging on "the real, denser scan") converge on different, overlapping target sets - two of the door's own blocks end up wanting the same cell, one placement is refused, and after 5 consecutive ticks the gate jams before ever reaching the resting frame that would have reconciled everything.

**Chosen approach (Decision 8, option 4 - the hybrid)**: keep the uniform transform as the shared, rigid *base* motion (unchanged from 6.10 - this is still what keeps a well-fit block visually agreeing with its neighbors for most of the swing), and add a small per-block *residual* correction on top, tapered in non-linearly so it only becomes significant near the end of the swing:

1. **No change to the fit itself, `CachedGateDoor`, `GateLoaderAdapter`, open-only blocks, or the no-fit fallback.** All of 6.10's plumbing (`RigidTransform.fit`, `fittedOpenTransform`, `openOnlyBlockSynthesizedRelativePositions`, `GateBlockPairing` unchanged) is reused as-is. Only `GateFrameCalculator.calculateBlockPositionBreakdown`'s `ROTATION` branch, for a *paired closed block specifically*, needs its formula updated - see Decision 8's write-up for why open-only blocks and the degenerate case already need zero change (an open-only block's `residualTarget` is always exactly zero, by construction; the no-fit fallback still has nothing to compute a residual from).
2. **New formula for a paired closed block**:
   ```
   residualTarget     = openTarget - transformPos   // this block's own gap between truth and the shared prediction
   residualTaper      = progress ** 3                // NOT plain progress - see the pitfall below
   residualCorrection = residualTarget * residualTaper
   position = arcPos(frame) + uniformCorrection + residualCorrection   // uniformCorrection unchanged from 6.10
   ```
3. **The pitfall to not reintroduce while implementing this**: tapering `residualCorrection` by plain `progress` (matching `uniformCorrection`'s own factor) makes the two `transformPos` terms cancel algebraically, collapsing the whole formula back to exactly the pre-6.10 broken per-block blend (`(openTarget - arcPosFinal) * progress`) - passing the same exactness tests while reintroducing 100% of the original non-rigid motion. The residual's taper must be a genuinely different curve. `progress³` is the chosen default (documented rationale, including why the exact exponent is a tunable constant and not a correctness question, in Decision 8) - implement it as written, don't "simplify" it back to `progress`.
4. **Expose the residual/taper values in `BlockPositionBreakdown`** (or extend it) so the existing trace-logging path in `GateAnimationTask` can show them - useful for confirming live whether a specific outlier block's catch-up motion is behaving as designed, without another diagnostic-logging round trip.
5. **`GateRestingFramePlacer` still fully unchanged** - this fix only touches the mid-swing formula, same as 6.10.

**Tests** (extending 6.10's existing coverage, same file/classes):
- Regression: for a synthetic gate where the fit is exact (every paired block's `residualTarget` is zero), this hybrid must be byte-for-byte identical to 6.10's plain uniform-transform output at every frame - proves the residual is a genuine no-op when there's nothing to correct.
- New: a synthetic gate with one deliberately-mismatched pair (a nonzero `residualTarget`) must still return the exact closed position at `progress=0` and the exact real open position at `progress=1` (the algebra Decision 8 shows holds for *any* taper with `f(0)=0, f(1)=1`) - the taper-collapse pitfall itself should get a dedicated regression test asserting the result is **not** equal to the old `(openTarget - arcPosFinal) * progress` formula at an intermediate frame, so a future accidental "simplification" back to a linear taper is caught immediately.
- New: at a low/mid progress (e.g. 0.5), a block with a large `residualTarget` should show most of its positional divergence coming from `uniformCorrection`, not `residualCorrection` (residual's contribution should be small, per the cubic taper) - a direct, numeric check that the "stays visually rigid for most of the swing" property actually holds, not just an eyeball claim.
- Live verification: re-run entity 14's REGION-mode open/close cycle, confirm the animation actually reaches `AnimationState.OPEN`/`CLOSED` (no jam), the swing still reads as visually rigid for the well-fit majority of blocks, and all 49/32 resting-frame blocks are still exactly correct (no regression on 6.8/6.9's fixes). Also re-check `/knk gate info` reports no `JAMMED` state after a full cycle.

Implemented exactly as planned above:

The hybrid formula itself (`uniformCorrection` unchanged from 6.10, `residualCorrection = (openTarget - transformPos) * residualTaper(progress)`, `residualTaper(progress) = progress³`) lives entirely inside this one helper. Confirmed by construction (not just by reasoning) that open-only blocks and the no-fit case need zero special-casing: an open-only block's own `openTarget` *is* `transformPos` by definition of how its synthesized start point was built, so its residual reduces to the zero vector automatically; the no-fit path never reaches the residual computation at all (`transform == null` short-circuits `blendRotationPosition` before `openTarget` is even considered).

#### 6.11.1 — Follow-up fix: settle-and-hold near the end of the swing

🔶 Implemented and unit-tested 2026-09-18, live-tested same day and **found insufficient** - see 6.11.2 below.

- **Fix**: in `GateFrameCalculator.blendRotationPosition`, when a block has a real target to converge onto (`transform != null && openTarget != null`), remap `progress` for the *entire* blend (arc, uniform correction, and residual together, not just the residual) via `effectiveProgress = Math.min(1.0, progress / SETTLE_PROGRESS)` with `SETTLE_PROGRESS = 0.95`. This makes the block's position reach its exact real target by 95% raw progress and then hold there motionless (zero drift) for the remaining ~5% of ticks, instead of asymptotically approaching forever. An earlier idea (capping only the residual's own taper) was considered and rejected in the doc write-up: it would not have worked, since the arc and uniform-correction terms are independently progress-dependent and would still drift for as long as raw progress advances.
- Endpoints stay exact for any `SETTLE_PROGRESS` in `(0, 1]` (verified algebraically in Decision 8.1) - it's a visual tuning knob (how long the "already arrived, holding" tail is), not a correctness parameter, same property as the residual's own taper exponent.
- New test: `calculateBlockPosition_RotationNearEndOfSwing_SettlesExactlyBeforeTrueCompletion` - confirms a block is bit-for-bit exactly at its real target from several ticks before the true final frame onward, and confirms it is *not* yet exactly there one tick before the settle threshold (proving this is a genuine settle-and-hold, not the formula trivially being exact everywhere).

#### 6.11.2 — Follow-up fix: distance-based snap instead of a fixed progress threshold

✅ Implemented, unit-tested, and **confirmed live 2026-09-19** (`knk-plugin` commit `e11d2d1`). The user tested 4 full open/close cycles and confirmed the animation reliably completes every time - the jam is fixed. Two things flagged from that same test, addressed in 6.11.3 below: (1) one orphaned open-only block left behind after closing, at a position adjacent to but not part of the real closed structure; (2) the swing, while no longer jamming, still didn't look as rigid as wanted.

- **Fix**: in `GateFrameCalculator.blendRotationPosition`, replace 6.11.1's progress remap entirely. The blend (arc + uniform correction + residual, computed with raw, unmodified `progress` as originally in 6.11) is still computed as before; then, if the block has a real target (`openTarget != null`) and the blended result is within `SNAP_DISTANCE = 0.5` blocks of that target, the position snaps to the target exactly instead of using the blended value.
- `0.5` is not a re-guessed tuning constant - it is proven unconditionally safe directly from the geometry: two distinct real scanned blocks are never less than 1 full block apart (both are on the integer world lattice), so by the triangle inequality, being strictly within 0.5 of one target rules out simultaneously being within 0.5 of any other real target. `Math.floor()` (what actually decides a block's placed world cell) cannot be ambiguous about which real block this is once snapped, regardless of which specific pair of blocks or which frame is involved - this is what makes the fix adapt automatically to each block's own convergence rate instead of guessing a global timing constant that only fit the last observed failure.
- New test: `calculateBlockPosition_RotationBlockConvergingToTarget_SnapsExactlyOnceWithinSnapDistance` - walks every frame of a synthetic swing (rather than hand-predicting a boundary frame, since the whole point of this fix is that the boundary isn't reliably predictable by a simple formula) and confirms a block reaches its exact target strictly before the true final frame, stays there for every subsequent frame, and is confirmed not yet there the frame immediately before the snap. Replaces 6.11.1's now-removed settle test (same intent, different mechanism).
  - **Note on the test fixture itself**: a first version reused this file's existing large-translation fixture (anchor far from the world origin, ~150-block fit translation) and found the snap never triggered before the literal final frame. Traced to `VectorMath.rotateAroundAxis` rotating around the world origin, not the gate's own anchor - combined with that fixture's large translation, the uniform-correction term for any test point becomes over 100 blocks, swamping the realistic few-block residual the test needed to isolate. Fixed by building a dedicated fixture with an anchor near the origin, matching real gate geometry's actual scale - a reminder that this class of test needs magnitudes representative of real geometry, not just internally self-consistent ones.
- **Verified**: `./gradlew clean test` across `knk-core`/`knk-api-client`/`knk-paper` green - 143/143 `knk-core` (net unchanged from 6.11.1 - one test replaced another), 226/226 `knk-paper` unchanged, 14 pre-existing `@Disabled` skips unchanged.

#### 6.11.3 — Fix orphaned stray cells at completion; tune rigidity further

✅ Implemented and unit-tested 2026-09-19 (`knk-plugin`, branch `gate-structure-animation`, commit `17f016d`). **Confirmed live 2026-09-20** - the user rebuilt/deployed and ran 4 full open/close cycles against entity 14 (`GeometryDefinitionMode=REGION`): no orphaned blocks after closing or opening, and the swing reads as rigid under the quintic taper.

**Orphaned block, root cause**: `GateAnimationTask.finishOpening`/`finishClosing` call `GateRestingFramePlacer.transitionRestingFrame`, which vacates only what the *idealized* source resting frame contains that the idealized target frame doesn't (the real open-scan list vs. the real closed `BlockSnapshot`s). An open-only block's mid-swing position (item 6.10/6.11) is driven by a *synthesized* closed-frame start point - an inverse-transform extrapolation, not a real scanned position - so a leftover placement there is invisible to both idealized frames: it isn't the block's real open position, and open-only blocks were never part of the closed scan to begin with. `transitionRestingFrame` has no way to know it needs clearing. Confirmed live: a stray block left behind after closing at `(1375, 50, -586)`, adjacent to but not part of the real closed structure.

**Fix**: new `GateAnimationTask.vacateStrayCells(gate, targetFrame)`, called right before `transitionRestingFrame` in both `finishOpening` and `finishClosing`. Diffs the gate's *actual* last-known-placed cells (`lastPlacedCellsByGate`, the same real-placement tracking item 6.8 already introduced for the per-tick vacate step) against the true target resting frame, and vacates anything extra. This closes the gap generally, for any future case of this shape, not just this specific stray block - and touches only `GateAnimationTask`, not `GateRestingFramePlacer` (unchanged, per the standing constraint). No new test: the only new logic is the call sequence itself; the actual diff (`GateRestingFramePlacer.cellsToClear`) is already covered by existing tests, and `vacateStrayCells` has no Bukkit-free decision logic of its own worth extracting (matching this file's existing precedent for when a completion-path method does/doesn't get dedicated coverage).

**Rigidity tuning**: raised `GateFrameCalculator.residualTaper` from cubic (`progress³`) to quintic (`progress⁵`) per the user's request after confirming the swing, while no longer jamming, still didn't look rigid enough. A well-fit block's residual contribution now stays under ~3% through the first half of the swing (was ~13% at cubic) and under ~10% through 70% of the swing (was ~34%) - an outlier's individual catch-up motion is pushed later and becomes more concentrated. `SNAP_DISTANCE`'s 0.5-block snap (item 6.11.2) is unaffected and still independently guarantees exact, collision-free convergence regardless of how late that catch-up starts - raising the taper exponent is a pure visual tuning change with no correctness risk, same property documented for every taper/threshold constant in this item.

- **Admin-authored FormConfig data, not just code**: item 5.3 flags one example (`ConditionalValueMatchValidator`'s `GateType`/`MotionType` rule) but the general point applies broadly — any FormConfig/DisplayCondition rows authored against the old GateStructure-level fields (steps, visibility conditions, validators) need auditing once those fields move to `GateDoor`, since that configuration lives in the database, not in source-controlled code, and won't show up in a code diff.
