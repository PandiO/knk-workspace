## 2. The checkpoint (12 min)

`/siege admin skip cinix` shortens the matchmaking. Every `[Survival] Lobby cinix:` line below is in the server log.

1. **Checkpoint rows during the match**: `/siege join cinix`, pick a kit, play round 1. `/knk siege survival status` shows the new line `Checkpoint: API match <id>, revision n, sent n, failures 0, interval 30 s, last trigger round 1 start` — **`<id>` is the API match id** for every call below. `GET $API/api/siege-survival/matches/<id>/checkpoint` → `substate WAVE_ACTIVE`, `wave 1`, `completedWave 0`, `aliveEnemies`/`queuedEnemies` as in the status, `activeSpawnZoneIds [<zone>]`, `players[0]` with your `userId`, `kitId`, `matchBalance 0`, `ghost false`, `revision 1`. Kill one enemy and wait 30 s: `revision` went up (the interval), `matchBalance 70`, `kills 1`. Clear the round: `last trigger round 1 end`, the row says `INTERMISSION`, `completedWave 1`. Die in round 2 with a second player alive (or skip): the next row has `ghost true`. Roll a box and read the row during the reel: `pendingMysteryBoxRollId m<id>-p…`. `doorRepairs` is `[]` until S6.
2. **Special round** (optional, 2 min): author a special profile and an explicit entry for wave 2 on scenario 1 (the generic form endpoints of the S5 seeds `SurvivalSpecialWaveProfile` and `SurvivalSpecialWaveEntry`, e.g. `POST $API/api/SurvivalSpecialWaveProfiles` with `siegeScenarioId 1, key "wolves", name "Wolves", countOverride 3` plus its monster type, then `POST $API/api/SurvivalSpecialWaveEntries` with `survivalSpecialWaveProfileId, kind "Explicit", wave 2, priority 1`; check the stored shape with the matching `GET`), restart the server (cache), start a match: the round 2 title reads **"Round 2 — Special round: Wolves · 3 enemies"**, chat `Special round: Wolves - 3 enemies this round.`, the status line `… round 2 … special wolves …`, the checkpoint row `specialProfileKey "wolves"`, log `round 2 started: … special profile <id> (Wolves)` and, when cleared, `special profile … cleared (no special reward, DESIGN §7)`. No reward or drop is attached to a special round (flag S8b-3).
3. **Team wipe → survival result screen**: die as the last living player during a round with at least two kills on your name. Everyone online sees `Survival Test lobby is over: the defenders were wiped out. Waves reached r, completed c. k enemies slain.` — **not** the PvP "… won the siege …" line. You see four lines: `Survival over - Your team was wiped out. Waves reached r, completed c.`, `You: k kills (b headshot/critical) · d deaths · team k kills.`, `Match coins: n left (earned e, spent s) - match currency, gone with the match.` and `Permanent reward: +C coins, +X XP (per-kill accrual c.c / x.x, rounded down once; being recorded…)` — the permanent payout **separate** from the match balance (§11), and C/X are the floor of the exact accrual (3 plain kills = 90.0 / 9.0 → +90 / +9; 3 headshot kills = 99.0 / 9.9 → +99 / +9). A moment later: `Rewards credited: +C coins, +X XP are on your account.` The post-match wait at the hub and the restore are as before; the outcome title is still the Siege one (flag S8b-4). No `Your rewards: …` PvP line, no capture/holding reward lines.
4. **The result row and the ledger**: `GET $API/api/siege-survival/matches/<id>/result` → `endReason TeamWipe`, `reachedWave`/`completedWave` as announced, `earnedKills` = the team's kills, `systemKills` = the stuck-handling kills (0 unless step S5-11 happened), `source Plugin`, `rewardPolicyVersion v1-per-kill`, `players[0]` with `presentAtEnd true`, `kitId`, `kills`, `bonusKills`, `deaths`, `matchCurrencyEarned`/`Spent`/`finalMatchBalance` as the screen said, `coinsAccrued`/`xpAccrued` exact, `coinsSettled C`/`xpSettled X`, `mysteryBoxRolls/Claims/Forfeits` from your rolls; `settlement.settlesRewards true`, `totalCoins C`, `totalXp X`, `ledgerKey siege-survival:<id>`, **`settledAt` set and `ledgerPostingId` set**, `playersSettled 1`. `/balance` → your coins rose by **exactly C**; `/transactions me xp` → one `SURVIVAL_REWARD` posting of X XP (and a title bonus only if that XP crossed a bracket, as in PvP). Log: `posting the survival result of match <id> (TeamWipe, waves r/c, 1 players, settles true: C coins / X xp)` then `result of match <id> posted; settled C coins / X xp for 1 player(s), ledger posting <guid> at …`; `/knk siege survival status` → `Result cinix match <id>: posted - settled … ledger posting … at …`. The recovery file `plugins/KnightsAndKings/siege-survival/matches/<id>.yml` is **gone** (it existed during the match with `state: OPEN`).
5. **Leaver forfeits** (second player): in the next match let the mate make a kill and `/siege leave` during a round, then wipe. The mate gets no result lines; the row has the mate `presentAtEnd false`, `leftAt` set, their `kills` kept, `coinsSettled 0`/`xpSettled 0`, `finalMatchBalance 0`; `playersSettled 1`; your own screen unchanged. Log `… 2 players, settles true …` with only your coins in the totals.
6. **A repeat post pays nothing twice**: take the body from the `GET` of step 4, drop the API-filled fields (`rewardPolicyVersion`, `source`, `recordedAt`, every `mysteryBox*`, `settlement.settledAt/ledgerPostingId/playersSettled`) and `POST $API/api/siege-survival/matches/<id>/result` it with `X-API-Key` → **200** with the same stored row; `/balance` and `/transactions me xp` unchanged. Change one number (e.g. `coinsSettled` + 1) and post again → **409 `ResultAlreadyStored`**; a fresh match whose plugin numbers disagree would be the **409 `SettlementMismatch`** the plugin logs as SEVERE and never retries with changed numbers (not provokable from the client; the unit tests cover it).
7. **Admin stop → abort row, open roll forfeited**: start a match, roll a Mystery Box and, during the reel or the claim window, `/siege admin stop cinix`. Chat: `Survival Test lobby ended: stopped by an admin. Waves reached 1, completed 0. No permanent rewards (aborted).`, your lines end with `Permanent reward: none - the match was aborted (stopped by an admin).`, then `Match result recorded (already stored).` or `Match result recorded.` (which of the two depends on whether the plugin's result or the Siege abort reached the API first — both are right). `GET …/result` → `endReason AdminAbort`, `settlesRewards false`, `totalCoins 0`, `ledgerKey null`, no `settledAt`; `source` is `Plugin` (waves and kills filled) or `Abort` (waves 0). `GET …/mystery-box/rolls` → the roll is `Forfeited` with `forfeitReason MatchEnded` (plugin or API side; both say `MatchEnded`). `/balance` unchanged. Log: `posting the survival result of match <id> (AdminAbort, …, settles false: 0 coins / 0 xp)` and either `… posted; no settlement (AdminAbort)` or `match <id> already has a result row (ResultAlreadyStored|MatchAborted); using the stored one`.
8. **PvP still settles as before** (one match): on a scenario **without** survival settings (or scenario 1 after `DELETE $API/api/SiegeSurvival/scenarios/1/settings` and a restart), play one ordinary PvP match to its end: the PvP announcement and the `Your rewards: …` lines, `SIEGE_REWARD` in `/transactions`, no `[Survival]` line, no survival result row (`GET …/result` → 404). Re-enable survival afterwards (`PUT …/settings` as in S7b step 2.1 + restart).
9. **Restart during a match** (S61): start a match, let round 1 spawn, confirm `plugins/KnightsAndKings/siege-survival/matches/<id>.yml` exists (`state: OPEN`, `end-reason: ServerRestart`, your user id under `players`), then `stop` the server. On the next start the log shows, in this order or interleaved: the Siege abort/restore as for PvP (`[Siege] …` abort of the match, or `Startup recovery aborted 1 match(es) left open by the last run (ServerRestart)` when the stop did not get the abort out), `[Survival] Recovery of match <id>: the last run left this survival match open; posting a ServerRestart result (no settlement)` and either `… already has a result row (ResultAlreadyStored|MatchAborted); using the stored one` or `… posted; no settlement (ServerRestart)`, then `[Survival] Recovery: 1 survival result file(s) replayed to the API`. The file is gone; `GET …/result` → `endReason ServerRestart`, `settlesRewards false`; `/knk siege survival status` → `Result recovery match <id>: posted …`. Join again: your inventory is restored on join as in PvP; `/balance` unchanged.

**If something is off**
- `Checkpoint: API match id unknown, … skipped without match id n`: the Siege `createMatch` has not answered (API down at the start); checkpoints resume with the next trigger once it has. A result at the end then waits up to 60 s for the id (`the API match id is not known yet; the result waits …`) and is dropped with a SEVERE line when it never comes (an unrecorded round has no row to post to; flag S8b-2).
- `checkpoint failed (<trigger>): …; further failures are logged once a minute`: the API is unreachable; the match goes on, the next trigger sends again; `failures n` in the status.
- `Rewards credited` never arrives but `Permanent reward: +C …` did: look for `posting the result of match <id> failed (attempt n/8): …; retrying in s s` (transport error; the same body is retried with backoff, then `giving up for now (kept for the next start)`: the file stays with `state: RESULT` and is posted again at the next start) or `the API rejected the settlement of match <id> (SettlementMismatch): <the API's differences>` (SEVERE, final: the plugin's numbers and the API's disagree — report both).
- `Result cinix: waiting for the API match id (TEAM_WIPE)` in the status: see the first item.
- The PvP announcement appears for a survival match: `presenting the result failed; the PvP result is shown` (SEVERE with the stack) — report it.

## 3. What to watch in the server log

`[Survival] Lobby cinix:` lines added by S8b: `round n started: … [, special profile <id> (<name>)]`, `round n completed; … [; special profile <id> cleared (no special reward, DESIGN §7)]`, `checkpoint skipped (…): the API match id is not known yet` (once), `checkpoint failed (…)` (once a minute), `posting the survival result of match <id> (<reason>, waves r/c, p players, settles true|false: C coins / X xp)`, `result of match <id> posted; settled C coins / X xp for p player(s), ledger posting <guid> at <time>` or `…; no settlement (<reason>)`, `match <id> already has a result row (<code>); using the stored one`, `stored result of match <id> fetched; …`, `posting the result of match <id> failed (attempt n/8): …; retrying in s s` (WARNING), `the API rejected the settlement of match <id> (SettlementMismatch): …` (SEVERE), `the API match id never became known; the survival result (…) is dropped` (SEVERE). Startup: `[Survival] Recovery of match <id>: …`, `[Survival] Recovery: n survival result file(s) replayed to the API`. `[Survival] Could not write the recovery file of match <id>` (WARNING) only when the data folder is not writable. Nothing else at SEVERE.

## 4. Flags that need a decision after the test

From the chain report's S8b block: **S8b-1** (`equipmentMode` is sent as null = the scenario's setting at post time, not the frozen mode), **S8b-2** (a result without an API match id is dropped after 60 s — nothing to settle against), **S8b-3** (no special-wave reward or drop: DESIGN §7 "no unrequested special-wave reward … is implied"), **S8b-4** (the post-match outcome title stays the Siege one, "Defeat" for a wipe), **S8b-5** (the plugin posts an `AdminAbort` / `ServerRestart` result too, so an aborted match's row carries waves and kills when the plugin wins the race — S8a's note said the abort row alone is enough), **S8b-6** (leavers' kills and spending stay in the result as history; their accrual is forfeited at the leave, so `coinsAccrued` is 0 for a leaver), **S8b-7** (the first checkpoint of a match is written on the first tick of PREPARING, before round 1, so the interval counts from there), **S8b-8** (the provisional recovery marker is refreshed at round changes and leaves only, not every checkpoint — a crash mid-round posts the last round boundary's waves).
